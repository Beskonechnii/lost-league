# Архитектура — как устроены подсистемы

Ядро — **один источник истины (БД)**: админка пишет, публичная таблица и графика читают.
Здесь — устройство подсистем: модель данных, синк, реестр баллов, студия, драфт, ростер,
групповая стадия, архив, турниры.

**Почему сделано именно так — в [`DECISIONS.md`](./DECISIONS.md)** (журнал решений с датами).
Где что лежит — `MAP.md`, что осталось — `BACKLOG.md`, ход работ — `WORKLOG.md`.

## Встраивание в чужой лендинг

Маркетинговый лендинг живёт отдельно (Tilda), приложение — на субдомене. Публичную таблицу
можно встроить туда `iframe`'ом либо `fetch`'ем нашего API. Для `iframe` нужен заголовок
`frame-ancestors` со списком доменов — переменная `FRAME_ANCESTORS` (ставится в `web/next.config.ts`),
без неё браузер встраивание заблокирует. Служебную часть не встраиваем.

Запасной путь вообще без сервера — статический экспорт таблицы (`scripts/build-standings-site.ts`).

## Модель данных

**Источник истины — `web/prisma/schema.prisma`** (там же комментарии к полям). Ниже — назначение моделей:

| Модель | Зачем |
|---|---|
| `Team` | команда: `slug` (ключ импорта и имя файла ассета), айдентика для графики — `logo`, `wordmark`, `photo`, `color` |
| `Player` | игрок: `slug`, `accountId` (Dota/Steam32), ссылки на профили, анкета (`telegram`, `birthday`, `city`) |
| `Series` | **личная встреча (Bo1/Bo3) любой стадии** — контейнер архива турнира: дивизион, `stage` (group/playoff), группа либо половина сетки + раунд, счёт. Бывшая `GroupSeries` |
| `Match` | одна карта: пара команд, расписание, статус, победитель, сторона Radiant, `openDotaMatchId`, длительность и место в серии (`seriesId` + `gameNumber`) |
| `MatchStat` | стата игрока на карте из OpenDota — из неё считаются рейтинги турнира, инфографика и подсказка MVP |
| `Ward` | расстановка вардов карты (obs/sen, координаты, тайминги, кто снял) — из неё «карта вардов команды» (`/admin/vision`) |
| `PointsEntry` | реестр баллов (см. TRACKING) |
| `Render` | сохранённая генерация графики: `templateId` + payload формы |

- **Standings** не храним как истину — считаем: wins/losses из `Match`, очки из суммы `PointsEntry`. (Можно кэшировать.)
- **MVP** = запись `PointsEntry(reason=mvp)` + отметка игрока матча.
- sqlite не поддерживает enum → перечисления хранятся строками, допустимые значения — в комментариях схемы.
- `openDotaMatchId` — **строка**: id матчей Dota не влезает в 32-битный Int.

## SYNC (OpenDota)

1. Вход: `openDotaMatchId` (админ вводит после игры).
2. Читается **тот же `MatchReport`, что рисует постгейм** (`loadMatchReport()` в `match-api.ts`, через общий
   файловый кэш) → `MatchStat` на каждого игрока, который есть в ростере: герой, победа, K/D/A, урон по героям
   и строениям, лечение, net worth, GPM/XPM, добито/денаи, стаки и варды.
3. Из статы — **авто-подсказка MVP** (топ по композитному скору) + данные для инфографики и рейтингов.

**Решение: у синка и у постгейма один источник (29.07.2026).** Раньше `match-sync.ts` ходил в OpenDota сам и
брал пять полей — форма данных для показа и для базы разъезжалась, а поход в сеть не переиспользовал кэш
отчётов. Теперь в базу приземляется ровно то, что видно на странице матча: цифра в рейтинге и цифра в отчёте
не могут разойтись по определению.

⚠️ Детальные поля (урон, лагеря) есть только у **распарсенных** матчей. Если не распарсен — дёрнуть `POST /request/{id}`, подождать, повторить.

## TRACKING (баллы)

- **Реестр `PointsEntry` — единственный способ менять баллы.** Итог = сумма записей.
- **Корректировки = новые записи** (сторно/добавление), ничего не перетираем → полный аудит.
- Правила (заготовка, числа позже):
  - `placement` — победа матча → очки команде.
  - `mvp` — игрок матча → очки/отметка.
  - `cast` / `stream` — кастеру/стримеру за эфир.

## Продукт и служебная часть

Маршруты разделены на две группы одного приложения: `src/app/(public)/` — продукт (лендинг,
турниры и их витрины, ростер, разбор матча), `src/app/(admin)/` — всё, что пишет (студия, правка
ростера, модерация, архив серий). Группы на URL не влияют: у каждой свои `layout`, навигация и
метаданные, у служебной — `robots: noindex`. Граница «читают/пишут» видна прямо в адресе.

Разница между группами — только в правах и метаданных: хром у них общий (один сайдбар,
`src/app/_components/app-shell.tsx`), состав его пунктов режется правами (`currentPermissions()`
в `src/lib/account.ts`). Отдельного `isAdmin()` больше нет — «показывать ли кусок» решает право,
а не роль. **Добавляя поле на витрину, проверяй: это факт о лиге или состояние наших данных?**
Второе — под правом (`can()`).

Почему так и почему не отдельный репозиторий — `DECISIONS.md`, «две route-группы одного приложения».

## Флоу (итог)

```
матч сыгран → админ вносит match_id → SYNC (OpenDota) → MatchStat
           → подсказка MVP → админ подтверждает MVP + баллы → PointsEntry
           → Standings пересчитан → публичная таблица + данные для визуала
```

## Студия графики (`/studio`)

_Где лежат файлы движка — в [CLAUDE.md](./CLAUDE.md). Здесь — принятые решения._

Генерация графики к матчам живёт в том же приложении и на тех же данных: команды и игроки — из ростера,
матчи — из `Match`. Отдельного сервиса рендера не заводим.

**Решение: шаблон декларативный** — размер холста + схема полей (`FieldDef`) + React-компонент. Форма мастера
строится из схемы автоматически, поэтому новый шаблон не требует ни новых страниц, ни новых форм. Цена решения —
шаблон ограничен набором типов полей (text/select/team/player/group); расширять их приходится в одном месте.

**Решение: экспорт клиентский** (`modern-screenshot`), а не серверный скриншот. Превью и экспорт — один и тот же
компонент, масштаб снимается на клоне → PNG выходит ровно в размер шаблона. Это даёт инвариант «что вижу — то и
скачал»; ломать его нельзя, иначе расхождение превью и результата придётся ловить глазами.

`/studio/render/[templateId]?p=<base64 payload>` — «голый» рендер без интерфейса: задел под серверный скриншот
(Playwright), когда понадобится рендер по API. Компонент общий с превью, расхождений не будет.

Подложки — экспорт из Figma **без текста и лого команд** (их рисует компонент). Файла нет → градиент-заглушка.
Сохранённые генерации — модель `Render` (payload формы), чтобы переоткрыть прошлый анонс и поправить,
а не собирать заново.

**Решение: пост-гейм скорборд — поле `kind:"match"` (05.08.2026).** Шаблон `postgame-board` (референс: Falcons
vs Tundra) — плотная таблица 10 игроков × колонки (герой, K/D/A, урон, предметы), с перегородками между блоками
команд и колонками. Такое не заполнить руками и не разложить свободными элементами canvas-редактора, поэтому
добавлен новый тип поля `match`: оператор выбирает карту, а весь скорборд разворачивается из неё. Данные и
**предметы** берутся из того же `MatchReport`, что рисует постгейм (`buildScoreboard()` в `src/lib/scoreboard.ts`
поверх `loadMatchReport()` — общий кэш и лимит), лого/цвета команд — из ростера по `radiantTeamId`. Отчёт тяжёлый
и серверный, поэтому в поток `resolvePayload` он не грузится скопом: мастер догружает борд по выбору матча
(`GET /api/studio/match-board`), а «голый» рендер собирает его по `matchId` из payload (`getBoardsForPayload`).
Radiant — верхний блок, Dire — нижний (конвенция Dota и страницы `/match`). Сохранённый `Render` привязывается к
`Match`, поэтому графика видна из архива серий: у каждой карты в `/admin/series` есть кнопка «скорборд», которая
открывает мастер с уже выбранной картой (`/studio/new/postgame-board?match=<id>`).

### Генерация картинок по API (`/studio/generate`)

Второй способ получить картинку — не сборка по данным лиги, а свободная генерация через **OpenAI Images**
(модели `gpt-image-*`). Настройки: модель, промт, размер, качество, количество, режим «использовать как референс».

**Решение: ключ только на сервере.** `OPENAI_API_KEY` живёт в `web/.env` (в `.gitignore`), читает его
единственный роут `POST /api/studio/generate`. Из браузера в OpenAI не ходим — иначе ключ утечёт в бандл.
Поэтому же модуль разделён надвое: `lib/openai-images.ts` (сервер, ключ) и `lib/image-options.ts`
(варианты настроек, безопасно импортировать в клиентский компонент).

**Решение: один роут на два эндпоинта.** Есть референсы → multipart `POST /v1/images/edits` (файлы полем
`image[]`), нет → JSON `POST /v1/images/generations`. Для вызывающего разница только в наличии файлов.
Модели `gpt-image-*` всегда возвращают base64 и **не принимают `response_format`** — его не шлём.

Результаты сохраняются в `public/uploads/generated/` (вне git, чистится вручную). В БД не пишем: это черновой
материал, а не сущность лиги. **Каждая генерация платная** — счёт идёт на аккаунт из ключа; в UI выбрано
дешёвое качество по умолчанию («Авто»), для черновиков есть `gpt-image-1-mini` и «Низкое».

## UNDERBEER 2.0 — шоу-драфт (`/underbeer`, 28.07.2026)

Инструмент эфира: оператор собирает **шоу-команды** из живого ростера драфтом капитанов. Раздел в
служебной части (`(admin)`, за паролем), пункт меню «UNDERBEER 2.0» рядом со Студией.

**Решение: это вывод оператора, а не ростер.** Шоу-команды к `RosterSpot` отношения не имеют — как и
студийная графика, это эфемерный результат, а не источник. Поэтому новая модель `DraftSession` хранит
**всё состояние одной JSON-строкой в `payload`** (как `Render`), а не плодит таблицы команд/составов.
В payload лежат только **id игроков** (`picks`/`captainId`); карточки (ник/фото/mmr/позиция) резолвятся
из ростера при чтении (`src/lib/draft-data.ts` → `draftPool()`). Ушедший из ростера игрок просто выпадает
из состава — драфт живёт один эфир, дублировать снимок всего игрока в БД незачем.

**Решение: сначала отбор участников, потом команды.** Автомат начинается с фазы `roster`: из полного
ростера (поиск по нику/имени, колонки по позициям) оператор отмечает игроков турнира (`participants` в
состоянии), и уже **весь драфт идёт только из них** — пул команд и капитанов фильтруется по участникам.
Старые сессии без `participants` читают весь ростер (обратная совместимость).

**Решение: правила — чистый модуль без БД** (`src/lib/draft.ts`, как `qualification.ts`), поэтому один код
гейтит кнопки на клиенте и мог бы проверяться на сервере. Автомат `roster → config → draft → done`:

- Команд ≥ 2, каждой назначается капитан (капитан занимает первый слот, в драфте не участвует).
- Порядок ходов — **змейка** (1→N, N→1, …): иначе последний капитан всегда собирает объедки.
- В свой ход капитан **либо** берёт 1 игрока из пула, **либо** крадёт 1 из чужого состава
  (кража = действие хода, обычного пика в этот ход уже нет). `currentTurn()` идёт по змейке и пропускает
  уже укомплектованные команды — команда могла добрать состав кражей раньше очереди.
- **Кража честная: у кого украли — добирает вне очереди.** После кражи пострадавшая команда сразу берёт
  одного игрока из пула (`pendingPick` в состоянии, `currentTurn().comp = true`), и только потом змейка
  возобновляется с продвинутого за вором указателя. Так никто не остаётся в меньшинстве посреди драфта.
  Цепной кражи нет: в форс-добор можно только пикать из пула, красть/закреплять нельзя.
- «Закрепить» и «Украсть» — **по разу за весь драфт** на команду. Lock защищает своего игрока от кражи и
  **ход не тратит** (защитное действие); капитана и закреплённых красть нельзя.
- Драфт завершён, когда все команды набрали `targetSize` (капитан в счёт входит).

**Решение: клиент — истина хода, сервер только хранит.** Борд (`_components/draft-board.tsx`) применяет
редьюсеры из `draft.ts` и после каждого действия автосохраняет `PATCH /api/underbeer/[id]` весь payload;
роут лишь проверяет версию формата. Пул перетаскивается (`@dnd-kit/core`) или выбирается кликом,
сегментирован по позиции — **каждая позиция отдельной колонкой** (керри…хард + «без позиции»). **Ошибку
правила показываем строкой, борд не роняем**: редьюсеры бросают на невалидном входе, но кнопки и так
гейтятся предикатами `can*`.

**Решение: автосейв через очередь, а не fetch на каждое действие.** PATCH'и уходят строго по одному, и в
полёте всегда только последнее состояние (`pending`/`flushing` в борде). Иначе на быстрых кликах поздно
прилетевший ранний запрос перезаписывал бы финал — драфт откатывался к более раннему состоянию (поймано при
проверке: сессия «съезжала» обратно в конфиг). Оператор один, конфликтов между людьми нет — очередь решает
ровно переупорядочивание запросов одного клиента.

**Удаление.** Драфты чистятся из списка (`DELETE /api/underbeer/[id]`, кнопка на карточке, оптимистично).
По той же схеме сделано удаление сохранённых генераций студии — `DELETE /api/studio/renders/[id]` и кнопка
в «Истории» (`studio/_components/render-history.tsx`): payload формы это черновик, а не сущность лиги.
Подтверждение — **встроенное (два клика)**, а не `window.confirm()`: нативный диалог подавляется в
webview (панель предпросмотра, десктоп-приложение), и кнопка «молча не работала».

**Решение: оверлей для OBS — отдельная «голая» группа `(bare)`.** Результат драфта отдаётся публично на
`/overlay/underbeer/[id]` (группа `src/app/(bare)/` без навигации и без пароля: у OBS админской куки нет,
а показывается только результат, не операторские кнопки). Операторский борд `/underbeer` при этом закрыт —
префикс добавлен в `needsAdmin()`. Держать оверлей внутри `(admin)` не вышло бы: там бы он унаследовал
`AdminNav` и пароль. Запись (`POST`/`PATCH`/`DELETE /api/underbeer`) закрыта общим правилом «не-GET к `/api`».

## Ростер (`/roster`) — справочник лиги

_Файлы и порядок запуска импорта — в [CLAUDE.md](./CLAUDE.md). Здесь — решения._

**Решение: ростер отделён от студии.** Команды и игроки — единственное место, куда данные **пишут**;
студия и таблица их только читают. Иначе одно и то же название команды разъезжается по трём разделам.

**Решение: `slug` — сквозной ключ.** По нему идёт upsert при импорте и по нему же подбираются файлы лого и фото.
Одно имя связывает гугл-таблицу, БД и картинку — не нужно вести отдельный маппинг.

Роль — строка из списка в `roles.ts` (`carry | mid | offlane | soft-support | hard-support | standin | coach`);
**порядок массива задаёт сортировку состава** везде, поэтому менять его — значит менять вывод во всей графике.

Картинки — локально в `public/uploads/` (в `.gitignore`: это данные лиги, а не исходники).

**Решение: форму картинки задаёт слот, а не вёрстка (04.09.2026).** Раньше файл ложился в `public/uploads`
как есть, а слоты на страницах квадратные: лого 3:2 получало поля с одной стороны, портрет 9:16
резался `object-cover` по случайному месту. Теперь у каждого поля картинки есть **норма** —
`src/lib/image-norms.ts`: размер файла, соотношение, способ вписывания (`cover` — заполнить и срезать
лишнее, `contain` — вписать целиком с прозрачными полями) и формат (`png` там, где нужна прозрачность:
эмблема, вырезка «по грудь»; `webp` для баннеров). Файл приводится к норме **в браузере**, до загрузки:
окно подгонки (`app/_components/image-fit.tsx`) показывает рамку целевого формата, кадр в ней таскают и
масштабируют, `canvas` рисует ровно `width×height` нормы. Сервер (`/api/roster/upload`) остаётся тупым
хранилищем и про подгонку не знает. Одними и теми же цифрами рисуются рамка подгонки, превью в форме и
подсказка оператору — норма меняется в одном месте.

**Импорт составов берёт xlsx, а не CSV** — ссылки на профили в таблице являются гиперссылками ячеек, в CSV их
попросту нет. Из адресов `dotabuff.com/players/<id>` достаётся `accountId`; ссылка на что-то другое (сайт лиги,
Stratz) → поле пустое. Дивизион берётся из названия вкладки («Команды 1 div»), роль — из колонки «Роль»
(1–5, «Тренер», пусто → замена). Ключи `sheet-to-roster.ts`: `--only <слаги>`, `--div 1`,
`--alias "300$=300-dollars"`, `--dry`.

**Решение: MMR хранится у игрока, у команды — считается (23.07.2026).** `Player.mmr` приходит из колонки «MMR»
той же таблицы сезона. У команды поля нет: `teamMmr()` в `roster-data.ts` берёт **только основу** (позиции 1–5) и
отдаёт среднее и сумму — по той же логике, что и standings, которые тоже не хранятся. Замены и тренер в расчёт не
идут: иначе цифра, по которой команды сравнивают, зависела бы от того, сколько человек вписали в запас.

**Решение: дубль команды — ошибка, а не предупреждение (23.07.2026).** Раньше `sheet-to-roster.ts` только дописывал
команды в `data/roster.json` и никогда ничего не убирал, поэтому команда, сменившая слаг, оставалась в файле навсегда
и рядом с ней появлялась вторая (`300-dollars` + `300`). Теперь таблица — источник истины: при разборе целиком
команда разобранного дивизиона, которой в таблице больше нет, из файла удаляется (при `--only` — нет, там мы про
остальные ничего не знаем). Ручные правки при этом переживают перезалив: непустой `accountId` из файла не затирается
пустой ячейкой таблицы.

Второй рубеж — в `import-roster.ts`: перед записью проверяются три случая (один слаг дважды в файле; одна команда
под разными слагами в файле или в БД; один игрок **действующим** сразу в двух командах), и при любом импорт
**падает целиком**, а не чинит данные на ходу.

**Общий пул команд — таб «Ростер» (`/roster`, 28.08.2026).** Отдельный верхний таб рядом с «Турниры»:
все команды лиги в одном месте, сквозь сезоны, с фильтром по турниру и поиском. Отличается от витрины
внутри турнира (`/tournaments/<slug>/roster`), которая режет команды по одному сезону. Список даёт
`listPoolTeams()` (`roster-data.ts`): каждой команде показывает её **собственный актуальный** состав, а
не состав глобально «текущего» турнира. «Актуальный дивизион» команды вычисляет `teamDivision()`
(`tournaments.ts`) по единому правилу `tournamentRank` — кандидаты берутся из мест состава (`RosterSpot`)
и участия (`TournamentEntry`), приоритет у дивизиона, где реально есть состав, среди них — самый свежий
турнир (running > registration > finished, при равенстве — поздний старт; draft не показываем). Эта же
функция кормит и карточку команды: раньше она смотрела только `TournamentEntry`, и команда с местами
состава, но без участия (рассинхрон — участие сняли, места остались), показывала «Основа не заведена».

**Двухэтапное удаление команды (`Team.archivedAt`).** Удаление команды разрушительно (на неё висит
история — матчи, серии, места в группе), поэтому оно в два шага, оба под правом `roster.delete`:

- **Первое — в архив** (`DELETE /api/roster/teams/[id]?mode=archive`): ставит `archivedAt`. Команда
  исчезает из общего пула, но её прошлые таблицы и матчи целы — витрины турниров показывают её как
  прежде (архив трогает только таб «Ростер»). Обратимо: `POST .../restore` снимает флаг.
- **Второе — полностью** (`?mode=purge`): физический снос со всей историей. Разрешён только для уже
  архивной команды — один клик не сносит боевую команду со статистикой. Матчи на команду ссылаются без
  каскада (иначе случайное удаление рвало бы историю), поэтому в транзакции их сносят явно (стата и
  варды каскадятся от матча), денормализованный `Ward.teamId` обнуляют, остальное (составы, участие,
  серии, места в группе) уходит каскадом при удалении команды.

Кнопки видит только оператор с `roster.delete`; в табе есть разрез «В пуле / Архив» (серверный, `?view`).
Действия — **серверные** (`roster/_components/actions.ts`, `revalidatePath('/roster')`), а не `fetch` +
`router.refresh()`: в этом дев-билде Next обновлённый RSC до клиентского списка не доходил (счётчики
менялись, карточки — нет). Плюс оптимистичное скрытие карточки в `PoolExplorer` — мгновенный отклик,
не дожидаясь серверной перерисовки. Общие DB-операции (архив/возврат/снос) — в `lib/team-admin.ts`,
их же зовёт API-роут `/api/roster/teams/[id]`. Подтверждение удаления — **встроенное** в бар («Убрать
из пула» → «Точно? Да / Отмена»), а не нативный `window.confirm`: в песочном iframe (превью,
встраивание в лендинг) confirm молча возвращает `false` без диалога — и кнопка «не нажималась».

**Пул игроков (`/roster/players`).** Пара к пулу команд: те же фильтр по турниру и поиск, тот же
сквозной по сезонам список (`listPoolPlayers`), карточки — общий `PlayerMiniCard`. Переключатель
«Команды / Игроки» (`PoolSwitch`) стоит в теле обеих страниц — это разрез одной витрины, не отдельный
раздел (UI-GUIDELINES §2, L4). Удаления у игроков нет (просили только список); подсветку «нет
account_id» видит лишь оператор. У каждого игрока показываем его актуальную команду (по свежести
турнира его мест), прочие — строкой «ещё в …», и турниры, где он играл, — метками и фильтром.

**Ручного создания команд/игроков в UI больше нет.** Форма «Добавить команду/игрока» (`CreateForm`)
удалена отовсюду — и из витрин турнира, и из пула. Команда и игрок заводятся только штатными путями:
**заявкой** капитана (`/tournaments/<slug>/apply` → апрув), **импортом** таблицы сезона оператором и
**регистрацией** игрока (анкета → модерация). Свободное поле «впиши ник/название» плодило дубли и
сущности, которых лига не знает, — ровно то, от чего ушли в приёме составов (см. DECISIONS, 27.08.2026).
Заодно удалены и POST-роуты `/api/roster/{teams,players}` — остались только GET (списки для студии и
разбора матча); заводит команды/игроков теперь исключительно код заявок, импорта и регистрации.

## Групповая стадия

Отдельный этап, отыгранный до плей-офф. Источник — вкладка «GS» таблицы сезона, скрипт
`scripts/import-group-stage.ts --sheet <id> --div 1`. Модели: `GroupEntry` (строка команды в группе)
и `Series` со `stage="group"` (личная встреча, счёт серии). Своя вкладка — `/standings/<div>/groups`.

**Два дивизиона (28.07.2026).** Раздел таблиц division-aware: маршруты `/standings/[div]` (`d1`/`d2` →
`Division 1`/`Division 2`), голый `/standings` редиректит на `d1`. Справочник — `src/lib/divisions.ts` (slug ↔
имя ↔ подпись), он же питает две вкладки навигации «LOST D1»/«LOST D2» и под-вкладки дивизионов на `/roster/teams`.
`getStandings(division)` и `getGroupStage(division)` фильтруют по дивизиону; иначе группы A/B двух дивизионов
слились бы в один блок. Импорт GS ищет команду **сначала в своём дивизионе** — одноимённые «ReMix» в D1 и D2
иначе схлопнулись бы в одну; расхождения названий между вкладками «Команды» и «GS» разводит `--alias`
(например `Looking For a Guilty Prime=pasechniki`).

**Решение: единственный источник — сетка встреч (23.07.2026).** И/В/П/О и в группе, и в таблице лиги считаются
из `Series`, поэтому правка встречи двигает обе таблицы сразу — синхронизация выходит сама, копировать
данные между ними не нужно. `GroupEntry` остаётся, но только как **снимок таблицы сезона для сверки**: место в
группе (его из сетки не вывести) и исходные числа, которые показываются в скобках, если расчёт с ними разошёлся.

`getStandings()` складывает три слагаемых: встречи (`Series` любой стадии), одиночные матчи **без серии**
(`Match` с пустым `seriesId` — всё, что завели мимо архива) и ручные начисления (`PointsEntry`). Карты серии
намеренно пропускаются: они уже посчитаны в самой серии, иначе один Bo3 дал бы четыре сыгранных вместо одного.
Таблица делится **по группам**: команды из разных групп между собой не играли, и складывать их очки в один ряд
нечестно.

**Порядок в группе берётся из таблицы сезона, а не из расчёта.** При равенстве очков и побед (morbus mentis и
Eclipse Gaming — обе 4-3 и 12 очков) порядок задавал организатор, и по цифрам его не восстановить. Поэтому
`GroupEntry.place` главнее сортировки — иначе команда уезжает в чужую зону выхода.

**Зоны выхода: 1–4 — верхняя сетка, 5–6 — нижняя, два последних вылетают.** Правила и цвета — в
`src/lib/qualification.ts`, **без обращений к БД**: их использует и клиентская сетка групп. Та же развилка, что
у `openai-images.ts` (сервер) и `image-options.ts` (данные) — `group-stage.ts` тянет Prisma и на клиент не идёт.

**Решение: плей-офф ждёт конца группы, признак автоматический (23.08.2026).** Раньше сетка брала посев
из текущих позиций таблицы, и участники плей-офф менялись после каждой сыгранной встречи. Теперь
`getQualified()` отдаёт зоны только когда стадия завершена, а до этого сетка стоит с заглушками
(«A1», «Победитель ЧФ-1»). Завершённость **не переключается руками** — `groupStageDone()`
(`group-stage.ts`) проверяет, что у всех ожидаемых по жеребьёвке встреч есть результат: ожидаемое —
круговая n·(n−1)/2 по числу команд в группе, «есть результат» — неравный счёт (так же, как решённость
серии в плей-офф, включая техпоражения). Обратная сторона правила: незаведённая встреча для нас не
существует, поэтому обе страницы показывают «сыграно X из Y встреч» — на групповой стадии подписью
у заголовка, в плей-офф плашкой, объясняющей пустую сетку.

**Тег команды заполнен всегда:** `teamTag()` в `profiles.ts` возвращает свой тег из ростера, а если его нет —
выводит из названия (первое слово, до 5 знаков, в верхнем регистре). Заведут тег в ростере — он перекроет.

**Очки за серию Bo3: 2:0 — 3, 2:1 — 2, 1:2 — 1, 0:2 — 0.** Формула в таблице сезона не записана; выведена из
кросс-таблицы и сошлась на всех командах группы A первого дивизиона. Живёт в `seriesPoints()` (`group-stage.ts`).

**Кросс-таблица в источнике не подписана** — в шапке логотипы-картинки, ячейки заголовков пустые. Порядок команд
в матрице восстанавливается расчётом: по каждой строке считаются В-П-очки и сопоставляются с таблицей выше.
Где отпечаток уникален — подпись точная; где нет (в каждой группе нашлась пара команд с одинаковыми В-П-очки) —
встречи помечаются `guessed` и подсвечиваются в UI, чтобы их поправили руками. Правка через
`PATCH /api/series/[id]` снимает пометку: ручной ввод считается подтверждением.

## Архив серий и статистика турнира (29.07.2026)

Вопрос был «где собирать общую стату — кто больше всех убил, нанёс урона — в разрезах турнира». Ответ:
**в тех же строках, из которых уже считается таблица.**

**Решение: `GroupSeries` расширена до `Series`, а не заведена вторая модель.** Групповая встреча и встреча
плей-офф отличаются только полем `stage`: и там, и там пара команд, счёт Bo3 и очки по одной формуле. Вторая
модель означала бы два источника правды для одного и того же вопроса «кто с кем и с каким счётом сыграл» —
и таблица с архивом разъехались бы на первой же правке. Миграция — переименование таблицы, а не drop+create:
в `GroupSeries` лежала вручную выверенная сетка группы.

**Карта серии — это `Match`.** У серии до трёх карт (`seriesId` + `gameNumber`, уникальны в паре).
`openDotaMatchId` глобально уникален, поэтому одна карта физически не может лежать в двух сериях.
Длительность карты (`durationSec`) хранится у матча — без неё «урон в минуту» превращается в рейтинг
длинных игр.

**Стороны определяются по составам, а не вводятся руками.** `detectSides()` считает, чьих игроков больше
в пятёрке (минимум двое — иначе один случайно совпавший `account_id` перевернул бы серию). Та же логика,
что распознаёт названия команд на странице постгейма.

**Игрока опознаём по `account_id`, откуда бы он ни взялся.** Анкеты приходят из CRM неровно: у части
людей заполнено само поле, у части — только ссылка на Dotabuff/Stratz/Steam. `playerAccountId()`
(`src/lib/profiles.ts`) сводит это к одному значению, и им пользуются и синк, и распознавание команд.
Матчить по голой колонке `accountId` значило бы терять статистику половины ростера на ровном месте.
Именной адрес `steamcommunity.com/id/<vanity>` в число не превращается ничем, кроме Steam Web API —
для него есть `scripts/resolve-vanity.ts` (разовый прогон, результат пишется в БД навсегда).

**Ники везде — из ростера, а не из клиента Доты.** В игре человек может называться как угодно и менять
имя между матчами; в лиге у него одно имя. Постгейм подменяет ник на ростерный, когда игрок узнан по
`account_id` (неузнанный — стендин, чужой матч — остаётся под своим именем из OpenDota), а страница
встречи и рейтинги и так читают ник из `Player`. Для этого `/api/roster/teams` отдаёт состав как
`lineup: {accountId, nickname}[]`, а не голый список id.

**Рейтинги считаются, а не хранятся** (`src/lib/leaders.ts`). Любой хранимый итог пришлось бы пересчитывать
после каждой привязки карты и каждого допарса реплея — и он бы молча разъезжался. Строк тут сотни: суммировать
в памяти дешевле, чем поддерживать кэш. Разрез задаётся фильтром `Series` (дивизион / стадия / группа), а
карта **без серии в рейтинги не попадает вообще** — иначе в «плей-офф» протекли бы товарищеские матчи.

**Команды считаются по множеству карт, а не сложением строк.** Пять игроков дают пять строк на карту; сложи
их «сыграно» — и средние за карту окажутся впятеро занижены.

**Разрез — это `stage` + одно из двух полей.** Группа живёт в `Series.group`, половина сетки — в
`Series.bracket` (`upper`/`lower`/`grand`). Сетку держим отдельной колонкой, а не выводим из названия
раунда: по ней фильтруют архив и статистику, и разбирать ради этого свободный текст — способ однажды
потерять серию из-за опечатки. Значение проставляется само по выбранному раунду (`bracketOfRound()`),
поэтому в форме его не спрашивают. Список разрезов для интерфейса — `CUTS` в `src/lib/stages.ts`,
один на обе страницы.

**Решение: у встречи стабильный ключ в адресе (29.07.2026).** `id` автоинкрементный, а `db:import`
пересоздаёт производные строки — после каждого переноса данных встреча получала новый id, и ссылка
`/series/12`, отданная наружу, вела в никуда. Поэтому у `Series` есть `slug` вида
`guzliki-vs-from-paris` (по слагам команд — сквозному ключу проекта; повторная встреча той же пары
получает числовой хвост). Слаг считается один раз при создании, едет в снимке и переживает импорт.
Числовой id роут тоже принимает — ради ссылок, отданных до его появления.

**Страница встречи `/series/<slug>` повторяет форму разбора серии на Dotabuff:** шапка со счётом, ниже
карты, у каждой — оба состава с героем, уровнем и K/D/A. Детали карты (драфт, предметы, график золота)
не дублируются — за ними ведёт ссылка на `/match/<id>`, где всё это уже нарисовано. Счёт карты по
убийствам и первый пик хранятся у `Match`, а не считаются из `MatchStat`: там только игроки лиги, и
карта со стендином показала бы заниженные убийства.

Где что: `/admin/series` — завести встречу, подвесить/отцепить/перечитать карты и удалить встречу
(единственный вход в архив), `/standings/<div>/stats` — рейтинги; фильтры живут в query, поэтому любой
разрез можно кинуть ссылкой. `POST /api/series/[id]/games` читает стату сразу при привязке: отдельной
кнопки «синхронизировать» нет намеренно — карта без статы в архиве бесполезна. Отдельная кнопка
«перечитать» у карты всё же есть, но для другого случая: непарсенный матч через время обрастает
вардами и таймингами, а привязка была раньше.

## Инструмент: импорт матча (каркас)

Отчёт: `/match` (ввод id) → `/match/[id]` (клиент) → `GET /api/opendota/match/[id]` → `fetchMatchReport`
(`src/lib/opendota.ts`). БД не трогает — всё из источника. Сервис публичный и принимает **любой** матч
Dota 2, не только матчи лиги (решено с заказчиком).

Данные (реальные из OpenDota): шапка (время, счёт, победа), **пики/баны с очередью**, **график преимущества по золоту** (по минутам), aegis на команду. По игроку: герой, уровень, K/D/A, LH/денаи, GPM/XPM, ценность (net worth), урон по героям/строениям, хилл, **предметы** (+нейтралка, бэкпек), **порядок способностей**, **тайминги покупок**, постоянные баффы (стаки).

Имена команд подставляются из OpenDota, но поле **редактируемое** (кастомим под LOST).
Резолв id→имя через кэш констант OpenDota (`item_ids`/`items`, `ability_ids`/`abilities`, `permanent_buffs`). Детальные поля есть только у **распарсенных** матчей (`version != null`) — иначе часть пуста (есть предупреждение в UI).

## Турниры как сущность (22.08.2026)

Дивизионы были константой в коде: «завести сезон» означало правку исходников. Теперь сезон или кубок —
строка `Tournament`, дивизион (`Division`) принадлежит турниру, а участие команды — отдельная строка
`TournamentEntry` (там же группа и посев). Разделение принципиальное: **команда переживает турнир**,
её участие — нет, поэтому «дивизион команды» не поле у команды, а связь. Состав тоже сезонный —
`RosterSpot.divisionId`, иначе заявка нового сезона затирала бы прошлый.

**Зеркала строкой — сознательное отступление.** `Team.group`, `Series.division` и `GroupEntry.division`
продолжают хранить имя дивизиона текстом: по ним фильтруют полтора десятка выборок (standings,
leaders, архив серий, витрины ростера), и переписать их разом ради чистого FK — способ уронить
работающий сезон. Источник правды — `divisionId`; единственный, кто пишет зеркала, — `src/lib/tournaments.ts`.
Новый код разрезает данные по `divisionId`, а не по строке.

**Дубли профилей разбирает оператор, а не автоматика** (`/admin/duplicates`, `src/lib/duplicates.ts`).
Один человек попадает в ростер дважды, когда меняет ник между сезонами: апрув заявки узнаёт его по
`account_id`, но в таблице сезона номера часто нет, а слаг нового ника другой — и места в составах,
статистика карт и баллы расходятся по двум записям. Очередь показывает пары с признаком, почему они
похожи (общий `account_id`, телеграм, имя, почти одинаковый ник) и чем каждая запись наполнена — по
этому видно, какую оставлять. Решений три: **объединить** (всё переезжает к победителю, донор
удаляется), **переименовать** (это не дубль, а смена ника: данные и стата остаются на месте) и
**«разные люди»** — пара уходит в `PlayerDistinct` и больше не всплывает, иначе очередь вечно
показывала бы тёзок.

Автоматически не сливаем, потому что операция необратима, а общее имя — это ещё и два тёзки.
Слияние переносит места в составах, строки статистики карт, начисления реестра (`PointsEntry` —
руками: там не связь, а пара «тип + id») и заявку на привязку аккаунта; пустые поля победителя
дополняются данными донора, `Player.tp` пересчитывается из реестра. Совпавшие строки схлопываются —
одно место в той же команде сезона, одна строка статистики той же карты — иначе упрёмся в
`@@unique`; сколько схлопнется, показано до нажатия. Права: правка — `roster.edit`, слияние требует
ещё `roster.delete`, потому что запись исчезает.

**Составы попадают в лигу двумя путями, писатель один.** Импорт таблицы оператором (`roster-import.ts`)
пишет в ростер сразу — подтверждать себе нечего. Заявка капитана с сайта ложится в очередь
`TeamApplication` (payload — состав целиком JSON, `Team` до апрува не создаётся, как в плане аккаунтов)
и попадает в ростер только при одобрении. **Одна команда — одна строка в очереди**: повторная
отправка правит прежнюю заявку, включая уже принятую (состав меняют и после апрува — замена, ушедший
игрок), и такая правка возвращает ту же строку в `pending`, а не заводит вторую заявку той же
команды. Обе ветки зовут `writeTeamToRoster` и общий набор проверок
`applicationProblems` (дубли, конфликт составов, занятый слаг). Разбор входов — один парсер на все
формы (колоночная раскладка, блочная сезонная таблица, построчный текст), а сеть — Steam и
OpenDota — вынесена отдельным шагом (`enrich.ts`): запрос посреди сохранения дюжины команд
превращается в таймаут. Из OpenDota сохраняем только ранг (`Player.rank`); ник в лиге человек
выбирает сам, а `Player.photo` у нас всегда локальный файл — и то, и другое оператору показываем
справкой.

**Ранг сверяется отдельно от импорта** (`rank-refresh.ts`, экран `/admin/roster/ranks`). Импорт тянет
ранг один раз — в момент разбора таблицы сезона, и через месяц эта цифра врёт у половины ростера;
гонять ради неё импорт заново нельзя, он пишет составы. Кнопка сверяет ранг по всей лиге и хранит
**один шаг назад**: `Player.rankPrev` (значение до последней СМЕНЫ) и `Player.rankAt` (когда
подтверждали, даже если ранг не изменился). Истории рангов нет намеренно — вопрос всегда один,
«куда человек уехал с прошлой сверки», и на него отвечает одно прошлое значение, а не график.
Прогон идёт **горстями по десять** (серверный экшен на горсть, цикл — на клиенте): бесплатный
OpenDota держит 60 запросов в минуту, полный круг по ростеру — минуты, и один экшен такой длины
упёрся бы в таймаут, не оставив ни данных, ни объяснения. Каждая горсть записана до того, как
запрошена следующая, поэтому оборванный прогон обновил тех, до кого дошёл. Молчание OpenDota
(закрытый профиль, сеть) **не затирает** известный ранг, а ранг «тот же» не двигает `rankPrev` —
иначе первый холостой прогон стёр бы дельту, ради которой всё и делалось. Ключа этот путь не
требует: `/api/players/<account_id>` открыт, `STEAM_API_KEY` нужен только именным ссылкам Steam.

**Состав капитан собирает мышью, а не набирает текстом** (`src/app/(public)/tournaments/[slug]/apply/`).
Слева — пул игроков лиги, справа — пять слотов позиций плюс две замены и тренер; игрок переносится
перетаскиванием (`@dnd-kit`, та же техника, что у доски драфта UNDERBEER) или ставится кликом в
первый свободный слот. Капитан отмечается кружком у слота и хранится **игроком**, а не слотом, —
при перестановке капитанство едет с человеком.

**В пуле только те, кого лига знает**: игроки с `account_id` (в поле или выведенным из ссылки на
профиль) — без него человека не опознать в архиве матчей. Свободного поля ника нет вовсе, и это
главное правило экрана: раньше в состав можно было вписать кого угодно, и лига узнавала о человеке
на апруве. Незнакомого зовут ссылкой `t.me/<бот>?start=invite` — он проходит регистрацию в боте и
появляется в пуле. Имя бота для ссылки спрашивается у самого Telegram (`getMe`), а не заводится
переменной окружения: та молча разъедется с токеном.

Занятым показывается тот, кто уже действующий (поз. 1–5) в другой команде **этого дивизиона** —
правило и проверка общие с записью (`roster-spots.ts`, `applicationProblems`); своя же команда по
слагу названия из занятых исключается, иначе повторная заявка тем же составом блокировала бы сама
себя. Занятость считается по командам, **заявленным в турнир** (`TournamentEntry`), а не по всем
строкам состава в его дивизионе: состав сезонный, и строки команды остаются в дивизионе после того,
как её из турнира убрали, — без этой сверки прошлогодний состав чужой команды помечал бы пол-лиги
занятой в турнире, где она не играет. На сервер уходят не строки ввода, а id игроков и роль слота
(`RosterInput`): ники, ссылки и MMR берутся из базы, и заявка с чужим id просто не собирается. Дальше — общая очередь:
`submitTeamApplication`, `source = "web"`, апрув пишет ростер тем же `writeTeamToRoster`.

**Бот состав не собирает** — на «Подать заявку» внутри турнира он отдаёт ссылку на этот экран
(вход на сайт у игрока телеграмный, кодом из бота). Квиз состава удалён на Э6 нодового флоу вместе
с флагом `QUIZ_ROSTER`: пятёрку в чате не выбрать из пула, а вписать кого угодно мимо лиги новое
правило запрещает. Непонятый текст боту заявку тоже не начинает — на него он показывает меню.

**Что бот говорит, правит оператор, а не разработчик** — но одним местом: `/admin/bot/flow`, право
`tournaments.edit`. Формулировка шага — свойство ноды графа (ниже, «Нодовый флоу бота»). Отдельного
реестра текстов (`BotQuestion`, вкладка «Вопросы») больше нет: он был вторым местом для одного и
того же, и после переезда диалога в граф искать формулировку приходилось бы в двух окнах.

**Тайминги и тексты уведомлений о встречах — на `/admin/bot`** (`src/lib/bot-settings.ts`, то же
право `tournaments.edit`). Они остались отдельным реестром намеренно: у настройки нет входящего
сообщения и потому нет ноды — это исходящий поток, а не разговор. Уклад тот же, что у графа: реестр
настроек с дефолтами живёт в коде, в таблицу `BotSetting` (`key`/`value`, строкой) попадают только
отличия оператора, читается на каждую рассылку. Настройка — строка, а не колонка на каждую:
реестр здесь и рисует экран, и проверяет ввод, поэтому новая настройка стоит записи в массиве, а не
миграции. Первая очередь ключей: `remind_before` (интервалы напоминаний, `24h,1h`), `remind_targets`
(`all` | `captains`), `no_time_digest_at` (когда слать дайджест встреч без времени), `slots`
(времена начала, которые бот предлагает кнопками) и четыре текста — напоминание, перенос,
назначение встречи, предложение соперника, с подстановками `{команда}` / `{соперник}` / `{время}` /
`{турнир}` (движок подстановки — `fill` в том же файле). Ввод нормализуется на записи
(`normalizeSetting`): «25:00» и «завтра» возвращаются оператору ошибкой, а не ломают рассылку молча;
совпало с дефолтом — строка удаляется. Потребители таймингов — напоминания (ниже) и Э8 плана
`BOT-PLAN.md`.

**Напоминания о встречах** (`src/lib/tg-schedule.ts`, тик — в `scripts/bot.ts`). Тикает тот же
процесс, что крутит бота: раз в минуту зовётся `tickSchedule()`. Отдельного планировщика нет —
пока бот живёт одним процессом, второй демон был бы второй вещью, которую надо не забыть поднять;
после переезда на VPS тик уедет в тот же сервис, что и вебхук (`DEPLOY.md`).

Три исходящих потока. **Напоминание** уходит игрокам обеих команд (или только капитанам —
`remind_targets`) за каждый интервал из `remind_before`. Интервал выбирается полосой, а не
«моментом»: до встречи 30 минут — это полоса «за час», а не «за сутки». Так лечится простой бота —
пока он лежал, окно «за сутки» прошло, и при запуске уходит только актуальное напоминание, а не
оба разом. **Перенос** рассылается не по факту записи, а по решению организатора: и правка времени
в `/admin/series`, и (Э8) апрув запроса встречи ведут в одну функцию `announceReschedule(seriesId,
before)`; пустое `before` значит «назначили впервые», и текст берётся другой. **Дайджест** встреч
без назначенного времени уходит раз в сутки (`no_time_digest_at`) в служебный чат `TG_CHAT_ID` —
это работа организатора, а не игроков.

Адрес человека — привязка `UserAccount.tgId` (точная) либо, запасным ходом, хендл в `TgChat`;
кого бот не знает, того молча пропускаем, как в `tg-notify.ts`. Состав берётся из **дивизиона
встречи**: состав команды меняется от сезона к сезону, и без дивизиона в рассылку попал бы
прошлогодний.

**Повтор страшнее пропуска.** Бота перезапускают с ноутбука по нескольку раз в день, и без следа
отправки каждый запуск слал бы то же самое заново. След — `SeriesNotice` (`seriesId` + `kind` +
`mark`, уникальной тройкой): отметка ставится **до** рассылки и сама является захватом — упавшая
на середине рассылка не должна начинаться с начала на следующем тике. Исключение одно —
дайджест: это одно сообщение в один чат, не ушло значит не ушло никому, поэтому его отметки
снимаются обратно и следующий тик пробует снова. Перенос сносит `remind`-отметки встречи:
напоминания считаются от её времени, и без сброса «за сутки» после переноса уже не ушло бы.

**Заказ встречи капитаном** (`src/lib/match-request.ts` — очередь, `src/lib/tg-meetings.ts` —
диалог и тексты, шаги `mr_*`). Капитан выбирает встречу → день (кнопки «сегодня / завтра / …» либо
`ДД.ММ`) → время (кнопки из `slots`) → подтверждает; предложение уходит капитану соперника с
кнопками «Принять время» / «Предложить другое».

**Соперника выбирает расписание, а не человек.** Список — несыгранные серии его же команд
(`openSeriesFor`), включая уже назначенные: заказ времени у встречи со временем это перенос, и
запрещать его значило бы гнать капитанов обратно в личку организатора. Свободного выбора команды
нет — ошибиться в сопернике не должно быть возможности.

**Право заказывать даёт `RosterSpot.isCaptain` плюс привязка `UserAccount.tgId`** — это действие,
которое пишет, а хендл не удостоверение (то же правило, что у правки профиля). Кнопка «Заказать
встречу» и появляется только на экране того турнира, где человек капитан.

**Цепочка апрувов** (`MatchRequest.status`): `pending_opponent` → соперник принял → `pending_admin`
→ организатор подтвердил → `approved`. «Предложить другое» не правит чужую строку, а заводит свою
со ссылкой `parentId`, и исходная становится `declined` — в истории видно, кто с чего начал.
Живое предложение на встречу всегда одно: новое закрывает остальные (`supersede`), иначе
подтверждённым оказалось бы то, которое организатор случайно открыл первым. Сторона предложения
не хранится полем, а выводится из места капитана в дивизионе встречи: отдельное поле разъехалось
бы с ростером при пересборке состава.

**Время пишет только апрув организатора.** До него это переписка, а не расписание — то же правило,
что у заявки команды и правки профиля. Апрув ставит `Series.startAt` и зовёт `announceReschedule`
(см. выше): вход у уведомления «встреча назначена / перенесена» один, откуда бы время ни пришло —
из админки руками или из бота. Очередь `pending_admin` висит блоком наверху `/admin/series/<турнир>`
под правом `series.edit`: «подтвердить» одной кнопкой, «отклонить» — только с причиной, и она
уходит обоим капитанам. Предложение, чьё время уже прошло, тик расписания переводит в `expired`
молча: отвечать на «сыграем вчера в 20:00» некому.

**Меню бота и раздел «Турниры»** (`src/lib/tg-menu.ts` + `src/lib/tg-tournaments.ts`). Первый
уровень — «Личный профиль» и «Турниры», плюс «Анкеты» (когда открытая анкета есть) и
«Регистрация» (когда лига человека не знает). Всё остальное живёт уровнем ниже, у того, к чему
относится: вход на сайт и правка данных — в профиле, состав и команды — внутри турнира. Причина не
только в размере экрана: **состав принадлежит дивизиону турнира** (`RosterSpot.divisionId`), и одна
кнопка «Мой состав» на все сезоны сливала D1, D2 и прошлый сезон в один список — внутри турнира
вопрос однозначен.

Навигация — три уровня (турнир → раздел → команда), шаги `tt_*` в общей `BotSession`. Показываются
турниры со статусом `registration`, `running` и три последних `finished`; черновики не показываются
никогда — их оператор ещё заводит. Команды выводятся кнопками, а карточка приезжает отдельным
сообщением: в сообщение Telegram влезает 4096 знаков, а команд в дивизионе бывает два десятка.
Имена команд не уникальны (одноимённые команды есть в разных дивизионах) — по кнопке показываются
все совпавшие карточки, а не угаданная первой.

Навигация **не считается начатым диалогом**: кнопка меню посреди диалога (анкета, регистрация,
правка профиля) по-прежнему даёт справку и повтор вопроса — терять набранное нельзя, — а из раздела
«Турниры» кнопка меню просто выводит: там нечего терять, кроме места в списке. Отдельно ловятся
кнопки прошлой версии меню: клавиатура у Telegram висит до отмены, и «Мой состав» с «Подать заявку»
человек нажмёт ещё не раз — по ним он попадает туда, где эти разделы теперь живут, а не в диалог,
которого не просил.

**Регистрация игрока через бота** (`src/lib/tg-register.ts`, шаги `reg_*`). Второй вход в ту же
воронку, что и анкета в кабинете: те же поля, та же проверка (`normalizeApplication`), тот же JSON в
`UserAccount.application`, та же очередь `/admin/moderation` и тот же `approveRegistration`. Отличий
ровно два. Почты у пришедшего из бота нет — `UserAccount.email` стал необязательным, а вторым ключом
аккаунта служит `tgId` (это `from.id` апдейта, а не `chat.id`: в личке они совпадают, но ключ
принадлежит человеку). Телеграм не спрашивается вовсе — он приезжает в апдейте; без хендла
регистрация не начинается: это единственный контакт человека для организатора.

Смысл всей затеи — **привязка вместо узнавания по хендлу**. До неё бот опознавал человека по
`@username`, а хендл меняют, и освободившийся занимает посторонний, — поэтому боту нельзя было
доверить ничего, что пишет. `UserAccount.tgId ↔ playerId` переживает смену хендла и становится
первым источником в `identify` (`tg-menu.ts`); хендл и account_id из заявок остались запасными
ветками для тех, кто в лиге давно. Чат при отправке анкеты закрепляется за аккаунтом
(`TgChat.accountId`) — по нему уходит решение организатора (`tg-notify.ts`), и он же будет адресом
напоминаний о встречах.

Пишет анкету в базу сам `tg-register.ts`, а не `account.ts`: тот помечен `server-only` и в процесс
бота (обычный node, `scripts/bot.ts`) не грузится. Ровно та же причина, по которой заявку команды из
бота принимает `team-application.ts`. Второй реализации «пустить в лигу» при этом не появилось —
апрув один на оба входа.

**Вход на сайт по коду из бота** (`src/lib/tg-login.ts`, страница `/login/tg`). У зарегистрированного
через бота нет ни почты, ни пароля — войти в кабинет ему нечем, а сборка состава и профиль живут на
сайте. Кнопка «Войти на сайт» выдаёт шесть цифр, страница их принимает и ставит **ту же подписанную
куку**, что вход по паролю: код проверяет `redeemLoginCode`, сессию выдаёт `establishSession`
(`account.ts`) — второй реализации входа не появилось. Код живёт 10 минут, гасится при первом
использовании (условием `usedAt: null` в `updateMany` — два одновременных ввода не должны оба стать
входом), и живой держится **один на аккаунт**: подбор шестизначного числа упирается в одну цель со
сроком, а не в «любой из накопленных». Выдаётся код строго по привязке `UserAccount.tgId` — тому,
кого бот узнал только по хендлу, его не дают: хендл не удостоверение, а код это ключ от кабинета.

Почему код, а не Telegram Login Widget: виджету нужен домен, привязанный к боту в BotFather, а до
выката наружу у нас туннель и невыбранный VPS — вход не должен ждать переезда. После выката виджет
добавится второй кнопкой на `/me`, не вместо кода (`DEPLOY.md`). Адрес, который бот подставляет в
ссылку, — `siteUrl()` (`src/lib/site.ts`): сперва `BASE_URL`, потом адрес поднятого quick tunnel из
`web/.cache/tunnel.url` (его пишет скилл `serve`), и только потом `http://localhost:3000`. Порядок
именно такой, потому что телеграм **не делает ссылкой localhost** — показывает её текстом, и человек
решает, что бот сломался; а постоянного адреса у проекта пока нет, туннель выдаёт новый при каждом
запуске, и держать его в `.env` значит править файл и перезапускать бота каждый раз. Когда адрес
всё-таки локальный, бот не притворяется ссылкой, а говорит, что сайт не опубликован
(`siteIsLocal()`). Ссылка из бота **без кода в адресе**:
предпросмотр ссылки или чужой глаз в истории браузера сожгли бы его молча.

**Привязка телеграма с сайта** (`src/lib/tg-link.ts`, Э19) — та же связка `UserAccount.tgId`, но
заводится с другой стороны: не бот регистрирует человека, а вошедший на сайте зовёт бота подтвердить
его контакт. «Настройки → Телеграм» (и шаг 1 анкеты) выдают ссылку `t.me/<бот>?start=link_<token>`;
человек жмёт Start, и `redeemLinkToken` пишет аккаунту `tgId` с хендлом, а чату — `accountId`, то
есть ровно то, что при регистрации в боте делает `tg-register.ts`. Токен одноразовый, живёт 30
минут, живой держится один на аккаунт и гасится условием `usedAt: null` — теми же приёмами, что код
входа: это ключ от аккаунта, только в обратную сторону.

Start с токеном разбирает `tg-bot.ts` **до графа диалога**, в отличие от `/start invite`, который
объявлен точкой входа своего флоу: хвост здесь не постоянное слово, а случайный токен — совпадением
подписи (`entry.payloads`) его не поймать, да и править оператору в этом обмене нечего. После ответа
человек передаётся в главный флоу обычным `/start`, чтобы привязка не кончалась пустым чатом. Занятый
чужим аккаунтом `tgId` не перевешивается (у того аккаунта привязка может быть единственным входом),
а своя прежняя заменяется молча — токен выдан хозяину аккаунта. Отвязка (`unlinkTelegram`) сперва
проверяет, останется ли чем войти.

Страница, с которой ушли в бота, узнаёт об успехе опросом `/api/tg/link/status` (раз в три секунды,
не дольше трёх минут) и обновляется сама: привязка случается в другом процессе, и пуша с сервера у
нас нет. Из этого же следует, что кружок телеграма на входе перестал быть заглушкой — аккаунты с
`tgId` теперь заводит не только бот, и `/login/tg` стал рабочей дверью.

**Личный профиль в боте и правка через модерацию** (`src/lib/tg-profile.ts` + `profile-edit.ts`,
шаги `pe_*`). «Личный профиль» показывает всё, что лига о человеке знает: анкету (имя, город, дата
рождения, MMR), TP за всё время (кеш реестра, `Player.tp`), команду в разрезе турнира с позицией и
капитанством (последний `RosterSpot`), ссылки на Dotabuff/Stratz/Steam и телеграм.

**Кого именно показать** решает `identify` (`tg-menu.ts`), и здесь легко показать чужого. Из заявки
берётся не весь состав, а **своя строка** — та, где стоит хендл написавшего, а если заявка пришла из
этого же чата, то строка капитана: иначе «вами» оказывались все пятеро и бот отдавал профиль
сокомандника. Из дублей (один человек заведён в ростере дважды) показывается тот, у кого **свежее
место в составе**, а не тот, у кого их больше: мест читается ровно одно, самое свежее. Привязка
`UserAccount.tgId` перекрывает обе эвристики — это тот самый человек.

Кнопка «Изменить данные» появляется **только у привязанного профиля** (`UserAccount.tgId`) — то же
правило, что у кода входа: узнанному по хендлу бот показывает, но писать в чужой профиль не даёт.
Диалог из двух шагов (какое поле → новое значение), и правка уезжает **в очередь `ProfileEditRequest`**,
а не в `Player`: бот сам ничего не публикует. Одна строка — одно поле (`nickname`, `city`, `mmr`,
три ссылки, `photo`): человек чаще правит что-то одно, а оператору так видно «было → стало» без
диффа всей анкеты. Открытая правка на поле только одна — иначе оператор одобрил бы устаревшее
значение вслед за свежим. Смена ника соблюдает общий кулдаун (скользящее окно 120 дней,
`Player.nicknameChangedAt`): правило теперь живёт в `profile-edit.ts` и переиспользуется кабинетом
на сайте (`updateOwnProfile`) — двух правил «раз в сезон» быть не должно. Проверяется он **до**
вопроса о новом нике: заставить придумать ник и потом сказать «нельзя ещё 40 дней» — худший порядок.

Фото приезжает картинкой (транспорт пропускает `message.photo`, скачивание — `fetchFile` в
`telegram.ts`) и **кладётся в `public/uploads/players` сразу, до решения** — иначе оператору нечего
смотреть, а именно смотреть здесь и надо; так же работает загрузка из админки. Цена — файл
отклонённой правки остаётся на диске. Экран очереди — вкладка «Правки профиля» в `/admin/moderation`
под своим правом `roster.edit` (это правка ростера, а не решение «пускать в лигу»): без права
вкладки нет вовсе. Апрув пишет в `Player` и уведомляет в бот, отказ — с причиной (`tg-notify.ts`,
чат берётся из самой правки).

**Анкеты под ивенты** (`/admin/quizzes`, `src/lib/quizzes.ts` + `tg-forms.ts`) — то, что оператор
заводит сам: запись на шоуматч, опрос, заявка кастера. Отдельно от заявки команды сознательно:
заявка завязана на модель ростера (команда, пять позиций, ссылки, очередь модерации, запись в ростер
при апруве), а анкета не пишет никуда, кроме своих ответов, и вопросы у неё любые. Общий у них
только движок «вопрос → ответ → сводка»; свести их в одну сущность значит на каждой правке
разбираться, к какому из двух случаев относится проверка. Вопрос анкеты (`QuizQuestion`) поэтому
живёт только в базе — дефолт ему брать неоткуда, в отличие от графа диалога, у которого сид в коде.

Статусы анкеты — `draft` / `open` / `closed` плюс срок `closeAt`, закрывающий приём сам (как
`regCloseAt` у турнира). Кнопка «Анкеты» появляется в меню бота, только когда открытая анкета есть:
раздел, который на всё отвечает «сейчас ничего нет», хуже отсутствующего. Шаги анкеты живут в той же
`BotSession`, что и шаги заявки (диалог у человека один), и разведены префиксом `form_*`. Один чат —
одна запись на анкету: повторное прохождение правит прежнюю. Ответы хранятся вместе с текстом
вопроса — вопрос перепишут, а ответ прошлого месяца должен остаться читаемым; в таблице админки они
поэтому сопоставляются по тексту, а не по порядку, а ответы на удалённые вопросы показываются
отдельно, чтобы не пропасть молча. Выгрузка — `GET /api/quizzes/<slug>/export` (CSV с BOM, иначе
Excel ломает кириллицу); роут закрыт правом `quizzes` и добавлен в `needsAdmin` — это люди, их
контакты и то, что они написали организатору.

**Меню бота вне квиза** (`src/lib/tg-menu.ts`): «Мой состав», «Личный профиль», «Турниры». Человека
узнаём по привязке `UserAccount.tgId`, а без неё — по телеграм-хендлу отправителя — он приезжает в каждом апдейте, а в ростере хендл уже хранится
(`Player.telegram`), и просить представиться значит спрашивать известное. **Хендл при этом не
удостоверение**: его меняют, а освободившийся может занять посторонний. Поэтому меню показывает
только то, что и так публично на сайте, и ничего не меняет — всё, что пишет, идёт через квиз и
очередь модерации. «Мой состав» показывает **и поданные заявки со статусом, и составы, уже заведённые в лигу** — состав,
собранный минуту назад, в ростере появится только после одобрения, а прошлые сезоны никуда не делись.
Составы всегда в разрезе турнира: команда переживает сезон, участие — нет, и «мой состав» без турнира
это два разных состава, слитых в один список.

**Чат подавшего запоминается вместе с заявкой** (`TeamApplication.submittedChatId`), а все, кто писал
боту, — в `TgChat`. Причина простая: Telegram не даёт написать человеку по хендлу, только по `chat_id`,
и он появляется, лишь когда человек сам написал. Без этого нельзя ни показать капитану статус его
заявки (телеграм в составе он мог не указать — так и было на первом живом прогоне), ни уведомить о
решении организатора. По этой же ниточке идёт **опознание вторым способом**: к найденным по хендлу
добавляются игроки с `account_id` из заявок этого чата. Номер аккаунта Dota надёжнее хендла: хендл меняют.

**Опознание возвращает список, а не одного игрока.** В ростере встречаются дубли — один человек
заведён дважды (импортом и заявкой) с разными `account_id`, и мест в составе может не быть у той
записи, что попалась первой; бот тогда отвечал «вас нет в лиге» тому, кто в команде играет. Поэтому
«Мой состав» собирает составы всех совпавших записей, «Личный профиль» показывает ту, что реально
играет (профиль без единого места — почти всегда осколок импорта), и предупреждает о дубле:
склеивает записи оператор, но человек должен понимать, почему видит чужой MMR. «В лиге, но нигде не
заявлен» — отдельный ответ, не путать с «не нашли».

**Решение организатора уходит в телеграм** (`tg-notify.ts`): одобрили или вернули с причиной — бот
пишет подавшему и тем игрокам состава, чьи чаты знает. Отправка идёт после записи и вне транзакции:
упавший телеграм — повод написать в консоль, а не откатить заведение команды. Нажатие кнопки меню посреди квиза **не сбрасывает диалог**: бот отвечает и
повторяет вопрос, на котором стоял (`askCurrent`) — капитан на седьмом игроке не должен терять
состав из-за случайного нажатия.

**Удаление турнира** (`deleteTournament`) сносит сезон целиком: карты серий, серии, строки групп,
места составов дивизионов, начисления TP и сам турнир (дивизионы, участие, заявки — каскадом).
Зеркала и кеш `Player.tp` чинятся следом, потому что FK-каскад их не знает. Команды и игроки
остаются в ростере — уходит только участие. Задумано для тестовых прогонов, право `tournaments.edit`.

Права: всё, что пишет турниры, закрыто `tournaments.edit` — и на странице, и в server-action
(до экшена можно дойти мимо страницы, ACCOUNTS-PLAN.md §2.2).

### Нодовый флоу бота (`src/lib/bot-flow/`, Э1–Э7, 03.09.2026)

Структура диалога переехала из кода в данные: экран, кнопки на нём, куда ведёт каждая кнопка и
какие переменные копятся по пути — это граф, а не развилка в `handleMessage`. Раньше снаружи
настраивались только тексты (`BotQuestion`) и тайминги (`BotSetting`); сама последовательность
менялась правкой TS и перезапуском бота. **С Э6 граф — единственный путь бота**: рукописного
автомата за ним нет, точка входа (`src/lib/tg-bot.ts`) только запоминает чат и отдаёт сообщение
интерпретатору. План задачи — `BOT-FLOW-PLAN.md`.

**Граф ведёт навигацию, а не бизнес-логику.** Ноды решают, что бот скажет, какие кнопки покажет,
куда ветвится и что запомнит; тяжёлое (регистрация, заказ встречи, выдача кода входа) остаётся в TS
и подключается нодами `action` (реестр в `actions.ts`) и `subflow` (обёртка над рукописным модулем).
Полноценный визуальный язык программирования не строим — это месяцы работы и риск сломать то, что
уже принимает заявки.

**Хранение — JSON-документ с версиями** (`BotFlow`), а не таблицы нод и рёбер: канвас правится
целиком, и каждое перетаскивание ноды превращалось бы в пачку апдейтов, а откат собирался бы по
кускам. Дефолтный граф живёт **сидом в коде** (`default-flow.ts`) — тем же порядком, что вопросы и
настройки: пустая база означает бота с обычным флоу, а не бота без флоу. Версии не удаляются:
сессия помнит, на какой начала (`BotSession.flowVersion` — это `BotFlow.id`), и доигрывает на ней,
**пока разговор держит модуль** — анкета, регистрация, заказ встречи: у них наполовину введённые
данные лежат в состоянии модуля, и подмена графа под ними и есть «выбросить из середины». Стоянка на
обычной ноде графа закрепления не даёт: меню — тоже ждущая нода, и закрепляй его, публикация до
человека просто не доезжала бы (правка 03.09, `DECISIONS.md`).

**Ключ перехода — текст кнопки.** Клавиатура у бота reply, а не inline: ответ приезжает обычным
сообщением, значит ребро подписано ровно тем, что написано на кнопке. Отсюда правило валидатора
(Э3): две одинаковые подписи в одной ноде — ошибка графа.

Исполнение — `run.ts`: пришёл текст → взяли ноду из сессии → выбрали ребро → шагаем, копя ответы,
пока не упрёмся в ждущую ноду (`ask`/`menu`/`subflow`) или конец. Бюджет в 50 шагов сторожит петлю,
нарисованную мышью; падение ноды — это лог, понятная фраза человеку и возврат в меню, а не молчание
бота. Переменные трёх областей: `vars.*` (собрано диалогом, лежит в `BotSession.flowVars`), `ctx.*`
(вычислено по сообщению — кто написал, знает ли его лига; считается **лениво**, иначе каждое
«привет» стоило бы опознания игрока и списка турниров) и `settings.*` (тайминги и тексты
уведомлений — `bot-settings.ts`). Подстановка — прежними фигурными скобками, незнакомая скобка
остаётся текстом.

Граф ведёт **весь входящий путь**: первый уровень и справки (нодами `action`) плюс диалоги, которые
пишут в базу, — регистрацию, правку профиля, заказ встречи, анкеты и ответ на предложение соперника
(нодами `subflow`).

**Ноды-действия** (`actions.ts`, Э4) — тонкие обёртки, а не вторая реализация: внутри зовётся тот
же код, что и в рукописном пути (`tg-menu.ts`, `tg-tournaments.ts`, `tg-login.ts`), а справки ради
этого разделены на «текст» и «клавиатуру» (`profileCard`, `loginCodeText`, `flowTournaments` и
соседи). Разделение и есть суть переезда: **содержимое приносит действие, кнопки рисует нода**.
Поэтому экран в графе один на несколько справок — `screen-main` и `tour-screen` показывают
`{vars.экран}`: клавиатура у экрана постоянная, а текст каждый раз свой, и разводить их по ноде на
справку значило бы держать пять копий одной клавиатуры.

Две вещи, которых требовал переезд. Первая — **списки, которых граф не знает заранее**: названия
турниров и команд приходят из базы, статическими кнопками ноды их не описать. Действие возвращает
их рядами (`ActionResult.keyboard`), ряды достаются ближайшей ждущей ноде и встают НАД её
собственными кнопками — сперва выбор, потом «назад» и «в меню». Вторая — **параметры с
подстановками**: `{vars.турнир_id}` считается перед вызовом, так что нода объявляет, чем кормит
действие, а не действие лезет в переменные наугад. У действия объявлены и `provides` — что оно
кладёт в `vars.*`: без этого валидатор считал бы такие ссылки опечаткой.

**Ноды-модули** (`subflows.ts`, Э5) — то же самое для диалога, который идёт несколько ходов.
Действие отвечает одним экраном и сразу возвращает управление; модуль забирает разговор себе, пока
не скажет «готово». Переписывать рукописные модули не пришлось: все четыре уже одной формы —
`startX() → { replies, step, state, done }` и `handleX(...) → то же`, — и это ровно контракт ноды,
так что в реестре лежит перевод их результата в исходы графа и обратно. **Состояние модуля живёт в
той же строке `BotSession`**, в поле `state` под ключом `sub`: у графа своих данных там нет (его
место — `flowNode`/`flowVars`), а два хранилища на один разговор — это две правды о том, где человек
стоит. Заснули не на модуле — `sub` в строке не будет, иначе брошенная анкета всплыла бы через
неделю на другой ноде.

Выходов у модуля два, и «отменено» значит **модуль не взялся за работу**: править нечего, капитаном
человек не числится, открытых анкет нет. Прерывание уже начатого диалога модули от нормального
конца не отличают — у всех у них это один `done: true`, — и выдумывать разницу снаружи значило бы
врать графу; в дефолтном графе поэтому оба выхода ведут в одно место, а причину модуль объясняет
сам, словами. Ещё одно отличие от действий: **в холостом прогоне симулятора модуль не запускается
вовсе**, вместо экрана печатается пометка «[прогон]», и граф идёт по выходу «готово». Действие
показывает экран и возвращает управление, а модуль на выходе пишет в базу — заявку в очередь,
предложение сопернику, ответ на анкету; прогон, который это делает, не проверка, а вторая жизнь
бота.

**Перехваты уровня флоу** (Э6) — то, что до этого было россыпью `if` в начале `handleMessage`:
`/start`, `/cancel`, кнопки первого уровня, кнопки прошлых версий меню («Мой состав», «Подать
заявку») и ответ на предложение соперника из уведомления. Теперь это свойство графа
(`BotFlowGraph.intercepts`): текст, который бот разбирает раньше ноды, на которой стоит разговор, и
нода, куда он уводит. Перехват начинает разговор заново — собранное прошлым диалогом ему не
принадлежит.

Порядок разбора одного сообщения ровно такой: **собственная кнопка ноды** (иначе «Турниры» на
экране турнира вела бы не туда, куда нарисована связь) → **перехват** → обычный ход ноды → «нода не
взялась» (её вырезали из графа, у кнопки нет перехода) — разговор начинается заново.

Что делать с перехватом, решает **сама нода** — свойством «служебная кнопка» (`ServicePolicy`).
`перехват` — сработать: на меню и экранах справок терять нечего. `повторить` — не бросать начатое:
бот говорит «сначала закончим» и повторяет вопрос, на котором разговор стоит. Второе и есть переезд
старых `SERVICE`-массивов: анкета на седьмом вопросе не должна пропадать от кнопки, оставшейся на
клавиатуре, а у ноды-модуля вопрос знает только модуль — для этого в его контракте появился
`ask(park)`. `/start` и `/cancel` сильнее любой политики (`FlowIntercept.force`): ими человек и
бросает начатое, другого способа выйти у него нет.

**Пустой выход — ошибка валидатора** (тоже Э6). Пока за графом стоял старый обработчик, он значил
шов «дальше разберётся `tg-quiz.ts`»; теперь разбирать некому, и незаполненный выход роняет человека
в начало разговора. Дефолтный граф проходит проверку без единой претензии.

**Редактор — `/admin/bot/flow`** (Э2). Канвас поверх атома Кита `pouf/board.tsx`: ноду двигают
перетаскиванием, связь тянут от кружка выхода до любой ноды. Атому это стоило двух добавок —
смещение в `onDrop` и режим `follow` (за курсором едет сама нода, а не её копия): цели у канваса
нет, предмет остаётся там, где отпустили. Связи рисует свой SVG-слой, а не второй dnd-контекст, —
у dnd-kit целью может быть только объявленный droppable, а тут ею становится любая нода. Отсюда
жёсткая геометрия карточки (`NODE_W`, высоты шапки/тела/строки-выхода): точка, из которой выходит
линия, считается арифметикой, а не замером DOM после каждого рендера.

Общий язык канваса и инспектора — `editor.ts`: `portsOf(node)` отдаёт выходы ноды одним списком
(`next`, `else`, `да`/`нет`, `ок`/`ошибка`, `btn:<номер>`), `setPort` перевешивает любой из них.
Без него канвас, инспектор и валидатор знали бы про девять типов нод каждый по-своему. Ключ кнопки
— **номер, а не подпись**: подпись правят прямо в инспекторе, и связь, привязанная к тексту,
рвалась бы на каждой опечатке.

Правки копятся в памяти вкладки и уезжают целым документом по кнопке — прямое следствие хранения
графа JSON'ом. Порядок версий: черновик (`draft`, не больше одного на ключ) → «В эфир» переводит
его в `published`, прежнюю живую версию — в `archived`; номер версии при этом не меняется, по нему
на неё ссылаются сессии. **Откат — это публикация уже существующей строки**, а не копия; «в
черновик» кладёт старый граф на стол, не трогая эфир. При сохранении проверяется только читаемость
документа (`brokenGraph`: разбирается ли JSON, уникальны ли id, известен ли тип, на месте ли
стартовая нода): черновик на то и черновик, что работа в нём не доделана.

**Проверка и симулятор** (Э3). Валидатор — `validate.ts`, чистый модуль поверх `portsOf`: вход и
выход у каждой ноды (исключения ровно два — у `start` нет входа, у `end` нет выхода), недостижимые
ноды, битые порты, дубли подписей кнопок, ссылки на несуществующие переменные и настройки, циклы,
в которых бот ни о чём не спрашивает, тупики. Ошибки не пускают граф в эфир — и в редакторе (кнопка
гаснет), и на сервере (`publishFlowDraft` и откат зовут ту же проверку: экран мог быть отрисован до
правки). Реестры того, что существует (`ctx.*`, `settings.*`, действия), собирает `registries.ts` и
отдаёт пропсом — сам валидатор чист и потому считается прямо в браузере на каждой правке.
Незаполненный выход был предупреждением ровно до Э6, пока за графом стоял старый обработчик и пустой
выход значил «отдать наружу»; теперь это ошибка (выше).

Симулятор (`simulate.ts` + панель редактора) гоняет тот же интерпретатор по графу **с экрана**,
включая несохранённый черновик. Состояние разговора — нода и переменные — живёт в браузере и
уезжает аргументом каждым ходом, поэтому на сервере от прогона не остаётся ничего: ни строки в
`BotSession`, ни отправки в Telegram, и симулятор не собьёт живого человека посреди анкеты. Ради
этого `run.ts` разделён на ход (`walk`/`turn` — граф и контекст) и его последствия (`settle` —
запись сессии): бот и симулятор ходят одним кодом, а пишет только бот. Тестов в проекте нет —
симулятор и есть способ проверить граф до живого чата. Ноды-действия в прогоне выполняются
по-настоящему (иначе он показывал бы выдуманные экраны), но получают признак холостого прогона
`ActionInput.dry`, и то единственное действие, которое пишет в базу, — выдача кода входа — в прогоне
не пишет.

**Несколько флоу и точка входа** (Э7). Граф больше не один: `main` — меню и `/start`, `invite` —
онбординг по ссылке-приглашению, `answer` — ответ на предложение соперника. Разводить их стоило
потому, что это **разные входы, а не ветки одного разговора**: в `invite` попадают из ссылки на
сайте, в `answer` — с кнопки, которую поставило уведомление неделю назад, и экрана-входа у них нет
вовсе. Как в граф попадают, объявлено **в самом документе** (`BotFlowGraph.entry`): «главный флоу»
(такой один — в него ведёт `/start` без хвоста и возврат «в меню»), хвосты deeplink'а (`invite` —
это `t.me/бот?start=invite`) и подписи кнопок из рассылки.

Складывает объявления в один список `router.ts`, и разбираются они тем же правилом, что перехваты:
точное совпадение по всему списку, потом команда с хвостом, — поэтому `/start invite` выигрывает у
общего `/start`. Порядок списка: перехваты своего флоу → перехваты **главного** (клавиатура первого
уровня висит у человека всегда, и «Турниры» посреди онбординга обязаны значить то же, что в меню) →
точки входа всех графов. Вход по ссылке — команда, и он сильнее политики ноды; вход кнопкой — нет:
начатую анкету случайное нажатие не роняет. Переходы между графами два: нода `goto` с указанным
флоу и конец с «вернуть в меню» — он ведёт в главный флоу, а не в начало своего. Сессия помнит, где
стоит разговор (`BotSession.flowKey` + `flowVersion`), и доигрывает свою версию **своего** графа —
пока его держит модуль, — а соседние берутся из эфира.

**Исходящие уведомления в граф не переехали** (решение Э7, блок в `DECISIONS.md`): нод-триггеров по
расписанию нет, `tg-schedule.ts` шлёт напоминания сам, тайминги живут во вкладке «Настройки». Стык
сделан со стороны входа — кнопка уведомления объявлена точкой входа флоу `answer`, и что случится
по нажатию, правится в редакторе.

Редактор с Э7 правит по одному графу: ключ в адресе (`/admin/bot/flow?flow=invite`), переключатель
и заведение нового флоу — сверху, панель «Точка входа» — рядом с перехватами. Новый ключ открывается
заготовкой «вход → конец» и появляется в списке после первого сохранения. Валидатор получил
проверки, которым нужен весь набор: два главных флоу, одна и та же кнопка входа в двух документах,
переход в несуществующий флоу. Симулятор начинает прогон тем же сообщением, которым в открытый граф
входит живой человек (`/start invite`, «Принять время»), а соседние графы берёт из эфира — дойдя до
«вернуть в меню», он показывает настоящее меню и говорит, что разговор ушёл в другой флоу.

**Гайд оператора — соседний маршрут `/admin/bot/flow/guide`** (Э8), ссылка на него стоит действием
у заголовка редактора. Это не заметка для разработчика, а вводная для человека, который открыл
канвас впервые: разбор каждого типа ноды и каждого поля инспектора, переменные, реестры действий и
модулей, вход и перехваты, версии, симулятор, таблица всех сообщений валидатора «что значит — как
чинить», рецепты и разбор поломки. Устроен он так, чтобы не врать со временем: действия, модули,
`ctx.*`, `settings.*`, типы нод и их выходы рендерятся из тех же реестров, что и сам редактор, а
руками написано только то, чего в коде нет словами. Почему страницей, а не файлом в репозитории —
`DECISIONS.md`, 03.09.2026.

## UI: одна библиотека — Кит в `components/pouf/` (Э3, 01.09.2026)

**До Э3 библиотек было три:** `components/ui/` (сгенерированный shadcn — своя палитра слотов),
`components/pouf/` (Кит — «подушки», токены, Nunito) и `app/_components/ui.tsx` (серверные блоки
страницы). Две кнопки и два инпута делили экраны пополам, из-за чего каждый новый экран был
лотереей, а перекраска — невозможной. Осталась одна: **`web/src/components/pouf/`**.

**Что где внутри.** `pouf.css` — единственный источник значений (палитра Light Clay, тени, радиусы,
шкала отступов, `@utility cushion-*`). Атомы: `Button` (+`IconButton`, `buttonClasses`), `Input`
(+`Field`, `Textarea`, `FormInput`, `FormTextarea`, `Label`, `inputClasses`), `text`, `surface`,
`media`, `layout`, `Segmented`, `separator`, `status`, `Icon`. Интерактив на Radix: `select`,
`checkbox`, `alert-dialog`, `menu`, `sheet`, `toaster`. Блоки страницы: `blocks.tsx` —
`SectionHeader`, `Chip`, `StatTile`, `Meter` и три токена ширины (`SITE_MAX_W` / `READ_MAX_W` /
`FORM_MAX_W`); без `"use client"`, поэтому тянутся в серверные страницы.

**Одно поле — две эргономики.** `Input` контролируемый (`value` + `onChange(string)`), `FormInput`
неконтролируемый (нативные пропы, `name`, читается из FormData). Хром у них общий — одна `cva`
`inputClasses`, — различается только способ достать значение: формы `/me` и служебной части
отправляются серверным экшеном и состояния в React не держат.

**Мост токенов вместо второй палитры.** `@theme inline` в `globals.css` больше не алиасит слоты
shadcn (`--color-primary`, `--color-card`, `--color-border` и т.д.) — их некому читать, блок снят
вместе с библиотекой. Остались имена LOST (`canvas`, `surface-1..3`, `ink`, `ink-muted`,
`ink-subtle`, `hairline`, `accent`, `d1`/`d2`), развёрнутые в `var(--lost-*, fallback)`, где
fallback = значение Кита. `text-muted` и `text-ink-muted` теперь один цвет: раньше первый вёл на
ПОВЕРХНОСТЬ (наследие shadcn, где `muted` — фон), и это лечилось переопределением утилиты внутри
скоупа `.pouf-lost`. Скоупа больше нет.

**Грабля `@theme inline` осталась:** ссылку акцента вести на **сырую** рантайм-переменную
(`var(--accent, …)`), а не на theme-токен (`var(--color-accent)`). Цепочка через theme-токен
схлопывается в литерал на сборке и перестаёт слышать переопределение дивизиона
(`tournaments/[slug]/[div]/layout.tsx` ставит `--accent` инлайном).

**Цвет живёт в токенах, не в call-site.** У `Button` есть проп `className`, но только под раскладку
(отступ, выравнивание): у pouf утилиты одного свойства не каскадируют (порядок классов не решает,
решает порядок правил в собранном CSS), поэтому `className="text-red-600"` поверх кнопки просто не
срабатывает — это не стиль, а тихая ошибка. Цвет задаётся тоном: `.tone-*` несёт и заливку
(`--tone`), и цвет надписи (`--tone-ink`), потому что у Кита к каждому статусу идёт свой ink.
Разрушительное действие — `tone="down"`.

**Тон по-оттенку — это API, не токен.** Имена `tone="purple" | "mint" | "pink"` оставлены (их знают
все call-site), но значения семантические: purple = акцент, mint = ok, pink = ошибка, orange и
yellow = одно и то же внимание. Оттеночных переменных (`--purple`, `--orange`, `--mint`) в
`pouf.css` больше нет.

**Что было отложено:** тёмная графика пост-гейма. Расплетено на Э6 — см. следующий раздел.

## Кожа пост-гейма: один набор блоков, две палитры (Э6, 02.09.2026)

Блоки отчёта по матчу — иконки Доты, инвентарь, дерево талантов, график преимущества, карта
строений, бейджи событий (`app/_components/postgame/blocks.tsx`) — рендерят ДВА разных места:
страницу `/match/<id>` и `/series/<slug>` на бумаге Кита и **экспортный холст PNG** на тёмной
подложке трансляции (`export-canvas.tsx`). До Э6 набор классов у них был один и он был тёмным
(`neutral-800`, `ring-black/50`, `fill-neutral-500`), поэтому светлый сайт таскал за собой
остаток тёмной темы, а перекрасить его было нельзя, не сломав картинку.

**Решение: компоненты не знают своего цвета.** Всё, что не иконка Доты, нарисовано на
`var(--pg-*)` — `--pg-ink`, `--pg-muted`, `--pg-well`, `--pg-ring`, `--pg-plot`, `--pg-grid`,
`--pg-tip`, `--pg-radiant`/`--pg-dire` (+ их мягкие подложки), `--pg-crest`, `--pg-gold`.

- **Экранная кожа — значение по умолчанию.** Объявлена в `globals.css` на `:root`, поэтому любая
  страница получает светлый вариант, ничего не оборачивая. Забыть обёртку невозможно.
- **Тёмная кожа выгрузки — локальное переопределение.** `postgame/skin.ts` экспортирует
  `EXPORT_SKIN`; его вешает инлайном на свою рамку сам холст (`Frame` в `export-canvas.tsx`).
  Действует ровно внутри снимаемой картинки и на сайт не протекает; `domToPng` клонирует рамку
  вместе с инлайновым стилем, поэтому PNG выходит тёмным.

Свет и Тьма красятся `--pg-radiant`/`--pg-dire` не только в отчёте, но и на странице встречи —
чтобы «зелёный» на всех экранах матча значил одно и то же. Зелёный/красный здесь — конвенция
самой Доты, а не акцент Кита: мятная заливка по-прежнему означает «победа/выбрано».

## Чат игроков и присутствие (03.09.2026)

Личная переписка игрок ↔ игрок и точка «в сети» по всему сайту. Две вещи в одной подсистеме
намеренно: присутствие — это побочный продукт живого канала чата, отдельного механизма ему не нужно.

**Кто участвует.** Только игрок лиги: аккаунт со статусом `active` и привязанным профилем
(`chatIdentity` в `src/lib/chat.ts`). Собеседника выбирают в ростере — человека без профиля там
просто нет, отвечать ему было бы некуда. Гость и неодобренный видят приглашение войти, но точки
онлайна видят все: это факт о лиге, а не переписка.

**Хранение.** `Conversation` + `ConversationMember` + `ChatMessage`. Диалог сейчас ровно на двоих,
но комната заведена отдельной сущностью — чат команды или общий канал добавляются составом
участников, не переписыванием доставки. Ключ пары `Conversation.key` = «меньший id : больший id»
аккаунтов, уникален: без него два одновременных первых сообщения завели бы две беседы на одну пару.
Отметка прочтения — у участника (`lastReadAt`), она у каждого своя. Правок и удалений сообщений нет:
переписка — след разговора, а не документ.

**Системный канал «Spirit CTRL» (04.09.2026).** Лига говорит с игроком в том же чате: решения
модерации, приглашения в состав. Собеседник — служебный аккаунт (`UserAccount.system`, помечается
и находится в `src/lib/system-chat.ts`), то есть **обычный участник обычной беседы**: список,
непрочитанное, отметка прочтения и живой канал работают на нём без единой правки. Отличий два —
у него нет профиля в ростере (`Peer.system`, адрес `/chat/system` вместо `/chat/<id игрока>`) и
писать ему нельзя (`sendMessage` отбивает: это канал, а не собеседник).

**Сообщение с выбором.** У системной реплики бывают кнопки — «Иду / Не иду» на приглашение в состав.
Вид действия лежит в `ChatMessage.kind`, его данные — в `payload` (JSON), а **состояние выбора не
хранится нигде**: `src/lib/chat-actions.ts` каждый раз читает его из самой сущности
(`TeamApplicationMember.status`). Иначе у одного факта было бы две правды — «в заявке отказался» и
«в чате нажал принять», — и они разошлись бы на первом же ответе из бота. Оттого ответ, данный
в телеграме или в самой ленте, виден в ней сразу: кнопки сменяются строкой «Вы подтвердили
участие». Нажатие уходит в `POST /api/chat/action` и возвращает ту же строку с пересчитанным
состоянием — лента меняет одну реплику, а не перечитывает беседу.

**Беседа заводится первым сообщением, а не открытием страницы.** Адрес — `/chat/<id игрока>`,
и пока разговора не было, беседы в базе нет. Иначе список зарастал бы пустыми диалогами от каждого
«зашёл в профиль, нажал написать»; заодно серверный рендер страницы остаётся чистым чтением
(Next волен отрендерить его дважды).

**Доставка — SSE.** Одно соединение на вкладку (`GET /api/chat/stream`), открывает его провайдер в
хроме (`_components/chat-live.tsx`), поэтому канал живёт на любой странице, а не только в чате.
Сервер только вещает, клиент отвечает обычными POST — это ровно случай SSE: он переживает прокси,
сам переподключается и не требует второго сервера рядом с Next. WebSocket дал бы то же самое
дороже. Опроса нет ни на одном экране.

**Присутствие живёт в памяти процесса** (`src/lib/presence.ts`), а не в БД: оно истинно только
«сейчас», после перезапуска его надо забыть, а не восстановить. Приложение — один постоянный
процесс Node (`DEPLOY.md`), поэтому память процесса и есть полная картина; станет нод несколько —
на это место встанет Redis-pub/sub, а внешний договор модуля не изменится. Открыта вкладка —
человек в сети, закрыл — вышел, без таймаутов и heartbeat-запросов. Гостю точки и счётчик
рисуются снимком, снятым при рендере страницы: цифра честна на момент открытия и не притворяется живой.

**Обновление экранов.** Открытая беседа дописывает сообщение сама, по подписке на канал; список
бесед и счётчик непрочитанного рисует сервер, и провайдер обновляет его через `router.refresh()`.
Так истина остаётся в одном месте (сервер), а клиент не пересобирает список в состоянии.

**Право писать.** `needsAdmin()` закрывает любой не-GET к `/api/*` для не-админов — для `/api/chat/`
сделано явное исключение: писать в чат это обычное дело игрока. Право проверяет сам роут через
`currentChatMe()`, плюс ограничение частоты (30 сообщений в минуту с аккаунта) и предел длины
(`chat-limits.ts`, один на клиент и сервер).

## Заметки по стеку

Грабли Prisma 7, запуск, проверки — в [CLAUDE.md](./CLAUDE.md) (§2) и `web/AGENTS.md`, чтобы не расходились
в двух местах.

Почему такой выбор: **libsql-адаптер** (`@prisma/adapter-libsql`) — чистый JS, без нативной сборки, поэтому
не требует тулчейна на Windows. **SQLite** — файловая БД, минимум инфраструктуры; рост до Postgres меняет
только строку подключения и адаптер.
