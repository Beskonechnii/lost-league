# Архитектура — как устроены подсистемы

Ядро — **один источник истины (БД)**: админка пишет, публичная таблица и графика читают.
Здесь — устройство подсистем: модель данных, синк, реестр баллов, студия, драфт, ростер,
групповая стадия, архив, турниры.

**Почему сделано именно так — в [`DECISIONS.md`](./DECISIONS.md)** (журнал решений с датами).
Где что лежит — `MAP.md`, что осталось — `BACKLOG.md`, ход работ — `WORKLOG.md`.

## Встраивание в чужой лендинг

Маркетинговый лендинг живёт отдельно (Tilda), приложение — на субдомене. Публичную таблицу
можно встроить туда `iframe`'ом либо `fetch`'ем нашего API. Для `iframe` нужен заголовок
`frame-ancestors` со списком доменов — переменная `FRAME_ANCESTORS` (ставится в `web/next.config.ts`),
без неё браузер встраивание заблокирует. Служебную часть не встраиваем.

Запасной путь вообще без сервера — статический экспорт таблицы (`scripts/build-standings-site.ts`).

## Модель данных

**Источник истины — `web/prisma/schema.prisma`** (там же комментарии к полям). Ниже — назначение моделей:

| Модель | Зачем |
|---|---|
| `Team` | команда: `slug` (ключ импорта и имя файла ассета), айдентика для графики — `logo`, `wordmark`, `photo`, `color` |
| `Player` | игрок: `slug`, `accountId` (Dota/Steam32), ссылки на профили, анкета (`telegram`, `birthday`, `city`) |
| `Series` | **личная встреча (Bo1/Bo3) любой стадии** — контейнер архива турнира: дивизион, `stage` (group/playoff), группа либо половина сетки + раунд, счёт. Бывшая `GroupSeries` |
| `Match` | одна карта: пара команд, расписание, статус, победитель, сторона Radiant, `openDotaMatchId`, длительность и место в серии (`seriesId` + `gameNumber`) |
| `MatchStat` | стата игрока на карте из OpenDota — из неё считаются рейтинги турнира, инфографика и подсказка MVP |
| `Ward` | расстановка вардов карты (obs/sen, координаты, тайминги, кто снял) — из неё «карта вардов команды» (`/admin/vision`) |
| `PointsEntry` | реестр баллов (см. TRACKING) |
| `Render` | сохранённая генерация графики: `templateId` + payload формы |

- **Standings** не храним как истину — считаем: wins/losses из `Match`, очки из суммы `PointsEntry`. (Можно кэшировать.)
- **MVP** = запись `PointsEntry(reason=mvp)` + отметка игрока матча.
- sqlite не поддерживает enum → перечисления хранятся строками, допустимые значения — в комментариях схемы.
- `openDotaMatchId` — **строка**: id матчей Dota не влезает в 32-битный Int.

## SYNC (OpenDota)

1. Вход: `openDotaMatchId` (админ вводит после игры).
2. Читается **тот же `MatchReport`, что рисует постгейм** (`loadMatchReport()` в `match-api.ts`, через общий
   файловый кэш) → `MatchStat` на каждого игрока, который есть в ростере: герой, победа, K/D/A, урон по героям
   и строениям, лечение, net worth, GPM/XPM, добито/денаи, стаки и варды.
3. Из статы — **авто-подсказка MVP** (топ по композитному скору) + данные для инфографики и рейтингов.

**Решение: у синка и у постгейма один источник (29.07.2026).** Раньше `match-sync.ts` ходил в OpenDota сам и
брал пять полей — форма данных для показа и для базы разъезжалась, а поход в сеть не переиспользовал кэш
отчётов. Теперь в базу приземляется ровно то, что видно на странице матча: цифра в рейтинге и цифра в отчёте
не могут разойтись по определению.

⚠️ Детальные поля (урон, лагеря) есть только у **распарсенных** матчей. Если не распарсен — дёрнуть `POST /request/{id}`, подождать, повторить.

## TRACKING (баллы)

- **Реестр `PointsEntry` — единственный способ менять баллы.** Итог = сумма записей.
- **Корректировки = новые записи** (сторно/добавление), ничего не перетираем → полный аудит.
- Правила (заготовка, числа позже):
  - `placement` — победа матча → очки команде.
  - `mvp` — игрок матча → очки/отметка.
  - `cast` / `stream` — кастеру/стримеру за эфир.

## Продукт и служебная часть

Маршруты разделены на две группы одного приложения: `src/app/(public)/` — продукт (лендинг,
турниры и их витрины, ростер, разбор матча), `src/app/(admin)/` — всё, что пишет (студия, правка
ростера, модерация, архив серий). Группы на URL не влияют: у каждой свои `layout`, навигация и
метаданные, у служебной — `robots: noindex`. Граница «читают/пишут» видна прямо в адресе.

`src/lib/admin-session.ts` (`isAdmin()` для серверных компонентов) вынесен отдельно от `auth.ts`
намеренно: `auth.ts` импортирует `src/proxy.ts`, а `next/headers` туда тянуть нельзя.
**Добавляя поле на витрину, проверяй: это факт о лиге или состояние наших данных?** Второе — под `isAdmin()`.

Почему так и почему не отдельный репозиторий — `DECISIONS.md`, «две route-группы одного приложения».

## Флоу (итог)

```
матч сыгран → админ вносит match_id → SYNC (OpenDota) → MatchStat
           → подсказка MVP → админ подтверждает MVP + баллы → PointsEntry
           → Standings пересчитан → публичная таблица + данные для визуала
```

## Студия графики (`/studio`)

_Где лежат файлы движка — в [CLAUDE.md](./CLAUDE.md). Здесь — принятые решения._

Генерация графики к матчам живёт в том же приложении и на тех же данных: команды и игроки — из ростера,
матчи — из `Match`. Отдельного сервиса рендера не заводим.

**Решение: шаблон декларативный** — размер холста + схема полей (`FieldDef`) + React-компонент. Форма мастера
строится из схемы автоматически, поэтому новый шаблон не требует ни новых страниц, ни новых форм. Цена решения —
шаблон ограничен набором типов полей (text/select/team/player/group); расширять их приходится в одном месте.

**Решение: экспорт клиентский** (`modern-screenshot`), а не серверный скриншот. Превью и экспорт — один и тот же
компонент, масштаб снимается на клоне → PNG выходит ровно в размер шаблона. Это даёт инвариант «что вижу — то и
скачал»; ломать его нельзя, иначе расхождение превью и результата придётся ловить глазами.

`/studio/render/[templateId]?p=<base64 payload>` — «голый» рендер без интерфейса: задел под серверный скриншот
(Playwright), когда понадобится рендер по API. Компонент общий с превью, расхождений не будет.

Подложки — экспорт из Figma **без текста и лого команд** (их рисует компонент). Файла нет → градиент-заглушка.
Сохранённые генерации — модель `Render` (payload формы), чтобы переоткрыть прошлый анонс и поправить,
а не собирать заново.

**Решение: пост-гейм скорборд — поле `kind:"match"` (05.08.2026).** Шаблон `postgame-board` (референс: Falcons
vs Tundra) — плотная таблица 10 игроков × колонки (герой, K/D/A, урон, предметы), с перегородками между блоками
команд и колонками. Такое не заполнить руками и не разложить свободными элементами canvas-редактора, поэтому
добавлен новый тип поля `match`: оператор выбирает карту, а весь скорборд разворачивается из неё. Данные и
**предметы** берутся из того же `MatchReport`, что рисует постгейм (`buildScoreboard()` в `src/lib/scoreboard.ts`
поверх `loadMatchReport()` — общий кэш и лимит), лого/цвета команд — из ростера по `radiantTeamId`. Отчёт тяжёлый
и серверный, поэтому в поток `resolvePayload` он не грузится скопом: мастер догружает борд по выбору матча
(`GET /api/studio/match-board`), а «голый» рендер собирает его по `matchId` из payload (`getBoardsForPayload`).
Radiant — верхний блок, Dire — нижний (конвенция Dota и страницы `/match`). Сохранённый `Render` привязывается к
`Match`, поэтому графика видна из архива серий: у каждой карты в `/admin/series` есть кнопка «скорборд», которая
открывает мастер с уже выбранной картой (`/studio/new/postgame-board?match=<id>`).

### Генерация картинок по API (`/studio/generate`)

Второй способ получить картинку — не сборка по данным лиги, а свободная генерация через **OpenAI Images**
(модели `gpt-image-*`). Настройки: модель, промт, размер, качество, количество, режим «использовать как референс».

**Решение: ключ только на сервере.** `OPENAI_API_KEY` живёт в `web/.env` (в `.gitignore`), читает его
единственный роут `POST /api/studio/generate`. Из браузера в OpenAI не ходим — иначе ключ утечёт в бандл.
Поэтому же модуль разделён надвое: `lib/openai-images.ts` (сервер, ключ) и `lib/image-options.ts`
(варианты настроек, безопасно импортировать в клиентский компонент).

**Решение: один роут на два эндпоинта.** Есть референсы → multipart `POST /v1/images/edits` (файлы полем
`image[]`), нет → JSON `POST /v1/images/generations`. Для вызывающего разница только в наличии файлов.
Модели `gpt-image-*` всегда возвращают base64 и **не принимают `response_format`** — его не шлём.

Результаты сохраняются в `public/uploads/generated/` (вне git, чистится вручную). В БД не пишем: это черновой
материал, а не сущность лиги. **Каждая генерация платная** — счёт идёт на аккаунт из ключа; в UI выбрано
дешёвое качество по умолчанию («Авто»), для черновиков есть `gpt-image-1-mini` и «Низкое».

## UNDERBEER 2.0 — шоу-драфт (`/underbeer`, 28.07.2026)

Инструмент эфира: оператор собирает **шоу-команды** из живого ростера драфтом капитанов. Раздел в
служебной части (`(admin)`, за паролем), пункт меню «UNDERBEER 2.0» рядом со Студией.

**Решение: это вывод оператора, а не ростер.** Шоу-команды к `RosterSpot` отношения не имеют — как и
студийная графика, это эфемерный результат, а не источник. Поэтому новая модель `DraftSession` хранит
**всё состояние одной JSON-строкой в `payload`** (как `Render`), а не плодит таблицы команд/составов.
В payload лежат только **id игроков** (`picks`/`captainId`); карточки (ник/фото/mmr/позиция) резолвятся
из ростера при чтении (`src/lib/draft-data.ts` → `draftPool()`). Ушедший из ростера игрок просто выпадает
из состава — драфт живёт один эфир, дублировать снимок всего игрока в БД незачем.

**Решение: сначала отбор участников, потом команды.** Автомат начинается с фазы `roster`: из полного
ростера (поиск по нику/имени, колонки по позициям) оператор отмечает игроков турнира (`participants` в
состоянии), и уже **весь драфт идёт только из них** — пул команд и капитанов фильтруется по участникам.
Старые сессии без `participants` читают весь ростер (обратная совместимость).

**Решение: правила — чистый модуль без БД** (`src/lib/draft.ts`, как `qualification.ts`), поэтому один код
гейтит кнопки на клиенте и мог бы проверяться на сервере. Автомат `roster → config → draft → done`:

- Команд ≥ 2, каждой назначается капитан (капитан занимает первый слот, в драфте не участвует).
- Порядок ходов — **змейка** (1→N, N→1, …): иначе последний капитан всегда собирает объедки.
- В свой ход капитан **либо** берёт 1 игрока из пула, **либо** крадёт 1 из чужого состава
  (кража = действие хода, обычного пика в этот ход уже нет). `currentTurn()` идёт по змейке и пропускает
  уже укомплектованные команды — команда могла добрать состав кражей раньше очереди.
- **Кража честная: у кого украли — добирает вне очереди.** После кражи пострадавшая команда сразу берёт
  одного игрока из пула (`pendingPick` в состоянии, `currentTurn().comp = true`), и только потом змейка
  возобновляется с продвинутого за вором указателя. Так никто не остаётся в меньшинстве посреди драфта.
  Цепной кражи нет: в форс-добор можно только пикать из пула, красть/закреплять нельзя.
- «Закрепить» и «Украсть» — **по разу за весь драфт** на команду. Lock защищает своего игрока от кражи и
  **ход не тратит** (защитное действие); капитана и закреплённых красть нельзя.
- Драфт завершён, когда все команды набрали `targetSize` (капитан в счёт входит).

**Решение: клиент — истина хода, сервер только хранит.** Борд (`_components/draft-board.tsx`) применяет
редьюсеры из `draft.ts` и после каждого действия автосохраняет `PATCH /api/underbeer/[id]` весь payload;
роут лишь проверяет версию формата. Пул перетаскивается (`@dnd-kit/core`) или выбирается кликом,
сегментирован по позиции — **каждая позиция отдельной колонкой** (керри…хард + «без позиции»). **Ошибку
правила показываем строкой, борд не роняем**: редьюсеры бросают на невалидном входе, но кнопки и так
гейтятся предикатами `can*`.

**Решение: автосейв через очередь, а не fetch на каждое действие.** PATCH'и уходят строго по одному, и в
полёте всегда только последнее состояние (`pending`/`flushing` в борде). Иначе на быстрых кликах поздно
прилетевший ранний запрос перезаписывал бы финал — драфт откатывался к более раннему состоянию (поймано при
проверке: сессия «съезжала» обратно в конфиг). Оператор один, конфликтов между людьми нет — очередь решает
ровно переупорядочивание запросов одного клиента.

**Удаление.** Драфты чистятся из списка (`DELETE /api/underbeer/[id]`, кнопка на карточке, оптимистично).
По той же схеме сделано удаление сохранённых генераций студии — `DELETE /api/studio/renders/[id]` и кнопка
в «Истории» (`studio/_components/render-history.tsx`): payload формы это черновик, а не сущность лиги.
Подтверждение — **встроенное (два клика)**, а не `window.confirm()`: нативный диалог подавляется в
webview (панель предпросмотра, десктоп-приложение), и кнопка «молча не работала».

**Решение: оверлей для OBS — отдельная «голая» группа `(bare)`.** Результат драфта отдаётся публично на
`/overlay/underbeer/[id]` (группа `src/app/(bare)/` без навигации и без пароля: у OBS админской куки нет,
а показывается только результат, не операторские кнопки). Операторский борд `/underbeer` при этом закрыт —
префикс добавлен в `needsAdmin()`. Держать оверлей внутри `(admin)` не вышло бы: там бы он унаследовал
`AdminNav` и пароль. Запись (`POST`/`PATCH`/`DELETE /api/underbeer`) закрыта общим правилом «не-GET к `/api`».

## Ростер (`/roster`) — справочник лиги

_Файлы и порядок запуска импорта — в [CLAUDE.md](./CLAUDE.md). Здесь — решения._

**Решение: ростер отделён от студии.** Команды и игроки — единственное место, куда данные **пишут**;
студия и таблица их только читают. Иначе одно и то же название команды разъезжается по трём разделам.

**Решение: `slug` — сквозной ключ.** По нему идёт upsert при импорте и по нему же подбираются файлы лого и фото.
Одно имя связывает гугл-таблицу, БД и картинку — не нужно вести отдельный маппинг.

Роль — строка из списка в `roles.ts` (`carry | mid | offlane | soft-support | hard-support | standin | coach`);
**порядок массива задаёт сортировку состава** везде, поэтому менять его — значит менять вывод во всей графике.

Картинки — локально в `public/uploads/` (в `.gitignore`: это данные лиги, а не исходники).

**Импорт составов берёт xlsx, а не CSV** — ссылки на профили в таблице являются гиперссылками ячеек, в CSV их
попросту нет. Из адресов `dotabuff.com/players/<id>` достаётся `accountId`; ссылка на что-то другое (сайт лиги,
Stratz) → поле пустое. Дивизион берётся из названия вкладки («Команды 1 div»), роль — из колонки «Роль»
(1–5, «Тренер», пусто → замена). Ключи `sheet-to-roster.ts`: `--only <слаги>`, `--div 1`,
`--alias "300$=300-dollars"`, `--dry`.

**Решение: MMR хранится у игрока, у команды — считается (23.07.2026).** `Player.mmr` приходит из колонки «MMR»
той же таблицы сезона. У команды поля нет: `teamMmr()` в `roster-data.ts` берёт **только основу** (позиции 1–5) и
отдаёт среднее и сумму — по той же логике, что и standings, которые тоже не хранятся. Замены и тренер в расчёт не
идут: иначе цифра, по которой команды сравнивают, зависела бы от того, сколько человек вписали в запас.

**Решение: дубль команды — ошибка, а не предупреждение (23.07.2026).** Раньше `sheet-to-roster.ts` только дописывал
команды в `data/roster.json` и никогда ничего не убирал, поэтому команда, сменившая слаг, оставалась в файле навсегда
и рядом с ней появлялась вторая (`300-dollars` + `300`). Теперь таблица — источник истины: при разборе целиком
команда разобранного дивизиона, которой в таблице больше нет, из файла удаляется (при `--only` — нет, там мы про
остальные ничего не знаем). Ручные правки при этом переживают перезалив: непустой `accountId` из файла не затирается
пустой ячейкой таблицы.

Второй рубеж — в `import-roster.ts`: перед записью проверяются три случая (один слаг дважды в файле; одна команда
под разными слагами в файле или в БД; один игрок **действующим** сразу в двух командах), и при любом импорт
**падает целиком**, а не чинит данные на ходу.

## Групповая стадия

Отдельный этап, отыгранный до плей-офф. Источник — вкладка «GS» таблицы сезона, скрипт
`scripts/import-group-stage.ts --sheet <id> --div 1`. Модели: `GroupEntry` (строка команды в группе)
и `Series` со `stage="group"` (личная встреча, счёт серии). Своя вкладка — `/standings/<div>/groups`.

**Два дивизиона (28.07.2026).** Раздел таблиц division-aware: маршруты `/standings/[div]` (`d1`/`d2` →
`Division 1`/`Division 2`), голый `/standings` редиректит на `d1`. Справочник — `src/lib/divisions.ts` (slug ↔
имя ↔ подпись), он же питает две вкладки навигации «LOST D1»/«LOST D2» и под-вкладки дивизионов на `/roster/teams`.
`getStandings(division)` и `getGroupStage(division)` фильтруют по дивизиону; иначе группы A/B двух дивизионов
слились бы в один блок. Импорт GS ищет команду **сначала в своём дивизионе** — одноимённые «ReMix» в D1 и D2
иначе схлопнулись бы в одну; расхождения названий между вкладками «Команды» и «GS» разводит `--alias`
(например `Looking For a Guilty Prime=pasechniki`).

**Решение: единственный источник — сетка встреч (23.07.2026).** И/В/П/О и в группе, и в таблице лиги считаются
из `Series`, поэтому правка встречи двигает обе таблицы сразу — синхронизация выходит сама, копировать
данные между ними не нужно. `GroupEntry` остаётся, но только как **снимок таблицы сезона для сверки**: место в
группе (его из сетки не вывести) и исходные числа, которые показываются в скобках, если расчёт с ними разошёлся.

`getStandings()` складывает три слагаемых: встречи (`Series` любой стадии), одиночные матчи **без серии**
(`Match` с пустым `seriesId` — всё, что завели мимо архива) и ручные начисления (`PointsEntry`). Карты серии
намеренно пропускаются: они уже посчитаны в самой серии, иначе один Bo3 дал бы четыре сыгранных вместо одного.
Таблица делится **по группам**: команды из разных групп между собой не играли, и складывать их очки в один ряд
нечестно.

**Порядок в группе берётся из таблицы сезона, а не из расчёта.** При равенстве очков и побед (morbus mentis и
Eclipse Gaming — обе 4-3 и 12 очков) порядок задавал организатор, и по цифрам его не восстановить. Поэтому
`GroupEntry.place` главнее сортировки — иначе команда уезжает в чужую зону выхода.

**Зоны выхода: 1–4 — верхняя сетка, 5–6 — нижняя, два последних вылетают.** Правила и цвета — в
`src/lib/qualification.ts`, **без обращений к БД**: их использует и клиентская сетка групп. Та же развилка, что
у `openai-images.ts` (сервер) и `image-options.ts` (данные) — `group-stage.ts` тянет Prisma и на клиент не идёт.

**Решение: плей-офф ждёт конца группы, признак автоматический (23.08.2026).** Раньше сетка брала посев
из текущих позиций таблицы, и участники плей-офф менялись после каждой сыгранной встречи. Теперь
`getQualified()` отдаёт зоны только когда стадия завершена, а до этого сетка стоит с заглушками
(«A1», «Победитель ЧФ-1»). Завершённость **не переключается руками** — `groupStageDone()`
(`group-stage.ts`) проверяет, что у всех ожидаемых по жеребьёвке встреч есть результат: ожидаемое —
круговая n·(n−1)/2 по числу команд в группе, «есть результат» — неравный счёт (так же, как решённость
серии в плей-офф, включая техпоражения). Обратная сторона правила: незаведённая встреча для нас не
существует, поэтому обе страницы показывают «сыграно X из Y встреч» — на групповой стадии подписью
у заголовка, в плей-офф плашкой, объясняющей пустую сетку.

**Тег команды заполнен всегда:** `teamTag()` в `profiles.ts` возвращает свой тег из ростера, а если его нет —
выводит из названия (первое слово, до 5 знаков, в верхнем регистре). Заведут тег в ростере — он перекроет.

**Очки за серию Bo3: 2:0 — 3, 2:1 — 2, 1:2 — 1, 0:2 — 0.** Формула в таблице сезона не записана; выведена из
кросс-таблицы и сошлась на всех командах группы A первого дивизиона. Живёт в `seriesPoints()` (`group-stage.ts`).

**Кросс-таблица в источнике не подписана** — в шапке логотипы-картинки, ячейки заголовков пустые. Порядок команд
в матрице восстанавливается расчётом: по каждой строке считаются В-П-очки и сопоставляются с таблицей выше.
Где отпечаток уникален — подпись точная; где нет (в каждой группе нашлась пара команд с одинаковыми В-П-очки) —
встречи помечаются `guessed` и подсвечиваются в UI, чтобы их поправили руками. Правка через
`PATCH /api/series/[id]` снимает пометку: ручной ввод считается подтверждением.

## Архив серий и статистика турнира (29.07.2026)

Вопрос был «где собирать общую стату — кто больше всех убил, нанёс урона — в разрезах турнира». Ответ:
**в тех же строках, из которых уже считается таблица.**

**Решение: `GroupSeries` расширена до `Series`, а не заведена вторая модель.** Групповая встреча и встреча
плей-офф отличаются только полем `stage`: и там, и там пара команд, счёт Bo3 и очки по одной формуле. Вторая
модель означала бы два источника правды для одного и того же вопроса «кто с кем и с каким счётом сыграл» —
и таблица с архивом разъехались бы на первой же правке. Миграция — переименование таблицы, а не drop+create:
в `GroupSeries` лежала вручную выверенная сетка группы.

**Карта серии — это `Match`.** У серии до трёх карт (`seriesId` + `gameNumber`, уникальны в паре).
`openDotaMatchId` глобально уникален, поэтому одна карта физически не может лежать в двух сериях.
Длительность карты (`durationSec`) хранится у матча — без неё «урон в минуту» превращается в рейтинг
длинных игр.

**Стороны определяются по составам, а не вводятся руками.** `detectSides()` считает, чьих игроков больше
в пятёрке (минимум двое — иначе один случайно совпавший `account_id` перевернул бы серию). Та же логика,
что распознаёт названия команд на странице постгейма.

**Игрока опознаём по `account_id`, откуда бы он ни взялся.** Анкеты приходят из CRM неровно: у части
людей заполнено само поле, у части — только ссылка на Dotabuff/Stratz/Steam. `playerAccountId()`
(`src/lib/profiles.ts`) сводит это к одному значению, и им пользуются и синк, и распознавание команд.
Матчить по голой колонке `accountId` значило бы терять статистику половины ростера на ровном месте.
Именной адрес `steamcommunity.com/id/<vanity>` в число не превращается ничем, кроме Steam Web API —
для него есть `scripts/resolve-vanity.ts` (разовый прогон, результат пишется в БД навсегда).

**Ники везде — из ростера, а не из клиента Доты.** В игре человек может называться как угодно и менять
имя между матчами; в лиге у него одно имя. Постгейм подменяет ник на ростерный, когда игрок узнан по
`account_id` (неузнанный — стендин, чужой матч — остаётся под своим именем из OpenDota), а страница
встречи и рейтинги и так читают ник из `Player`. Для этого `/api/roster/teams` отдаёт состав как
`lineup: {accountId, nickname}[]`, а не голый список id.

**Рейтинги считаются, а не хранятся** (`src/lib/leaders.ts`). Любой хранимый итог пришлось бы пересчитывать
после каждой привязки карты и каждого допарса реплея — и он бы молча разъезжался. Строк тут сотни: суммировать
в памяти дешевле, чем поддерживать кэш. Разрез задаётся фильтром `Series` (дивизион / стадия / группа), а
карта **без серии в рейтинги не попадает вообще** — иначе в «плей-офф» протекли бы товарищеские матчи.

**Команды считаются по множеству карт, а не сложением строк.** Пять игроков дают пять строк на карту; сложи
их «сыграно» — и средние за карту окажутся впятеро занижены.

**Разрез — это `stage` + одно из двух полей.** Группа живёт в `Series.group`, половина сетки — в
`Series.bracket` (`upper`/`lower`/`grand`). Сетку держим отдельной колонкой, а не выводим из названия
раунда: по ней фильтруют архив и статистику, и разбирать ради этого свободный текст — способ однажды
потерять серию из-за опечатки. Значение проставляется само по выбранному раунду (`bracketOfRound()`),
поэтому в форме его не спрашивают. Список разрезов для интерфейса — `CUTS` в `src/lib/stages.ts`,
один на обе страницы.

**Решение: у встречи стабильный ключ в адресе (29.07.2026).** `id` автоинкрементный, а `db:import`
пересоздаёт производные строки — после каждого переноса данных встреча получала новый id, и ссылка
`/series/12`, отданная наружу, вела в никуда. Поэтому у `Series` есть `slug` вида
`guzliki-vs-from-paris` (по слагам команд — сквозному ключу проекта; повторная встреча той же пары
получает числовой хвост). Слаг считается один раз при создании, едет в снимке и переживает импорт.
Числовой id роут тоже принимает — ради ссылок, отданных до его появления.

**Страница встречи `/series/<slug>` повторяет форму разбора серии на Dotabuff:** шапка со счётом, ниже
карты, у каждой — оба состава с героем, уровнем и K/D/A. Детали карты (драфт, предметы, график золота)
не дублируются — за ними ведёт ссылка на `/match/<id>`, где всё это уже нарисовано. Счёт карты по
убийствам и первый пик хранятся у `Match`, а не считаются из `MatchStat`: там только игроки лиги, и
карта со стендином показала бы заниженные убийства.

Где что: `/admin/series` — завести встречу, подвесить/отцепить/перечитать карты и удалить встречу
(единственный вход в архив), `/standings/<div>/stats` — рейтинги; фильтры живут в query, поэтому любой
разрез можно кинуть ссылкой. `POST /api/series/[id]/games` читает стату сразу при привязке: отдельной
кнопки «синхронизировать» нет намеренно — карта без статы в архиве бесполезна. Отдельная кнопка
«перечитать» у карты всё же есть, но для другого случая: непарсенный матч через время обрастает
вардами и таймингами, а привязка была раньше.

## Инструмент: импорт матча (каркас)

Отчёт: `/match` (ввод id) → `/match/[id]` (клиент) → `GET /api/opendota/match/[id]` → `fetchMatchReport`
(`src/lib/opendota.ts`). БД не трогает — всё из источника. Сервис публичный и принимает **любой** матч
Dota 2, не только матчи лиги (решено с заказчиком).

Данные (реальные из OpenDota): шапка (время, счёт, победа), **пики/баны с очередью**, **график преимущества по золоту** (по минутам), aegis на команду. По игроку: герой, уровень, K/D/A, LH/денаи, GPM/XPM, ценность (net worth), урон по героям/строениям, хилл, **предметы** (+нейтралка, бэкпек), **порядок способностей**, **тайминги покупок**, постоянные баффы (стаки).

Имена команд подставляются из OpenDota, но поле **редактируемое** (кастомим под LOST).
Резолв id→имя через кэш констант OpenDota (`item_ids`/`items`, `ability_ids`/`abilities`, `permanent_buffs`). Детальные поля есть только у **распарсенных** матчей (`version != null`) — иначе часть пуста (есть предупреждение в UI).

## Турниры как сущность (22.08.2026)

Дивизионы были константой в коде: «завести сезон» означало правку исходников. Теперь сезон или кубок —
строка `Tournament`, дивизион (`Division`) принадлежит турниру, а участие команды — отдельная строка
`TournamentEntry` (там же группа и посев). Разделение принципиальное: **команда переживает турнир**,
её участие — нет, поэтому «дивизион команды» не поле у команды, а связь. Состав тоже сезонный —
`RosterSpot.divisionId`, иначе заявка нового сезона затирала бы прошлый.

**Зеркала строкой — сознательное отступление.** `Team.group`, `Series.division` и `GroupEntry.division`
продолжают хранить имя дивизиона текстом: по ним фильтруют полтора десятка выборок (standings,
leaders, архив серий, витрины ростера), и переписать их разом ради чистого FK — способ уронить
работающий сезон. Источник правды — `divisionId`; единственный, кто пишет зеркала, — `src/lib/tournaments.ts`.
Новый код разрезает данные по `divisionId`, а не по строке.

**Дубли профилей разбирает оператор, а не автоматика** (`/admin/duplicates`, `src/lib/duplicates.ts`).
Один человек попадает в ростер дважды, когда меняет ник между сезонами: апрув заявки узнаёт его по
`account_id`, но в таблице сезона номера часто нет, а слаг нового ника другой — и места в составах,
статистика карт и баллы расходятся по двум записям. Очередь показывает пары с признаком, почему они
похожи (общий `account_id`, телеграм, имя, почти одинаковый ник) и чем каждая запись наполнена — по
этому видно, какую оставлять. Решений три: **объединить** (всё переезжает к победителю, донор
удаляется), **переименовать** (это не дубль, а смена ника: данные и стата остаются на месте) и
**«разные люди»** — пара уходит в `PlayerDistinct` и больше не всплывает, иначе очередь вечно
показывала бы тёзок.

Автоматически не сливаем, потому что операция необратима, а общее имя — это ещё и два тёзки.
Слияние переносит места в составах, строки статистики карт, начисления реестра (`PointsEntry` —
руками: там не связь, а пара «тип + id») и заявку на привязку аккаунта; пустые поля победителя
дополняются данными донора, `Player.tp` пересчитывается из реестра. Совпавшие строки схлопываются —
одно место в той же команде сезона, одна строка статистики той же карты — иначе упрёмся в
`@@unique`; сколько схлопнется, показано до нажатия. Права: правка — `roster.edit`, слияние требует
ещё `roster.delete`, потому что запись исчезает.

**Составы попадают в лигу двумя путями, писатель один.** Импорт таблицы оператором (`roster-import.ts`)
пишет в ростер сразу — подтверждать себе нечего. Заявка капитана с сайта ложится в очередь
`TeamApplication` (payload — состав целиком JSON, `Team` до апрува не создаётся, как в плане аккаунтов)
и попадает в ростер только при одобрении. Обе ветки зовут `writeTeamToRoster` и общий набор проверок
`applicationProblems` (дубли, конфликт составов, занятый слаг). Разбор входов — один парсер на все
формы (колоночная раскладка, блочная сезонная таблица, построчный текст), а сеть — Steam и
OpenDota — вынесена отдельным шагом (`enrich.ts`): запрос посреди сохранения дюжины команд
превращается в таймаут. Из OpenDota сохраняем только ранг (`Player.rank`); ник в лиге человек
выбирает сам, а `Player.photo` у нас всегда локальный файл — и то, и другое оператору показываем
справкой.

**Третий вход состава — телеграм-бот** (`src/lib/tg-quiz.ts`). Квиз ведёт капитана по одному вопросу:
турнир и дивизион (выбор из одного варианта проставляется молча), название и тег, дальше по каждому
игроку — ник, позиция, ссылка на профиль, телеграм. Готовый состав ложится в ту же очередь
`TeamApplication` с `source = telegram`, апрув и проверки общие; автора у такой заявки нет
(`submittedById` пуст) — капитана оператор опознаёт по телеграму в составе, а дедуп идёт по слагу.
Свободный текст бот не разбирает, хотя парсер (`roster-import.ts`) под рукой: на входе от незнакомого
человека тот ошибается молча, и оператор получает заявку с пустыми позициями. Пошаговый вопрос
проверяет ответ на месте, пока капитан ещё в диалоге. Ссылка на профиль обязательна у каждого игрока:
без account_id человек не находится ни в одном матче. Диалог живёт в `BotSession` (одна строка на чат),
а не в памяти процесса — бот работает с ноутбука и переживает перезапуск.

**Вопросы бота правит оператор, а не разработчик** (`/admin/bot`, право `tournaments.edit`).
Формулировка шага — работа организатора, и держать её в исходниках значит ходить за правкой запятой
в код. Дефолтные тексты остаются в коде (`quiz-config.ts`), в таблицу `BotQuestion` попадают **только
отличия**: пустая база означает бота с обычными вопросами, а не бота без вопросов, и правка дефолта
доезжает до всех, кто ничего не менял. Оператор меняет тексты, отключает необязательные шаги (тег,
телеграм игрока, выбор дивизиона) и заводит свои вопросы — они задаются после состава, а ответы
едут в заявку отдельным блоком и видны на странице заявок турнира. Порядок и состав обязательных
шагов оператору не отданы: ник, позиция и ссылка диктуются моделью заявки. Конфигурация читается на
каждое сообщение — правка действует сразу, без перезапуска бота.

**Меню бота и раздел «Турниры»** (`src/lib/tg-menu.ts` + `src/lib/tg-tournaments.ts`). Первый
уровень — «Личный профиль» и «Турниры», плюс «Анкеты» (когда открытая анкета есть) и
«Регистрация» (когда лига человека не знает). Всё остальное живёт уровнем ниже, у того, к чему
относится: вход на сайт и правка данных — в профиле, состав и команды — внутри турнира. Причина не
только в размере экрана: **состав принадлежит дивизиону турнира** (`RosterSpot.divisionId`), и одна
кнопка «Мой состав» на все сезоны сливала D1, D2 и прошлый сезон в один список — внутри турнира
вопрос однозначен.

Навигация — три уровня (турнир → раздел → команда), шаги `tt_*` в общей `BotSession`. Показываются
турниры со статусом `registration`, `running` и три последних `finished`; черновики не показываются
никогда — их оператор ещё заводит. Команды выводятся кнопками, а карточка приезжает отдельным
сообщением: в сообщение Telegram влезает 4096 знаков, а команд в дивизионе бывает два десятка.
Имена команд не уникальны (одноимённые команды есть в разных дивизионах) — по кнопке показываются
все совпавшие карточки, а не угаданная первой.

Навигация **не считается начатым диалогом**: кнопка меню посреди квиза заявки по-прежнему даёт
справку и повтор вопроса (терять там собранный состав нельзя), а из раздела «Турниры» кнопка меню
просто выводит — там нечего терять, кроме места в списке. Отдельно ловятся кнопки прошлой версии
меню: клавиатура у Telegram висит до отмены, а квиз заявки начинается на любой непонятый текст —
без этого нажатие на старую кнопку роняло человека в диалог, которого он не просил.

**Регистрация игрока через бота** (`src/lib/tg-register.ts`, шаги `reg_*`). Второй вход в ту же
воронку, что и анкета в кабинете: те же поля, та же проверка (`normalizeApplication`), тот же JSON в
`UserAccount.application`, та же очередь `/admin/moderation` и тот же `approveRegistration`. Отличий
ровно два. Почты у пришедшего из бота нет — `UserAccount.email` стал необязательным, а вторым ключом
аккаунта служит `tgId` (это `from.id` апдейта, а не `chat.id`: в личке они совпадают, но ключ
принадлежит человеку). Телеграм не спрашивается вовсе — он приезжает в апдейте; без хендла
регистрация не начинается: это единственный контакт человека для организатора.

Смысл всей затеи — **привязка вместо узнавания по хендлу**. До неё бот опознавал человека по
`@username`, а хендл меняют, и освободившийся занимает посторонний, — поэтому боту нельзя было
доверить ничего, что пишет. `UserAccount.tgId ↔ playerId` переживает смену хендла и становится
первым источником в `identify` (`tg-menu.ts`); хендл и account_id из заявок остались запасными
ветками для тех, кто в лиге давно. Чат при отправке анкеты закрепляется за аккаунтом
(`TgChat.accountId`) — по нему уходит решение организатора (`tg-notify.ts`), и он же будет адресом
напоминаний о встречах.

Пишет анкету в базу сам `tg-register.ts`, а не `account.ts`: тот помечен `server-only` и в процесс
бота (обычный node, `scripts/bot.ts`) не грузится. Ровно та же причина, по которой заявку команды из
бота принимает `team-application.ts`. Второй реализации «пустить в лигу» при этом не появилось —
апрув один на оба входа.

**Вход на сайт по коду из бота** (`src/lib/tg-login.ts`, страница `/login/tg`). У зарегистрированного
через бота нет ни почты, ни пароля — войти в кабинет ему нечем, а сборка состава и профиль живут на
сайте. Кнопка «Войти на сайт» выдаёт шесть цифр, страница их принимает и ставит **ту же подписанную
куку**, что вход по паролю: код проверяет `redeemLoginCode`, сессию выдаёт `establishSession`
(`account.ts`) — второй реализации входа не появилось. Код живёт 10 минут, гасится при первом
использовании (условием `usedAt: null` в `updateMany` — два одновременных ввода не должны оба стать
входом), и живой держится **один на аккаунт**: подбор шестизначного числа упирается в одну цель со
сроком, а не в «любой из накопленных». Выдаётся код строго по привязке `UserAccount.tgId` — тому,
кого бот узнал только по хендлу, его не дают: хендл не удостоверение, а код это ключ от кабинета.

Почему код, а не Telegram Login Widget: виджету нужен домен, привязанный к боту в BotFather, а до
выката наружу у нас туннель и невыбранный VPS — вход не должен ждать переезда. После выката виджет
добавится второй кнопкой на `/me`, не вместо кода (`DEPLOY.md`). Адрес, который бот подставляет в
ссылку, — `BASE_URL` (пусто = `http://localhost:3000`). Ссылка из бота **без кода в адресе**:
предпросмотр ссылки или чужой глаз в истории браузера сожгли бы его молча.

**Личный профиль в боте и правка через модерацию** (`src/lib/tg-profile.ts` + `profile-edit.ts`,
шаги `pe_*`). «Личный профиль» показывает всё, что лига о человеке знает: анкету (имя, город, дата
рождения, MMR), TP за всё время (кеш реестра, `Player.tp`), команду в разрезе турнира с позицией и
капитанством (последний `RosterSpot`), ссылки на Dotabuff/Stratz/Steam и телеграм.

Кнопка «Изменить данные» появляется **только у привязанного профиля** (`UserAccount.tgId`) — то же
правило, что у кода входа: узнанному по хендлу бот показывает, но писать в чужой профиль не даёт.
Диалог из двух шагов (какое поле → новое значение), и правка уезжает **в очередь `ProfileEditRequest`**,
а не в `Player`: бот сам ничего не публикует. Одна строка — одно поле (`nickname`, `city`, `mmr`,
три ссылки, `photo`): человек чаще правит что-то одно, а оператору так видно «было → стало» без
диффа всей анкеты. Открытая правка на поле только одна — иначе оператор одобрил бы устаревшее
значение вслед за свежим. Смена ника соблюдает общий кулдаун (скользящее окно 120 дней,
`Player.nicknameChangedAt`): правило теперь живёт в `profile-edit.ts` и переиспользуется кабинетом
на сайте (`updateOwnProfile`) — двух правил «раз в сезон» быть не должно. Проверяется он **до**
вопроса о новом нике: заставить придумать ник и потом сказать «нельзя ещё 40 дней» — худший порядок.

Фото приезжает картинкой (транспорт пропускает `message.photo`, скачивание — `fetchFile` в
`telegram.ts`) и **кладётся в `public/uploads/players` сразу, до решения** — иначе оператору нечего
смотреть, а именно смотреть здесь и надо; так же работает загрузка из админки. Цена — файл
отклонённой правки остаётся на диске. Экран очереди — вкладка «Правки профиля» в `/admin/moderation`
под своим правом `roster.edit` (это правка ростера, а не решение «пускать в лигу»): без права
вкладки нет вовсе. Апрув пишет в `Player` и уведомляет в бот, отказ — с причиной (`tg-notify.ts`,
чат берётся из самой правки).

**Анкеты под ивенты** (`/admin/quizzes`, `src/lib/quizzes.ts` + `tg-forms.ts`) — то, что оператор
заводит сам: запись на шоуматч, опрос, заявка кастера. Отдельно от заявки команды сознательно:
заявка завязана на модель ростера (команда, пять позиций, ссылки, очередь модерации, запись в ростер
при апруве), а анкета не пишет никуда, кроме своих ответов, и вопросы у неё любые. Общий у них
только движок «вопрос → ответ → сводка»; свести их в одну сущность значит на каждой правке
разбираться, к какому из двух случаев относится проверка. Отсюда и две модели вопросов: `BotQuestion`
переопределяет **дефолтные** шаги заявки (дефолт в коде), `QuizQuestion` существует только в базе —
дефолт ему брать неоткуда.

Статусы анкеты — `draft` / `open` / `closed` плюс срок `closeAt`, закрывающий приём сам (как
`regCloseAt` у турнира). Кнопка «Анкеты» появляется в меню бота, только когда открытая анкета есть:
раздел, который на всё отвечает «сейчас ничего нет», хуже отсутствующего. Шаги анкеты живут в той же
`BotSession`, что и шаги заявки (диалог у человека один), и разведены префиксом `form_*`. Один чат —
одна запись на анкету: повторное прохождение правит прежнюю. Ответы хранятся вместе с текстом
вопроса — вопрос перепишут, а ответ прошлого месяца должен остаться читаемым; в таблице админки они
поэтому сопоставляются по тексту, а не по порядку, а ответы на удалённые вопросы показываются
отдельно, чтобы не пропасть молча. Выгрузка — `GET /api/quizzes/<slug>/export` (CSV с BOM, иначе
Excel ломает кириллицу); роут закрыт правом `quizzes` и добавлен в `needsAdmin` — это люди, их
контакты и то, что они написали организатору.

**Меню бота вне квиза** (`src/lib/tg-menu.ts`): «Мой состав», «Личный профиль», «Турниры». Человека
узнаём по телеграм-хендлу отправителя — он приезжает в каждом апдейте, а в ростере хендл уже хранится
(`Player.telegram`), и просить представиться значит спрашивать известное. **Хендл при этом не
удостоверение**: его меняют, а освободившийся может занять посторонний. Поэтому меню показывает
только то, что и так публично на сайте, и ничего не меняет — всё, что пишет, идёт через квиз и
очередь модерации. «Мой состав» показывает **и поданные заявки со статусом, и составы, уже заведённые в лигу** — состав,
собранный минуту назад, в ростере появится только после одобрения, а прошлые сезоны никуда не делись.
Составы всегда в разрезе турнира: команда переживает сезон, участие — нет, и «мой состав» без турнира
это два разных состава, слитых в один список.

**Чат подавшего запоминается вместе с заявкой** (`TeamApplication.submittedChatId`), а все, кто писал
боту, — в `TgChat`. Причина простая: Telegram не даёт написать человеку по хендлу, только по `chat_id`,
и он появляется, лишь когда человек сам написал. Без этого нельзя ни показать капитану статус его
заявки (телеграм в составе он мог не указать — так и было на первом живом прогоне), ни уведомить о
решении организатора. По этой же ниточке идёт **опознание вторым способом**: к найденным по хендлу
добавляются игроки с `account_id` из заявок этого чата. Номер аккаунта Dota надёжнее хендла: хендл меняют.

**Опознание возвращает список, а не одного игрока.** В ростере встречаются дубли — один человек
заведён дважды (импортом и заявкой) с разными `account_id`, и мест в составе может не быть у той
записи, что попалась первой; бот тогда отвечал «вас нет в лиге» тому, кто в команде играет. Поэтому
«Мой состав» собирает составы всех совпавших записей, «Личный профиль» показывает ту, что реально
играет (профиль без единого места — почти всегда осколок импорта), и предупреждает о дубле:
склеивает записи оператор, но человек должен понимать, почему видит чужой MMR. «В лиге, но нигде не
заявлен» — отдельный ответ, не путать с «не нашли».

**Решение организатора уходит в телеграм** (`tg-notify.ts`): одобрили или вернули с причиной — бот
пишет подавшему и тем игрокам состава, чьи чаты знает. Отправка идёт после записи и вне транзакции:
упавший телеграм — повод написать в консоль, а не откатить заведение команды. Нажатие кнопки меню посреди квиза **не сбрасывает диалог**: бот отвечает и
повторяет вопрос, на котором стоял (`askCurrent`) — капитан на седьмом игроке не должен терять
состав из-за случайного нажатия.

**Удаление турнира** (`deleteTournament`) сносит сезон целиком: карты серий, серии, строки групп,
места составов дивизионов, начисления TP и сам турнир (дивизионы, участие, заявки — каскадом).
Зеркала и кеш `Player.tp` чинятся следом, потому что FK-каскад их не знает. Команды и игроки
остаются в ростере — уходит только участие. Задумано для тестовых прогонов, право `tournaments.edit`.

Права: всё, что пишет турниры, закрыто `tournaments.edit` — и на странице, и в server-action
(до экшена можно дойти мимо страницы, ACCOUNTS-PLAN.md §2.2).

## UI-примитивы: shadcn/ui на токенах LOST (03.08.2026)

shadcn/ui — не зависимость, а генератор: компоненты копируются в `web/src/components/ui/` (Radix +
`class-variance-authority`, иконки `lucide-react`, утилита `cn()` в `src/lib/utils.ts`). Добавление —
`npx shadcn@latest add <name>`; конфиг — `components.json` (style `new-york`, alias `@/components/ui`).

**Решение: мост токенов, а не вторая палитра.** У проекта уже своя дизайн-система (`globals.css`:
canvas/surface/ink/accent). Дефолтный `init` завёл бы параллельный набор переменных в OKLCH и серый вид,
спорящий с идентичностью LOST. Поэтому `init` не запускали — вместо этого в `@theme inline` **алиасим**
слоты shadcn на наши токены: `--color-primary → --accent`, `--color-card → surface-1`,
`--color-border → hairline`, `--color-ring → --accent` и т.д. Один источник правды по цвету.

**Грабля `@theme inline`:** ссылку акцента вести на **сырой** рантайм-переменную (`var(--accent, …)`),
а не на theme-токен (`var(--color-accent)`). Цепочка через theme-токен схлопывается в литерал на сборке и
перестаёт слышать переопределение дивизиона (`standings/[div]/layout.tsx` ставит `--accent` инлайном). При
прямой ссылке shadcn-хром (кнопки, ring, hover в меню) сам перекрашивается D1→D2, как и остальной хром.

**Граница ответственности:** shadcn — для **интерактива** (dialog, dropdown, tabs, tooltip, формы — всё с
`"use client"` и Radix). Серверные презентационные примитивы (`SectionHeader`, `Chip`, `StatTile`) остаются
в `src/app/_components/ui.tsx` — они без `"use client"` и через Radix их гнать незачем.

**Кнопки/поля стандартизованы на shadcn.** Все action-кнопки (CTA, сабмиты, строчные действия) сведены к
`Button` (варианты default = flat-accent / outline / ghost) — рукодельные градиентные кнопки убраны. Фирменный
янтарь UNDERBEER сохранён как `className` поверх `Button`. Текстовые поля/пароль/поиск — на `Input`, многострочные —
на `Textarea`, галочки — на `Checkbox`; `TextField`/`TextAreaField`/`SelectField` в `_components/form.tsx` внутри
уже на shadcn, поэтому все формы обновились разом. `alert()` — на `sonner`-тосты (нативный alert/confirm глохнет
в webview). Чип-метка `ui.tsx#Chip` — на базе `Badge` (вид LOST задан поверх). **Сознательно НЕ переведены** (иной
примитив, не `Button`): сегмент-тоглы и пилюли-фильтры (пилюли дивизионов, фильтры архива), табы (отчёт матча,
карточка команды), навигация (на роутинге), оверлей-иконки (↻/✕), инлайн-редакторы названий (прозрачные, без рамки)
и плотные инпуты/плитки борда драфта (своя sky/amber-палитра) — у них своя семантика.

**Карточки остаются на токенах, а не на `Card`-примитиве.** Бордер/поверхность карточек уже задаются теми же
токенами, что и `Card` (`rounded-xl border-hairline bg-surface-1` ≈ `bg-card`), а разметка внутри у каждой своя —
у команд, серий, драфтов, `StatTile`. Оборачивать их в `Card` = либо менять
паддинги/тень, либо гасить дефолты `Card` классами: визуально ноль, churn ненулевой. Поэтому `Card` держим для
**новых** обобщённых панелей, а существующие карточки — презентационный слой LOST на общих токенах.

## Заметки по стеку

Грабли Prisma 7, запуск, проверки — в [CLAUDE.md](./CLAUDE.md) (§2) и `web/AGENTS.md`, чтобы не расходились
в двух местах.

Почему такой выбор: **libsql-адаптер** (`@prisma/adapter-libsql`) — чистый JS, без нативной сборки, поэтому
не требует тулчейна на Windows. **SQLite** — файловая БД, минимум инфраструктуры; рост до Postgres меняет
только строку подключения и адаптер.
