# Архитектура — операционная система LOST (данные / флоу / треккинг)

Дев-спека того, что реализуем. Ядро — **один источник истины (БД)**: админка пишет, публичная таблица и графика читают.
Решения приняты 22.07.2026. Значения баллов и точные правила — задаём позже.

## Стек (рекомендация)

- **Next.js (React, TypeScript)** — одно приложение: публичная часть (standings) + **админка** (MVP/баллы) + API-роуты (синк OpenDota, запись баллов).
- **SQLite + Prisma (ORM)** — «кастомная БД», файловая, минимум инфраструктуры. Рост → Postgres меняет только строку подключения.
- Почему: один codebase, «меньше кода», не-разработчик правит через админку, фронт читает из той же БД.

### Интеграция с лендингом (Tilda)

Текущий сайт — **Tilda** (закрытый конструктор: кастомную БД внутрь не встроить, но есть HTML-блоки, iframe, кастомный JS). Сейчас таблицу результатов тянет из **Google Sheets**, профили — в Stratz/Dotabuff.

- Наш Next.js — на **субдомене** (напр. `app.leagueofspirits.ru`): `/standings` (публично), `/admin` (защищено), `/api/*` (синк OpenDota, баллы, JSON для графики).
- **Публичная таблица «на лендинге»:** встраиваем в Tilda через HTML-блок — `iframe` на `app…/standings` (быстро) **или** кастомный `fetch()` нашего API с рендером (аккуратнее). Заменяет текущий Google-Sheet-блок.
- Для `iframe` нужен заголовок **`frame-ancestors`** со списком доменов основного сайта — переменная
  `FRAME_ANCESTORS` (см. «Решение: кэш отчётов и лимит по IP»). Без неё браузер встраивание заблокирует.
- **Админка** — только на субдомене, в Tilda не встраиваем.
- **DNS:** CNAME субдомена → хостинг (напр. Vercel). Корень Tilda не трогаем.
- Маркетинговый лендинг оставляем как есть — добавляем пункт меню + блок-встройку.

## Модель данных

**Источник истины — `web/prisma/schema.prisma`** (там же комментарии к полям). Ниже — назначение моделей:

| Модель | Зачем |
|---|---|
| `Team` | команда: `slug` (ключ импорта и имя файла ассета), айдентика для графики — `logo`, `wordmark`, `photo`, `color` |
| `Player` | игрок: `slug`, `accountId` (Dota/Steam32), ссылки на профили, анкета (`telegram`, `birthday`, `city`) |
| `Series` | **личная встреча (Bo1/Bo3) любой стадии** — контейнер архива турнира: дивизион, `stage` (group/playoff), группа либо половина сетки + раунд, счёт. Бывшая `GroupSeries` |
| `Match` | одна карта: пара команд, расписание, статус, победитель, сторона Radiant, `openDotaMatchId`, длительность и место в серии (`seriesId` + `gameNumber`) |
| `MatchStat` | стата игрока на карте из OpenDota — из неё считаются рейтинги турнира, инфографика и подсказка MVP |
| `Ward` | расстановка вардов карты (obs/sen, координаты, тайминги, кто снял) — из неё «карта вардов команды» (`/admin/vision`) |
| `PointsEntry` | реестр баллов (см. TRACKING) |
| `Render` | сохранённая генерация графики: `templateId` + payload формы |

- **Standings** не храним как истину — считаем: wins/losses из `Match`, очки из суммы `PointsEntry`. (Можно кэшировать.)
- **MVP** = запись `PointsEntry(reason=mvp)` + отметка игрока матча.
- sqlite не поддерживает enum → перечисления хранятся строками, допустимые значения — в комментариях схемы.
- `openDotaMatchId` — **строка**: id матчей Dota не влезает в 32-битный Int.

## SYNC (OpenDota)

1. Вход: `openDotaMatchId` (админ вводит после игры).
2. Читается **тот же `MatchReport`, что рисует постгейм** (`loadMatchReport()` в `match-api.ts`, через общий
   файловый кэш) → `MatchStat` на каждого игрока, который есть в ростере: герой, победа, K/D/A, урон по героям
   и строениям, лечение, net worth, GPM/XPM, добито/денаи, стаки и варды.
3. Из статы — **авто-подсказка MVP** (топ по композитному скору) + данные для инфографики и рейтингов.

**Решение: у синка и у постгейма один источник (29.07.2026).** Раньше `match-sync.ts` ходил в OpenDota сам и
брал пять полей — форма данных для показа и для базы разъезжалась, а поход в сеть не переиспользовал кэш
отчётов. Теперь в базу приземляется ровно то, что видно на странице матча: цифра в рейтинге и цифра в отчёте
не могут разойтись по определению.

⚠️ Детальные поля (урон, лагеря) есть только у **распарсенных** матчей. Если не распарсен — дёрнуть `POST /request/{id}`, подождать, повторить.

### Решение: тема UI — цвета в файле, не в БД (12.08.2026)

Цветами проекта (акцент D1/D2, поверхности, текст, границы) управляет панель `/admin/theme`.
Значения лежат в `data/theme.json` — как `snapshot.json`, файл **коммитится** и едет между
устройствами, без миграции Prisma и бампа версии снимка. Читает/пишет `src/lib/theme-store.ts`,
чистая логика (типы, дефолты, список полей, сборка CSS) — `src/lib/theme.ts`.

Механика перекраски одна на весь сайт: базовые токены в `globals.css` под `@theme inline`
развёрнуты из литералов в `var(--lost-*, fallback)` (fallback = дефолт темы), а корневой layout
ставит текущие значения инлайн-`style` прямо на `<html>` (= `:root`). Приём тот же, что уже работал
для `--accent` (слой дивизиона): под `@theme inline` ссылка на сырую переменную остаётся живой в
рантайме, на theme-токен — схлопывается в литерал на сборке. Инлайн-`style` на `<html>`, а не
`<style>`-тег, выбран сознательно: `<style>` в React 19 требует `precedence`/`href` для хостинга и
шумит в консоли, а style-атрибут чисто обновляется и не хостится. Префикс `--lost-*` нарочный —
сырые `--ink`/`--muted`/`--surface` заняты pouf.css, без префикса вышла бы коллизия.

**Второй слой — 1st-Pouf.** На сайте параллельно живут две палитры: LOST (лендинг, таблицы, ростер)
и pouf/claymorphism (студия, архив, TP, драфт, заглушки, бейджи). Панель правит обе. Акцент pouf
(`--purple`) и `--on-accent` привязаны в `globals.css` прямо к бренд-`--accent`/`--accent-contrast`
— одна настройка на оба слоя. Остальные pouf-цвета (фон/поверхность/текст + статусы warn/down/up/
info/orange) идут через `--lost-pouf-*`, которые скоуп `.pouf-lost, .pouf-overlay, .pouf-sheet-dialog,
.pouf-menu` раздаёт в pouf-переменные тремя адресами разом: @theme-имя (`--color-*` для утилит
`bg`/`text`), короткий alias (`--surface`/`--ink`/… для CSS компонентов) и семантический alias
(`--warn`/`--down`/… через который тоны красят бейджи). Раздача на уровне body/скоупа, а не `:root`:
pouf объявляет эти переменные на `<html>`, и наследование от `body` (ниже по дереву) выигрывает —
поэтому правки видны и в порталах Radix.

Значения санитайзятся (`safeValue`) и на записи, и на рендере — руками поправленный `theme.json`
тоже ничего не инжектнёт. После записи API зовёт `revalidatePath("/", "layout")`, чтобы весь сайт
перечитал тему.

### Решение: варды карт лежат в БД (06.08.2026)

Расстановка вардов (`obs_log`/`sen_log` распарсенного отчёта) приземляется в модель `Ward` тем же `syncMatch`, что
и `MatchStat`: сторона, тип (обсервер/сентри), герой-постановщик, координаты (доля карты 0..1), секунды постановки и
снятия (пара матчится по `ehandle`), герой-убийца. `teamId` денормализован из стороны и `Match.radiantTeamId` — чтобы
«карта вардов команды» бралась одним `where` по `teamId`. Строки производные: при перечитке карты сносятся и
создаются заново.

**Зачем в БД, а не на лету из кэша.** Фича `/admin/vision` смотрит варды **по всему архиву команды** (сводное
наложение + каждая карта с полоской времени). Считать это на лету значило бы грузить десятки отчётов из кэша (gitignore,
TTL) или из OpenDota (лимит по IP) на каждый запрос. В БД — офлайн и быстро, как и остальная статистика архива. Данные
едут в снимке (`snapshot.json`, версия 5). Сборка выборок — `src/lib/vision.ts`, карта — общий клиентский компонент
`_components/postgame/vision-map.tsx` (он же во вкладке «Варды» отчёта матча). Уже привязанные до этой фичи карты
заполняются разово: `scripts/backfill-wards.ts` (резюмируемый, щадит лимит OpenDota).

## Продукт и служебная часть

### Решение: две route-группы одного приложения (28.07.2026)

Приложение выросло как **инструмент оператора, у которого есть публичные страницы**. Нужно было
обратное: **продукт, у которого есть админка**. Диагноз оказался не в слоях — они разложены нормально,
`needsAdmin()` и был единственным местом правды, — а в форме: входная дверь `/` это поле ввода id матча,
в меню торчала студия, у отчёта не было постоянной ссылки.

Маршруты разделены на `src/app/(public)/` (продукт: лендинг, разбор матча, таблица, витрины ростера)
и `src/app/(admin)/` (всё, что пишет: студия, правка ростера, вход). Группы на URL не влияют, у каждой
свои `layout`, навигация (`PublicNav` / `AdminNav`, янтарный акцент у служебной) и метаданные —
у служебной `robots: noindex`. Формы правки ростера переехали на `/admin/roster/*`, поэтому граница
«читают/пишут» видна прямо в адресе, а из `needsAdmin()` ушло правило про `/edit`.

**Почему не отдельный репозиторий.** Публичная часть читает ровно то, что пишет внутренняя. Два
репозитория означали бы либо общую БД (тогда это не разделение), либо API-контракт между своими же
страницами; плюс `opendota.ts`, `standings.ts`, блоки постгейма и 58 МБ вендоренных иконок уехали бы
в копию, которая разойдётся за месяц.

**Что всплыло по дороге:** витрины ростера писали в БД — `CreateForm` стоял прямо на страницах, которые
стали публичными, а рядом торчала операторская диагностика (счётчики «без account_id», подписи
«нет: …», служебный `slug`). Появился `src/lib/admin-session.ts` — `isAdmin()` для серверных
компонентов, вынесенный отдельно от `auth.ts` намеренно: `auth.ts` импортирует `src/proxy.ts`,
а `next/headers` туда тянуть нельзя. **При добавлении новых полей на витрины проверять: это факт
о лиге или состояние наших данных?** Второе — под `isAdmin()`.

**Хостинг.** Все публичные страницы кроме постгейма — `force-dynamic` из sqlite, статикой не обойтись:
нужен живой Node на VPS (обвязка — `DEPLOY.md`). Статический экспорт таблицы
(`scripts/build-standings-site.ts`) не выбрасываем — это запасной путь, единственный работающий
вообще без сервера.

### Решение: лендинг на `/` (28.07.2026)

`src/app/(public)/page.tsx` — первый экран (кто мы, две кнопки), полоса цифр и три карточки разделов,
повторяющие верхнюю навигацию. Цифры (команды, игроки, группы, сыгранные серии) **считаются из базы**,

## Студия графики (`/studio`)

_Где лежат файлы движка — в [CLAUDE.md](./CLAUDE.md). Здесь — принятые решения._

Генерация графики к матчам живёт в том же приложении и на тех же данных: команды и игроки — из ростера,
матчи — из `Match`. Отдельного сервиса рендера не заводим.

**Решение: шаблон декларативный** — размер холста + схема полей (`FieldDef`) + React-компонент. Форма мастера
строится из схемы автоматически, поэтому новый шаблон не требует ни новых страниц, ни новых форм. Цена решения —
шаблон ограничен набором типов полей (text/select/team/player/group); расширять их приходится в одном месте.

**Решение: экспорт клиентский** (`modern-screenshot`), а не серверный скриншот. Превью и экспорт — один и тот же
компонент, масштаб снимается на клоне → PNG выходит ровно в размер шаблона. Это даёт инвариант «что вижу — то и
скачал»; ломать его нельзя, иначе расхождение превью и результата придётся ловить глазами.

`/studio/render/[templateId]?p=<base64 payload>` — «голый» рендер без интерфейса: задел под серверный скриншот
(Playwright), когда понадобится рендер по API. Компонент общий с превью, расхождений не будет.

Подложки — экспорт из Figma **без текста и лого команд** (их рисует компонент). Файла нет → градиент-заглушка.
Сохранённые генерации — модель `Render` (payload формы), чтобы переоткрыть прошлый анонс и поправить,
а не собирать заново.

**Решение: пост-гейм скорборд — поле `kind:"match"` (05.08.2026).** Шаблон `postgame-board` (референс: Falcons
vs Tundra) — плотная таблица 10 игроков × колонки (герой, K/D/A, урон, предметы), с перегородками между блоками
команд и колонками. Такое не заполнить руками и не разложить свободными элементами canvas-редактора, поэтому
добавлен новый тип поля `match`: оператор выбирает карту, а весь скорборд разворачивается из неё. Данные и
**предметы** берутся из того же `MatchReport`, что рисует постгейм (`buildScoreboard()` в `src/lib/scoreboard.ts`
поверх `loadMatchReport()` — общий кэш и лимит), лого/цвета команд — из ростера по `radiantTeamId`. Отчёт тяжёлый
и серверный, поэтому в поток `resolvePayload` он не грузится скопом: мастер догружает борд по выбору матча
(`GET /api/studio/match-board`), а «голый» рендер собирает его по `matchId` из payload (`getBoardsForPayload`).
Radiant — верхний блок, Dire — нижний (конвенция Dota и страницы `/match`). Сохранённый `Render` привязывается к
`Match`, поэтому графика видна из архива серий: у каждой карты в `/admin/series` есть кнопка «скорборд», которая
открывает мастер с уже выбранной картой (`/studio/new/postgame-board?match=<id>`).

### Генерация картинок по API (`/studio/generate`)

Второй способ получить картинку — не сборка по данным лиги, а свободная генерация через **OpenAI Images**
(модели `gpt-image-*`). Настройки: модель, промт, размер, качество, количество, режим «использовать как референс».

**Решение: ключ только на сервере.** `OPENAI_API_KEY` живёт в `web/.env` (в `.gitignore`), читает его
единственный роут `POST /api/studio/generate`. Из браузера в OpenAI не ходим — иначе ключ утечёт в бандл.
Поэтому же модуль разделён надвое: `lib/openai-images.ts` (сервер, ключ) и `lib/image-options.ts`
(варианты настроек, безопасно импортировать в клиентский компонент).

**Решение: один роут на два эндпоинта.** Есть референсы → multipart `POST /v1/images/edits` (файлы полем
`image[]`), нет → JSON `POST /v1/images/generations`. Для вызывающего разница только в наличии файлов.
Модели `gpt-image-*` всегда возвращают base64 и **не принимают `response_format`** — его не шлём.

Результаты сохраняются в `public/uploads/generated/` (вне git, чистится вручную). В БД не пишем: это черновой
материал, а не сущность лиги. **Каждая генерация платная** — счёт идёт на аккаунт из ключа; в UI выбрано
дешёвое качество по умолчанию («Авто»), для черновиков есть `gpt-image-1-mini` и «Низкое».

## UNDERBEER 2.0 — шоу-драфт (`/underbeer`, 28.07.2026)

Инструмент эфира: оператор собирает **шоу-команды** из живого ростера драфтом капитанов. Раздел в
служебной части (`(admin)`, за паролем), пункт меню «UNDERBEER 2.0» рядом со Студией.

**Решение: это вывод оператора, а не ростер.** Шоу-команды к `RosterSpot` отношения не имеют — как и
студийная графика, это эфемерный результат, а не источник. Поэтому новая модель `DraftSession` хранит
**всё состояние одной JSON-строкой в `payload`** (как `Render`), а не плодит таблицы команд/составов.
В payload лежат только **id игроков** (`picks`/`captainId`); карточки (ник/фото/mmr/позиция) резолвятся
из ростера при чтении (`src/lib/draft-data.ts` → `draftPool()`). Ушедший из ростера игрок просто выпадает
из состава — драфт живёт один эфир, дублировать снимок всего игрока в БД незачем.

**Решение: сначала отбор участников, потом команды.** Автомат начинается с фазы `roster`: из полного
ростера (поиск по нику/имени, колонки по позициям) оператор отмечает игроков турнира (`participants` в
состоянии), и уже **весь драфт идёт только из них** — пул команд и капитанов фильтруется по участникам.
Старые сессии без `participants` читают весь ростер (обратная совместимость).

**Решение: правила — чистый модуль без БД** (`src/lib/draft.ts`, как `qualification.ts`), поэтому один код
гейтит кнопки на клиенте и мог бы проверяться на сервере. Автомат `roster → config → draft → done`:

- Команд ≥ 2, каждой назначается капитан (капитан занимает первый слот, в драфте не участвует).
- Порядок ходов — **змейка** (1→N, N→1, …): иначе последний капитан всегда собирает объедки.
- В свой ход капитан **либо** берёт 1 игрока из пула, **либо** крадёт 1 из чужого состава
  (кража = действие хода, обычного пика в этот ход уже нет). `currentTurn()` идёт по змейке и пропускает
  уже укомплектованные команды — команда могла добрать состав кражей раньше очереди.
- **Кража честная: у кого украли — добирает вне очереди.** После кражи пострадавшая команда сразу берёт
  одного игрока из пула (`pendingPick` в состоянии, `currentTurn().comp = true`), и только потом змейка
  возобновляется с продвинутого за вором указателя. Так никто не остаётся в меньшинстве посреди драфта.
  Цепной кражи нет: в форс-добор можно только пикать из пула, красть/закреплять нельзя.
- «Закрепить» и «Украсть» — **по разу за весь драфт** на команду. Lock защищает своего игрока от кражи и
  **ход не тратит** (защитное действие); капитана и закреплённых красть нельзя.
- Драфт завершён, когда все команды набрали `targetSize` (капитан в счёт входит).

**Решение: клиент — истина хода, сервер только хранит.** Борд (`_components/draft-board.tsx`) применяет
редьюсеры из `draft.ts` и после каждого действия автосохраняет `PATCH /api/underbeer/[id]` весь payload;
роут лишь проверяет версию формата. Пул перетаскивается (`@dnd-kit/core`) или выбирается кликом,
сегментирован по позиции — **каждая позиция отдельной колонкой** (керри…хард + «без позиции»). **Ошибку
правила показываем строкой, борд не роняем**: редьюсеры бросают на невалидном входе, но кнопки и так
гейтятся предикатами `can*`.

**Решение: автосейв через очередь, а не fetch на каждое действие.** PATCH'и уходят строго по одному, и в
полёте всегда только последнее состояние (`pending`/`flushing` в борде). Иначе на быстрых кликах поздно
прилетевший ранний запрос перезаписывал бы финал — драфт откатывался к более раннему состоянию (поймано при
проверке: сессия «съезжала» обратно в конфиг). Оператор один, конфликтов между людьми нет — очередь решает
ровно переупорядочивание запросов одного клиента.

**Удаление.** Драфты чистятся из списка (`DELETE /api/underbeer/[id]`, кнопка на карточке, оптимистично).
По той же схеме сделано удаление сохранённых генераций студии — `DELETE /api/studio/renders/[id]` и кнопка
в «Истории» (`studio/_components/render-history.tsx`): payload формы это черновик, а не сущность лиги.
Подтверждение — **встроенное (два клика)**, а не `window.confirm()`: нативный диалог подавляется в
webview (панель предпросмотра, десктоп-приложение), и кнопка «молча не работала».

**Решение: оверлей для OBS — отдельная «голая» группа `(bare)`.** Результат драфта отдаётся публично на
`/overlay/underbeer/[id]` (группа `src/app/(bare)/` без навигации и без пароля: у OBS админской куки нет,
а показывается только результат, не операторские кнопки). Операторский борд `/underbeer` при этом закрыт —
префикс добавлен в `needsAdmin()`. Держать оверлей внутри `(admin)` не вышло бы: там бы он унаследовал
`AdminNav` и пароль. Запись (`POST`/`PATCH`/`DELETE /api/underbeer`) закрыта общим правилом «не-GET к `/api`».

## Ростер (`/roster`) — справочник лиги

_Файлы и порядок запуска импорта — в [CLAUDE.md](./CLAUDE.md). Здесь — решения._

**Решение: ростер отделён от студии.** Команды и игроки — единственное место, куда данные **пишут**;
студия и таблица их только читают. Иначе одно и то же название команды разъезжается по трём разделам.

**Решение: `slug` — сквозной ключ.** По нему идёт upsert при импорте и по нему же подбираются файлы лого и фото.
Одно имя связывает гугл-таблицу, БД и картинку — не нужно вести отдельный маппинг.

Роль — строка из списка в `roles.ts` (`carry | mid | offlane | soft-support | hard-support | standin | coach`);
**порядок массива задаёт сортировку состава** везде, поэтому менять его — значит менять вывод во всей графике.

Картинки — локально в `public/uploads/` (в `.gitignore`: это данные лиги, а не исходники).

**Импорт составов берёт xlsx, а не CSV** — ссылки на профили в таблице являются гиперссылками ячеек, в CSV их
попросту нет. Из адресов `dotabuff.com/players/<id>` достаётся `accountId`; ссылка на что-то другое (сайт лиги,
Stratz) → поле пустое. Дивизион берётся из названия вкладки («Команды 1 div»), роль — из колонки «Роль»
(1–5, «Тренер», пусто → замена). Ключи `sheet-to-roster.ts`: `--only <слаги>`, `--div 1`,
`--alias "300$=300-dollars"`, `--dry`.

**Решение: MMR хранится у игрока, у команды — считается (23.07.2026).** `Player.mmr` приходит из колонки «MMR»
той же таблицы сезона. У команды поля нет: `teamMmr()` в `roster-data.ts` берёт **только основу** (позиции 1–5) и
отдаёт среднее и сумму — по той же логике, что и standings, которые тоже не хранятся. Замены и тренер в расчёт не
идут: иначе цифра, по которой команды сравнивают, зависела бы от того, сколько человек вписали в запас.

**Решение: дубль команды — ошибка, а не предупреждение (23.07.2026).** Раньше `sheet-to-roster.ts` только дописывал
команды в `data/roster.json` и никогда ничего не убирал, поэтому команда, сменившая слаг, оставалась в файле навсегда
и рядом с ней появлялась вторая (`300-dollars` + `300`). Теперь таблица — источник истины: при разборе целиком
команда разобранного дивизиона, которой в таблице больше нет, из файла удаляется (при `--only` — нет, там мы про
остальные ничего не знаем). Ручные правки при этом переживают перезалив: непустой `accountId` из файла не затирается
пустой ячейкой таблицы.

Второй рубеж — в `import-roster.ts`: перед записью проверяются три случая (один слаг дважды в файле; одна команда
под разными слагами в файле или в БД; один игрок **действующим** сразу в двух командах), и при любом импорт
**падает целиком**, а не чинит данные на ходу.

### Решение: анкета игрока — те же поля, что в CRM (23.07.2026)

`Player` дополнен `birthday`, `city`, `country` (телеграм был раньше): в лиговой CRM это уже собрано, а графике
нужны возраст и город на плашках. Хранится **у человека, а не у места в составе** — при переходе в другую команду
дата рождения не меняется.

Три решения, чтобы поля не приходилось чистить руками:

- **Ввод прощает формат, база — нет.** `accountIdFromUrl()` принимает ссылку на steam-профиль, Dotabuff, Stratz,
  OpenDota и голое число, а в БД кладёт всегда steam32. steam64 больше 2^53, поэтому вычитание константы Valve —
  только через `BigInt`. Так же `normalizeTelegram()` (хендл без «@» и без `t.me/`) и `parseBirthday()`
  (`21.04.1998` и `1998-04-21`). Одни и те же функции используют форма, API и импорт.
- **`steamcommunity.com/id/<vanity>` не разворачивается.** Имя → steam64 знает только Steam Web API, ключа нет.
  Такую ссылку API отвергает с внятным текстом, а не пишет мусор в `accountId`.
- **Дата — полдень UTC.** Время в дате рождения не значимо, а полночь при выводе в отрицательной таймзоне уехала бы
  на сутки назад. `input[type=date]` при этом читает срез ISO без преобразований.

Дыры в анкете считает `playerGaps()` — один список для счётчика в шапке `/roster/players` и для подписи под ником,
чтобы «12 с неполной анкетой» и подписи не разъезжались.

### Решение: профиль и правка — разные страницы (23.07.2026)

`/roster/players/<id>` — карточка игрока (шапка с аватаркой, команда, анкета, сокомандники, задел под стату),
формы уехали на `/roster/players/<id>/edit`. Раньше страница **была** формой: смотреть на неё как на профиль
не получалось, а под будущую защиту админки всё равно пришлось бы разделять — правка живёт по своему адресу.

Аватарка без фото — **инициалы ника на градиенте в цвет команды** (`_components/avatar.tsx`), а не серый квадрат:
фото сейчас нет ни у кого, и заглушка-прочерк превращала бы любую страницу в решето. По той же причине
«фото» убрано из `playerGaps()` — его отсутствие видно по инициалам, а приписка у всех 95 карточек была бы шумом.

Цвет команды (`Team.color`) — единственный источник акцента на странице: он и в градиенте шапки, и в аватарках,
и в рамке плашки команды. Лого уходит в подложку водяным знаком, чтобы читалось имя, а не картинка.

### Решение: цвет команды выводится из слага (23.07.2026)

`Team.color` заполнен у трёх команд из шестнадцати, а на нём держится вся визуальная разница между
карточками, обложками и аватарками-заглушками. Поэтому `teamAccent()` в `profiles.ts`: поле из ростера —
истина, а без него тон берётся из хэша **слага** (насыщенность и светлота фиксированы, чтобы на тёмной теме
ничего не выжигало). Цвет у команды всегда один и тот же и не зависит от страницы — при условии, что везде
считается от слага, а не от названия, поэтому `slug` добавлен даже в узкую выборку `listPlayers()`.

Возвращается **hex**, а не `hsl()`: в разметке к цвету дописывают альфу суффиксом (`${accent}66`), с `hsl()`
так нельзя.

### Решение: страница команды — обложка, а не форма (23.07.2026)

Как и у игрока: `/roster/teams/<id>` — витрина, правка на `/roster/teams/<id>/edit`. Шапка — обложка
из командного фото (`Team.photo`), лого наезжает на неё снизу, wordmark ложится в правый нижний угол.
Фото нет ни у кого, поэтому обложка **генерится** (`_components/team-cover.tsx`): два цветных пятна в акцент
команды, диагональная штриховка, размытое лого как подсветка и огромный полупрозрачный тег. Просто градиент
на пустом месте читался как недогрузившаяся картинка — «полоска»; текстура и тег дают силуэт, который у каждой
команды свой. Появится `Team.photo` — он займёт то же место, вёрстку менять не придётся.

Заголовок под обложкой обязан быть `relative`: подложки обложки позиционированные, а позиционированные
элементы рисуются поверх обычного потока — без этого имя команды пропадало под нижней растушёвкой.

Участие в дивизионе — отдельным блоком: группа, место, В — П, очки, зона выхода и переходы в «Таблицу»,
«Групповую стадию» и «Плей-офф». Цифры берутся из `getStandings()`, а не считаются заново: у таблицы лиги и у
карточки команды должен быть один источник, иначе они разойдутся после первой же правки счёта в сетке.

**Акцент команды и цвет зоны — разные вещи.** Зона («Верхняя сетка» / «Нижняя» / «Вылет») красится только
классами из `QUALIFICATION` (`qualification.ts`), одинаковыми во всех разделах: когда её рисовали цветом
команды, смена цвета в ростере меняла и смысл подписи — зелёный «вылет» читался как проход дальше.

### Решение: список команд — раскрывающиеся карточки (23.07.2026)

`/roster/teams` — не плитка ссылок, а карточки с составом внутри (по образцу Liquipedia): лого, название,
средний MMR основы, вкладки «Основа» / «Штаб» (замены и тренер), игроки кликабельны напрямую. Чтобы посмотреть
пятёрку, больше не нужно заходить в команду и возвращаться.

Разделение на вкладки — то же правило, что и в расчёте MMR: основа — позиции 1–5, остальное штаб. Один критерий
(`rolePosition() !== null`) и там, и там, иначе «средний MMR по основе» и вкладка «Основа» показывали бы разные
множества людей. Страна рисуется **кодом** (`BY`, `RU`), а не флагом-эмодзи: Windows рисует флаги парой букв,
и один и тот же ростер выглядел бы по-разному в разных браузерах.

Данные даёт `listTeamRosters()` — отдельная выборка от `listTeams()`: составы нужны только этому списку.

**Решение: CRM переезжает к нам, а не синхронизируется (23.07.2026).** Внешняя база игроков — источник для
**однократного** импорта (`scripts/import-crm.ts`), дальше анкеты живут в ростере. Постоянная синхронизация
завела бы второго владельца данных, а правило проекта — «ростер единственный, куда пишут».

Как устроен импорт: колонки узнаются по подстрокам в шапке (ник / имя / телеграм / дата рождения / город /
страна / account_id / ссылка), потому что выгрузки называют их по-разному. Сведение с базой — по `accountId`,
иначе по слагу ника, иначе по нику без регистра. **Новых игроков не заводит** (в CRM вся лига за все сезоны,
в базе — Division 1) и **не затирает заполненное** без `--force`: в базе данные свежее. Непонятые значения не
пишутся молча, а печатаются списком «разобрать руками».

### Решение: состав — отдельная сущность (23.07.2026)

Было: у `Player` одна команда (`teamId`), а роль и капитанство лежали на карточке игрока. Один человек при этом
может стоять в двух составах — `Chervyak` действующий саппорт в Cruiser Aurora Team и замена в MOLOKO, — и такой
игрок молча уезжал в команду, которая импортировалась последней.

Стало: **`RosterSpot` (player ↔ team + роль + капитанство)**. Роль принадлежит месту, а не человеку: в одной
команде он саппорт, в другой — замена. `Player.teamId`, `Player.role` и `Player.isCaptain` удалены, чтобы не
осталось второго источника истины; миграция `20260723010000_roster_spots` переносит уже залитые составы.

Инвариант: **действующим (поз. 1–5) можно быть только в одной команде одного дивизиона**, заменой и тренером —
где угодно. Внутри дивизиона человек сыграет за одну команду, иначе стата и составы разъедутся; но D1 и D2 —
раздельные турниры, и игрок нередко заявлен и там, и там (пример — тройка ядра `300$` в D1 = ядро `U.S.Burgers`
в D2). Поэтому проверка сравнивает дивизион (`Team.group`), а не просто команду. sqlite не умеет частичные
уникальные индексы, поэтому правило живёт в коде — `spotConflict()` в `src/lib/roster-spots.ts`, один источник
и для импорта из таблицы, и для API (`/api/roster/spots`), чтобы оно не разъехалось между «залили скриптом»
и «поправили руками».

Импорт чистит за собой: место, которого больше нет в таблице, удаляется, а карточка игрока остаётся в базе — со
статой, фото и `account_id`. Дивизион пока берётся у команды; **сезона в модели нет** — появится, когда
понадобится история составов между сезонами.

## Групповая стадия

Отдельный этап, отыгранный до плей-офф. Источник — вкладка «GS» таблицы сезона, скрипт
`scripts/import-group-stage.ts --sheet <id> --div 1`. Модели: `GroupEntry` (строка команды в группе)
и `Series` со `stage="group"` (личная встреча, счёт серии). Своя вкладка — `/standings/<div>/groups`.

**Два дивизиона (28.07.2026).** Раздел таблиц division-aware: маршруты `/standings/[div]` (`d1`/`d2` →
`Division 1`/`Division 2`), голый `/standings` редиректит на `d1`. Справочник — `src/lib/divisions.ts` (slug ↔
имя ↔ подпись), он же питает две вкладки навигации «LOST D1»/«LOST D2» и под-вкладки дивизионов на `/roster/teams`.
`getStandings(division)` и `getGroupStage(division)` фильтруют по дивизиону; иначе группы A/B двух дивизионов
слились бы в один блок. Импорт GS ищет команду **сначала в своём дивизионе** — одноимённые «ReMix» в D1 и D2
иначе схлопнулись бы в одну; расхождения названий между вкладками «Команды» и «GS» разводит `--alias`
(например `Looking For a Guilty Prime=pasechniki`).

**Решение: единственный источник — сетка встреч (23.07.2026).** И/В/П/О и в группе, и в таблице лиги считаются
из `Series`, поэтому правка встречи двигает обе таблицы сразу — синхронизация выходит сама, копировать
данные между ними не нужно. `GroupEntry` остаётся, но только как **снимок таблицы сезона для сверки**: место в
группе (его из сетки не вывести) и исходные числа, которые показываются в скобках, если расчёт с ними разошёлся.

`getStandings()` складывает три слагаемых: встречи (`Series` любой стадии), одиночные матчи **без серии**
(`Match` с пустым `seriesId` — всё, что завели мимо архива) и ручные начисления (`PointsEntry`). Карты серии
намеренно пропускаются: они уже посчитаны в самой серии, иначе один Bo3 дал бы четыре сыгранных вместо одного.
Таблица делится **по группам**: команды из разных групп между собой не играли, и складывать их очки в один ряд
нечестно.

**Порядок в группе берётся из таблицы сезона, а не из расчёта.** При равенстве очков и побед (morbus mentis и
Eclipse Gaming — обе 4-3 и 12 очков) порядок задавал организатор, и по цифрам его не восстановить. Поэтому
`GroupEntry.place` главнее сортировки — иначе команда уезжает в чужую зону выхода.

**Зоны выхода: 1–4 — верхняя сетка, 5–6 — нижняя, два последних вылетают.** Правила и цвета — в
`src/lib/qualification.ts`, **без обращений к БД**: их использует и клиентская сетка групп. Та же развилка, что
у `openai-images.ts` (сервер) и `image-options.ts` (данные) — `group-stage.ts` тянет Prisma и на клиент не идёт.

**Решение: плей-офф ждёт конца группы, признак автоматический (23.08.2026).** Раньше сетка брала посев
из текущих позиций таблицы, и участники плей-офф менялись после каждой сыгранной встречи. Теперь
`getQualified()` отдаёт зоны только когда стадия завершена, а до этого сетка стоит с заглушками
(«A1», «Победитель ЧФ-1»). Завершённость **не переключается руками** — `groupStageDone()`
(`group-stage.ts`) проверяет, что у всех ожидаемых по жеребьёвке встреч есть результат: ожидаемое —
круговая n·(n−1)/2 по числу команд в группе, «есть результат» — неравный счёт (так же, как решённость
серии в плей-офф, включая техпоражения). Обратная сторона правила: незаведённая встреча для нас не
существует, поэтому обе страницы показывают «сыграно X из Y встреч» — на групповой стадии подписью
у заголовка, в плей-офф плашкой, объясняющей пустую сетку.

**Тег команды заполнен всегда:** `teamTag()` в `profiles.ts` возвращает свой тег из ростера, а если его нет —
выводит из названия (первое слово, до 5 знаков, в верхнем регистре). Заведут тег в ростере — он перекроет.

**Очки за серию Bo3: 2:0 — 3, 2:1 — 2, 1:2 — 1, 0:2 — 0.** Формула в таблице сезона не записана; выведена из
кросс-таблицы и сошлась на всех командах группы A первого дивизиона. Живёт в `seriesPoints()` (`group-stage.ts`).

**Кросс-таблица в источнике не подписана** — в шапке логотипы-картинки, ячейки заголовков пустые. Порядок команд
в матрице восстанавливается расчётом: по каждой строке считаются В-П-очки и сопоставляются с таблицей выше.
Где отпечаток уникален — подпись точная; где нет (в каждой группе нашлась пара команд с одинаковыми В-П-очки) —
встречи помечаются `guessed` и подсвечиваются в UI, чтобы их поправили руками. Правка через
`PATCH /api/series/[id]` снимает пометку: ручной ввод считается подтверждением.

## Архив серий и статистика турнира (29.07.2026)

Вопрос был «где собирать общую стату — кто больше всех убил, нанёс урона — в разрезах турнира». Ответ:
**в тех же строках, из которых уже считается таблица.**

**Решение: `GroupSeries` расширена до `Series`, а не заведена вторая модель.** Групповая встреча и встреча
плей-офф отличаются только полем `stage`: и там, и там пара команд, счёт Bo3 и очки по одной формуле. Вторая
модель означала бы два источника правды для одного и того же вопроса «кто с кем и с каким счётом сыграл» —
и таблица с архивом разъехались бы на первой же правке. Миграция — переименование таблицы, а не drop+create:
в `GroupSeries` лежала вручную выверенная сетка группы.

**Карта серии — это `Match`.** У серии до трёх карт (`seriesId` + `gameNumber`, уникальны в паре).
`openDotaMatchId` глобально уникален, поэтому одна карта физически не может лежать в двух сериях.
Длительность карты (`durationSec`) хранится у матча — без неё «урон в минуту» превращается в рейтинг
длинных игр.

**Стороны определяются по составам, а не вводятся руками.** `detectSides()` считает, чьих игроков больше
в пятёрке (минимум двое — иначе один случайно совпавший `account_id` перевернул бы серию). Та же логика,
что распознаёт названия команд на странице постгейма.

**Игрока опознаём по `account_id`, откуда бы он ни взялся.** Анкеты приходят из CRM неровно: у части
людей заполнено само поле, у части — только ссылка на Dotabuff/Stratz/Steam. `playerAccountId()`
(`src/lib/profiles.ts`) сводит это к одному значению, и им пользуются и синк, и распознавание команд.
Матчить по голой колонке `accountId` значило бы терять статистику половины ростера на ровном месте.
Именной адрес `steamcommunity.com/id/<vanity>` в число не превращается ничем, кроме Steam Web API —
для него есть `scripts/resolve-vanity.ts` (разовый прогон, результат пишется в БД навсегда).

**Ники везде — из ростера, а не из клиента Доты.** В игре человек может называться как угодно и менять
имя между матчами; в лиге у него одно имя. Постгейм подменяет ник на ростерный, когда игрок узнан по
`account_id` (неузнанный — стендин, чужой матч — остаётся под своим именем из OpenDota), а страница
встречи и рейтинги и так читают ник из `Player`. Для этого `/api/roster/teams` отдаёт состав как
`lineup: {accountId, nickname}[]`, а не голый список id.

**Рейтинги считаются, а не хранятся** (`src/lib/leaders.ts`). Любой хранимый итог пришлось бы пересчитывать
после каждой привязки карты и каждого допарса реплея — и он бы молча разъезжался. Строк тут сотни: суммировать
в памяти дешевле, чем поддерживать кэш. Разрез задаётся фильтром `Series` (дивизион / стадия / группа), а
карта **без серии в рейтинги не попадает вообще** — иначе в «плей-офф» протекли бы товарищеские матчи.

**Команды считаются по множеству карт, а не сложением строк.** Пять игроков дают пять строк на карту; сложи
их «сыграно» — и средние за карту окажутся впятеро занижены.

**Разрез — это `stage` + одно из двух полей.** Группа живёт в `Series.group`, половина сетки — в
`Series.bracket` (`upper`/`lower`/`grand`). Сетку держим отдельной колонкой, а не выводим из названия
раунда: по ней фильтруют архив и статистику, и разбирать ради этого свободный текст — способ однажды
потерять серию из-за опечатки. Значение проставляется само по выбранному раунду (`bracketOfRound()`),
поэтому в форме его не спрашивают. Список разрезов для интерфейса — `CUTS` в `src/lib/stages.ts`,
один на обе страницы.

**Решение: у встречи стабильный ключ в адресе (29.07.2026).** `id` автоинкрементный, а `db:import`
пересоздаёт производные строки — после каждого переноса данных встреча получала новый id, и ссылка
`/series/12`, отданная наружу, вела в никуда. Поэтому у `Series` есть `slug` вида
`guzliki-vs-from-paris` (по слагам команд — сквозному ключу проекта; повторная встреча той же пары
получает числовой хвост). Слаг считается один раз при создании, едет в снимке и переживает импорт.
Числовой id роут тоже принимает — ради ссылок, отданных до его появления.

**Страница встречи `/series/<slug>` повторяет форму разбора серии на Dotabuff:** шапка со счётом, ниже
карты, у каждой — оба состава с героем, уровнем и K/D/A. Детали карты (драфт, предметы, график золота)
не дублируются — за ними ведёт ссылка на `/match/<id>`, где всё это уже нарисовано. Счёт карты по
убийствам и первый пик хранятся у `Match`, а не считаются из `MatchStat`: там только игроки лиги, и
карта со стендином показала бы заниженные убийства.

Где что: `/admin/series` — завести встречу, подвесить/отцепить/перечитать карты и удалить встречу
(единственный вход в архив), `/standings/<div>/stats` — рейтинги; фильтры живут в query, поэтому любой
разрез можно кинуть ссылкой. `POST /api/series/[id]/games` читает стату сразу при привязке: отдельной
кнопки «синхронизировать» нет намеренно — карта без статы в архиве бесполезна. Отдельная кнопка
«перечитать» у карты всё же есть, но для другого случая: непарсенный матч через время обрастает
вардами и таймингами, а привязка была раньше.

### Решение: архив в два уровня и явные правила перечитывания карты (23.08.2026)

Вход в `/admin/series` — блоки турниров (дивизионы, сколько встреч, сколько карт, сколько встреч без
карт). Техническая часть — заведение встречи, привязка/отцепка карт, перечитывание — живёт на уровень
глубже, в `/admin/series/<слаг турнира>`: оператор работает с одним сезоном за раз, а прежняя страница
вываливала все сезоны разом. Карты у встречи свёрнуты (`details`): в свёрнутом виде счёт и число карт.

**Правила перечитывания карты собраны в `resyncGame()`** (`src/lib/series.ts`), а не размазаны по
кнопке и роуту. Перечитывают, когда отчёт дозрел (непарсенный матч позже обрастает вардами и
таймингами), когда стата легла неполной или когда поправили ростер. Перезаписывается всё, что
выведено из отчёта: `MatchStat` опознанных игроков, `Ward` карты (сносятся и пишутся заново), у матча
— длительность, старт, счёт сторон, первый пик, стороны и победитель; **счёт серии пересчитывается**
(раньше «перечитать» этого не делало, и смена победителя карты не доезжала до таблицы). Строки статы
игроков, которых в свежем отчёте нет, удаляются — кроме случая, когда отчёт не опознал вообще никого:
тогда не трогаем ничего, иначе одно неудачное перечитывание стёрло бы стату карты. Остаются нетронутыми
привязка, дата серии, начисленные баллы и собранная графика — это решения оператора, а не производные отчёта.

**Источник id матчей — поля у турнира** (`Tournament.matchesUrl` и `Tournament.leagueId`), а не у
встречи: список матчей общий на сезон. Ссылка — «куда смотреть глазами», `league_id` — тикет лиги в
Dota 2, единственный ключ, которым матчи сезона связаны программно.

**Разведка источников (23.08.2026), на живой лиге LOST S2 div#1 (`league_id` 19700).** OpenDota
отдаёт **отдельный** матч — на этом стоит весь наш разбор, — но списка матчей лиги у неё для нас нет:
лига помечена `tier: "excluded"`, в `/leagues/<id>/matches` и в explorer попадают только турниры с
тиром. Stratz знает матч и его `leagueId`, но саму лигу отдаёт как `null`. Liquipedia страницы лиги
нашего размера не имеет, а заводить её руками дороже, чем вводить id. Dotabuff — скрейпинг под
Cloudflare и против их правил. Остаётся **Steam Web API** (`IDOTA2Match_570/GetMatchHistory`): он
видит матчи по тикету лиги независимо от тира, но требует `STEAM_API_KEY` (бесплатный, в `.env` его
сейчас нет — без ключа список не приходит, и архив честно пишет об этом оператору).

**Проверка лиги при привязке карты работает уже без ключа.** Отчёт матча отдаёт `leagueId`, и если у
турнира он задан, `attachGame` отбивает чужой матч до записи — самая частая ошибка оператора это
опечатка в id, которая тянет в архив чужую стату. `leagueId === null` (Steam-фолбэк, отчёт из старого
кэша) значит «не знаем» и не блокирует; публичный матч приезжает с нулём и отбивается. Поле в отчёте
новое, поэтому версия кэша поднята до 3 — иначе старые файлы отдавали бы `null` и проверка молчала.

## Инструмент: импорт матча (каркас)

Отчёт: `/match` (ввод id) → `/match/[id]` (клиент) → `GET /api/opendota/match/[id]` → `fetchMatchReport`
(`src/lib/opendota.ts`). БД не трогает — всё из источника. Сервис публичный и принимает **любой** матч
Dota 2, не только матчи лиги (решено с заказчиком).

Данные (реальные из OpenDota): шапка (время, счёт, победа), **пики/баны с очередью**, **график преимущества по золоту** (по минутам), aegis на команду. По игроку: герой, уровень, K/D/A, LH/денаи, GPM/XPM, ценность (net worth), урон по героям/строениям, хилл, **предметы** (+нейтралка, бэкпек), **порядок способностей**, **тайминги покупок**, постоянные баффы (стаки).

Имена команд подставляются из OpenDota, но поле **редактируемое** (кастомим под LOST).
Резолв id→имя через кэш констант OpenDota (`item_ids`/`items`, `ability_ids`/`abilities`, `permanent_buffs`). Детальные поля есть только у **распарсенных** матчей (`version != null`) — иначе часть пуста (есть предупреждение в UI).

### Решение: у отчёта постоянная ссылка, состояние — в адресе (28.07.2026)

Раньше постгейм был одностраничным приложением на `/`: id матча и всё остальное жили в `useState`,
поделиться разобранным матчем было нельзя. Теперь **`/match`** — форма ввода, **`/match/[id]`** — сам
отчёт, а состояние переехало в query: `?src=steam` (OpenDota — умолчание, в адрес не пишется),
`?tab=extra|export`, `?radiant=`/`?dire=` (ручные названия сторон). Ссылка воспроизводит ровно то,
что видел отправитель, вплоть до переименованных под LOST команд.

Правки адреса идут `router.replace`: «назад» из отчёта должно вести на форму, а не на прошлую вкладку.
Названия команд коммитятся в URL по уходу из поля, а не на каждую букву — иначе история браузера
засоряется, а каждый символ стоит перерисовки маршрута. Загрузка помечена ключом `id|src` вместо
флага «грузится»: поздний ответ на прошлый запрос не совпадёт меткой и не перезапишет открытый матч.
Форма принимает не только голый id — из ввода берётся первое число от шести знаков, поэтому ссылка
на Dotabuff/OpenDota тоже работает.

Полка выгрузок (`match-archive.tsx`) осталась **операторской**: она видна только вошедшему, как и
кнопка «В архив» в экспорте. Скачивание PNG публично — это продукт; архив — черновики оператора.

### Решение: кэш отчётов и лимит по IP (28.07.2026)

Как только разбор матча стал публичным сервисом, он упёрся в чужой лимит: у OpenDota порядка
**60 запросов в минуту на всех**. Публичный трафик выел бы его сразу и заодно уронил внутренний разбор.

Порядок описан один раз в `src/lib/match-api.ts` (оба роута отчёта — три строки каждый):
**проверить id → отдать с полки → занять слот лимита → сходить наружу → положить на полку.**

- **Кэш** (`src/lib/match-cache.ts`) — файл на матч в `web/.cache/matches` (~45 КБ, в `.gitignore`).
  Спасает природа данных: **отчёт по завершённому матчу неизменен**, поэтому распарсенный отчёт
  OpenDota и любой завершённый матч из Steam кэшируются навсегда, без инвалидации. Незавершённый и
  нераспарсенный — на час: реплей ещё допарсится, и график появится. Файлы, а не память процесса —
  кэш должен переживать деплой, иначе каждая выкладка набивает лимит заново. В БД ему не место: она
  коммитится в репозиторий, а кэш это вывод. Формат помечен `VERSION` — поменялась форма
  `MatchReport`, поднимаем номер, старые записи молча игнорируются.
- **Лимит** (`src/lib/rate-limit.ts`) — 10 запросов наружу в минуту с IP, окно в памяти процесса
  (приложение одно и на одной машине, Redis ради этого не заводим). Расходуют его **только промахи
  кэша**: популярная ссылка на отчёт открывается у всех и всегда. Сверху `429` с `Retry-After`.
  IP берётся из `x-forwarded-for` (его ставит Caddy) — заголовок подделывается, поэтому годится
  ровно для лимита, а не для доступа.
- **`frame-ancestors`** — `next.config.ts` из переменной `FRAME_ANCESTORS` (домены через пробел),
  по умолчанию `'self'`. Без заголовка встраивание в лендинг браузер блокирует. `X-Frame-Options`
  намеренно не ставим: он умеет ровно один домен и перебил бы список. `next start` читает конфиг
  в рантайме — поэтому `next.config.ts` копируется в рантайм-стадию `Dockerfile`.

### Решение: справочники Доты вендорятся, из сети берётся только матч (25.07.2026)

Раньше на холодный процесс уходило **8 запросов** к OpenDota: сам матч плюс 7 справочников
(`heroes`, `item_ids`, `items`, `ability_ids`, `abilities`, `hero_abilities`, `permanent_buffs`).
Справочники меняются раз в патч, а тянулись по сети постоянно — и когда у OpenDota лёг бэкенд
(Cloudflare 522 на **всех** путях, включая `/api/status`), отчёт не собирался вообще.

Теперь справочники лежат в репозитории: `src/lib/dota-constants.json`, собирается
`node scripts/build-dota-constants.mjs` из **odota/dotaconstants** на GitHub — того самого репозитория,
содержимое которого OpenDota и отдаёт по `/api/constants/*`. Файл слимится при сборке (из `items`/`abilities`
только `dname`, из `hero_abilities` только таланты): 2.8 МБ исходников → ~440 КБ. Перезапускать при смене патча,
как и `build-talents.mjs`.

Сетевой путь из `opendota.ts` **не удалён** — если файл почему-то пуст, `heroInfo()`/`constants()` уходят в API,
как раньше. Из сети теперь обязателен только `/api/matches/{id}`: его локальным не сделать.
Там же — ретраи транзиентных ответов (429, 5xx/52x) с нарастающей паузой и человекочитаемые ошибки,
которые API-роут отдаёт в UI как есть.

### Решение: у матча два источника, выбор кнопкой (25.07.2026)

Две кнопки на форме `/match` и переключатель в шапке отчёта — «OpenDota» и «Steam»
(`GET /api/opendota/match/[id]` и `/api/steam/match/[id]`; выбор живёт в адресе как `?src=`).
OpenDota остаётся основной: только у неё есть график преимущества, тайминги покупок, лог событий и ники.
Steam (`IDOTA2Match_570/GetMatchDetails`, `src/lib/steam-match.ts`) — первоисточник Valve, нужен ровно на случай
их аварии. Ключ бесплатный, лежит в `web/.env` как `STEAM_API_KEY`; без ключа кнопка отвечает понятной ошибкой.

Дублирования сборки нет: ответ Valve — это то, из чего OpenDota делает свой, поэтому Steam-адаптер приводит
ответ к `RawMatch` и зовёт общий `buildMatchReport()` (вынесен из `fetchMatchReport` без изменения логики).
Что у Valve беднее: нет графика золота/опыта, `purchase_log`, лога событий (первая кровь, рошан, курьеры, аегис),
перманентных баффов (Аганим/шард видны только предметом), ников (отдаётся лишь `account_id` — команда лиги
всё равно распознаётся) и `lane_role` (позиции считаются по фарму). Матч из Steam помечен в шапке отчёта
бейджем «источник: Steam», чтобы пустые блоки не выглядели багом.

STRATZ как третий источник не делался: требует токен и второй маппер, а закрывает те же дыры.

### Решение: архив хранит выгруженные картинки, а не шапки матчей (25.07.2026)

Архив — полка готовых PNG в `public/uploads/postgame/` (`src/lib/postgame-archive.ts`, API
`/api/postgame/archive`, полка — `src/app/_components/match-archive.tsx`). Кладёт туда картинку
кнопка **«В архив»** на вкладке экспорта, рядом со «Скачать PNG»: снимок берётся тот же самый,
второй раз ничего не пересобирается.

**Чем это заменило прежний вариант.** Сначала архив держал в `localStorage` только шапку матча и по
клику перезапрашивал отчёт из источника — то есть хранил *повод* собрать картинку заново. Это ломается
ровно там, где архив и нужен: OpenDota лежит, матч из выдачи ушёл, патч Доты переименовал предметы —
и повторный разбор даёт уже не ту картинку, которая ушла в работу. Поэтому храним результат.
Сохранение — отдельной кнопкой, а не побочным эффектом скачивания: на полку попадает то, что оператор
счёл финальным, черновые прогоны её не засоряют.

Раскладка: `<matchId>-summary.png`, `<matchId>-players.png` и подпись `<matchId>.json` рядом. **Истина о
содержимом архива — файлы на диске**, JSON хранит только подпись (команды, счёт, источник, время выгрузки):
пропал `.png` — запись сама исчезает с полки, рассинхрон чинить нечем. Id матча перед подстановкой в имя
файла проверяется как «только цифры» — иначе это путь наружу.

В БД записи нет и модели под неё не заводили: это по-прежнему удобство оператора, а не данные лиги.
В `.gitignore` папка ушла по той же причине, что и `uploads/generated/` — два PNG по 2–3 МБ на матч,
за сезон это сотни мегабайт в истории, откуда их уже не вычистить.

Названия в подписи — финальные, **с** ручным переименованием сторон: на картинке нарисованы именно они,
а архив теперь описывает картинку, а не матч. Id и источник всё же помним — кнопка «↻» на карточке
перезапрашивает матч, если картинку нужно пересобрать.

### Решение: постгейм экспортится двумя картинками 1920×1080 (24.07.2026)

Вкладка «Экспорт PNG» отдаёт не одну широкую картинку, а **две отдельные** 1920×1080: «сводка матча»
(шапка, герои, баны, карта строений, график преимущества, события) и «статистика игроков» (две колонки
карточек). Причина — формат постов: 16:9 ложится в ленту и сторис как есть, а прежние 2560×920 приходилось
резать руками.

Обе рисуются на **общей подложке** `public/templates/postgame/bg.png` — та же конвенция, что у шаблонов
студии (`<templateId>/bg.png`), файла нет → фирменный градиент. Из подложки следует главное ограничение:
её низ занят партнёрской плашкой (лого лиги, спонсоры), поэтому в холсте зарезервирована **безопасная зона
снизу** (`SAFE_BOTTOM`, 76px в координатах холста ≈ 150px на 1920×1080). Контент туда не заходит, и
затемнение рабочей зоны гасится градиентом в последних 48px, чтобы на границе не было ступеньки.

Рендер идёт в 960×540, PNG снимается со `scale: 2` → ровно 1920×1080. Так сохраняется инвариант
«что вижу — то и скачал» (превью и экспорт — один компонент), а внутренние размеры остаются в том же
порядке, что на странице. Размеры блоков подогнаны под замеры в браузере, а не на глаз: остаток высоты
после шапки/героев/банов — ~249px, из него живут карта (175px) и график (729×222); карточка игрока
ужата до ~79px. Менять шрифты и отступы здесь нужно с проверкой, что контент не наезжает на плашку.

### Решение: защита служебной части — по роли, без пароля (12.08.2026, было: один пароль 25.07.2026)

Сначала админ был один и вход — единый пароль `ADMIN_PASSWORD` (подписанная HMAC-кука, ключ из самого
пароля). Когда появились роли (решение выше), пароль стал лишней второй дверью: **его убрали совсем.**
Единственный вход — через Google в кабинете (`/me`), а «пускать или нет» решает роль сессии
(owner/admin — `sessionIsAdmin` из `player-auth.ts`). Развилка по-прежнему в `src/proxy.ts`: в Next 16
это **`proxy.ts`** (бывший `middleware.ts`, переименован в v16) на Node-рантайме — поэтому `node:crypto`
внутри player-auth в нём работает. `src/lib/auth.ts` усох до одной карты `needsAdmin()` — что вообще
требует прав; кто их имеет — вопрос роли, не этого файла. Вкладку «Админ» в шапке рисуем только когда
`isAdmin()` (роль из той же куки) — посетитель её не видит вовсе.

**Что закрыто — правило «закрыто всё, что пишет»** (`needsAdmin()`, одно место правды):

- любой не-GET запрос к `/api/*` — вся запись, включая платный `/api/studio/generate`;
- страницы, которые существуют только чтобы менять: `/studio*`, `/admin*`. Прежнее правило
  «всё, что кончается на `/edit`» выброшено — формы правки переехали под `/admin/roster/*`,
  и хватает префикса (см. «Решение: продукт и служебная часть» ниже);
- единственное исключение из «читать можно всем» — `GET /api/postgame/archive`: полка выгрузок
  это черновики оператора, а не факт о лиге, и прятать её в интерфейсе, раздавая списком
  через API, было бы половиной работы.

Публичная часть остаётся открытой — таблица, ростер и разбор матча: их и планировали встраивать
в лендинг на Tilda. API отвечает `401 JSON`, а не редиректом на HTML, иначе `fetch()` из форм получал
бы страницу вместо внятной ошибки; страницы уводятся в кабинет `/me` (единственный вход).

### Решение: вход игроков через Google (12.08.2026)

Пароль-админка закрывает **служебную часть** — там роль одна на всех. Игроку же нужна личность:
войти под собой, привязать свой профиль в ростере, дальше — свой кабинет. Заводить логины-пароли
и хранить хеши ради этого не хочется, а личность и так есть у Google — берём её через OAuth.

**Почему руками, а не NextAuth.** Авторизация в проекте уже самодельная (см. решение об админке
выше): HMAC-кука, ноль внешних зависимостей. Вход игрока — та же механика, только «кто ты» отвечает
Google. Ручной флоу (`src/lib/google-oauth.ts`) — три шага: увести на согласие Google с одноразовым
`state` в куке (CSRF), поймать код в `GET /api/auth/google/callback`, обменять его на `id_token` и
распаковать (подпись не проверяем — токен пришёл прямо из token-endpoint по TLS в ответ на наш запрос
с `client_secret`, канал доверенный). Ключи — `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` в `web/.env`.

**Аккаунт отдельно от игрока.** Модель `UserAccount` (ключ — `googleSub`, стабильный id гугл-аккаунта):
профиль игрока есть у всех в ростере, а аккаунт появляется только у вошедшего. Связь `UserAccount ↔ Player`
хранится **двумя** полями: `playerId` — подтверждённая привязка (уникальна: один профиль на один аккаунт),
`claimId` — заявка, ждущая подтверждения. Две связи, а не одна, чтобы непроверенная заявка не считалась
привязкой. Сессия игрока — своя кука `lost_player` с отдельным секретом (`AUTH_SECRET`, фолбэк —
`GOOGLE_CLIENT_SECRET`), устроена как админская: `<id аккаунта>.<срок>.<подпись>`, профиль тянется из БД.

**Флоу онбординга (`/me`, публичная страница).** После первого входа развилка ровно по задаче: *новый
игрок* вводит ник → сразу создаётся `Player` и привязывается (`createProfileFor`, slug уникализируется);
*уже в ростере* находит себя в списке → подаётся заявка (`claimExisting`), которую оператор подтверждает
на `/admin/claims` (`claimId` → `playerId`). Логика привязки — одно место, `src/lib/account.ts`; сессия —
`src/lib/player-auth.ts`. Публичность `/me` — как у `/admin/login`: страница входа сама закрытой быть не может.

**В снимке БД аккаунты есть** (версия снимка **10**): это реальные данные пользователей, а не производные,
и `db:import`-зеркало не должно их терять. Связи — по `slug` профиля, ключ переноса — `email` (см. ниже).

### Решение: вход по email + паролю рядом с Google (18.08.2026)

Google-входа мало: не у всех игроков он удобен, а классическая пара «почта + пароль» ожидаема. Добавили
её **рядом** с OAuth, не выкидывая его. Ключ аккаунта сместился с `googleSub` на **`email`** (уникален и
есть всегда): один человек ↔ один `UserAccount`, хоть через Google, хоть паролем, хоть оба сразу. Поэтому
`googleSub` стал опциональным, а в снимке аккаунты теперь сортируются/переносятся по `email` (у парольного
аккаунта `googleSub` пуст). Вход через Google, встретив уже заведённый парольный аккаунт с той же почтой,
прицепляет `googleSub` к нему, а не плодит дубль.

**Крипта — в стиле проекта, без новых зависимостей.** Пароль хешируется `scrypt` из `node:crypto`
(`src/lib/password.ts`, формат `salt:hash`, сравнение timing-safe) — как самодельная HMAC-кука сессии.
Подтверждение почты и сброс пароля сначала были сделаны на одноразовых токенах `AuthToken` с письмами
через Resend, но **20.08.2026 почтовый флоу убран целиком** — см. «Решение: воронка регистрации, права
и отказ от писем» ниже.

**Безопасность привязки пароля.** Регистрация НЕ трогает существующий email — иначе, зная чужую почту,
можно было бы подсадить свой пароль в чужой Google-аккаунт (перехват). Задать пароль существующему
аккаунту (в т.ч. тому, что входил только через Google) можно в кабинете `/me/security` — владение
доказано активной сессией. Роуты: `POST`-экшены на `/me` (вход и регистрация).

**Внутренний профиль пользователя.** На `/me` — карточка аккаунта: аватар/инициал, имя, почта (плашка
«подтверждена» — только когда её подтвердил Google), **бейдж роли** (owner/admin/player — цветом), способы
входа (Google/пароль). Дальше — та же развилка онбординга. Ключ окружения: `AUTH_SECRET` (обязателен, если
Google не настроен).

### Решение: роли и владелец (12.08.2026)

Пароль-админка (решение выше) — доступ «всё или ничего» для одного оператора. Когда игроков и
помощников стало больше, понадобилась иерархия: **владелец** раздаёт роли, **админы** принимают
заявки и правят лигу, **игроки** только входят в свой кабинет. Роль — поле `UserAccount.role`
(`owner | admin | player`, по умолчанию `player`).

**Владелец — не роль в БД, а адрес `OWNER_EMAIL`.** Кто вошёл через Google под этой почтой —
получает `owner`, и отнять это из UI нельзя (иначе владелец мог бы случайно разжаловать себя и
запереться снаружи). Эффективная роль (`effectiveRole` в `src/lib/account.ts`) = «owner по почте»
поверх записи в БД; это одно место правды — им пользуются и вход (какую роль вшить в куку), и панель.
Владелец закрепляется в БД при первом входе, чтобы быть видимым в списке как `owner`, а не только в куке.

**Гейт роли в proxy — чистой криптой, без БД.** Роль вшита в подписанную сессионную куку
(`<id>.<role>.<exp>.<sig>` в `player-auth.ts`), поэтому `proxy.ts` решает доступ к служебной части,
не ходя в базу на каждый запрос. Пускает сессия с ролью `owner`/`admin` — единственный путь после
того, как пароль убрали (решение «защита служебной части» ниже). Плата за «крипта вместо БД» —
роль в куке обновляется при следующем входе: понизили админа, а его текущая кука ещё админская до
перевхода/истечения (30 дней). Для узкого круга доверенных это приемлемо; всё, что решает конкретное
действие (раздача ролей и прав, `/admin/staff`), перепроверяется по свежей БД, а не по куке. Крипта-модуль
(`player-auth.ts`) отделён от куки-слоя (`player-session.ts`) — тот тянет `next/headers`, а его в
`proxy.ts` нельзя (та же причина, по которой `auth.ts` отделён от `admin-session.ts`).

### Решение: воронка регистрации, права и отказ от писем (20.08.2026)

Три проблемы разом. Письма при регистрации не доходили, а вход от них зависел (по паролю не пускали до
подтверждения почты). Регистрация сама по себе давала место в лиге — модерации не было. И админ был
«всё или ничего»: любой admin мог и удалять профили, и тратить деньги в студии. План целиком —
[`docs/archive/ACCOUNTS-PLAN.md`](docs/archive/ACCOUNTS-PLAN.md), здесь — принятые решения.

**Почтовый флоу удалён, а не спрятан.** Убраны `mailer.ts`, `auth-tokens.ts`, `app-url.ts`, модель
`AuthToken`, страница `/reset`, роут `/api/auth/verify` и «Забыли пароль» из форм. Причина держать
неработающий флоу «на потом» слабее, чем цена мёртвого кода в гейте входа. Возврат — из git (коммит
этапа 1 в `WORKLOG.md`) плюс ключ `RESEND_API_KEY`. Следствие принято осознанно: **восстановления
пароля нет**; пути обхода — вход через Google той же почтой (ключ аккаунта — `email`, аккаунт тот же),
задание пароля в `/me/security`, в крайнем случае — удаление аккаунта и регистрация заново (`Player`
при удалении аккаунта остаётся). `emailVerified` осталось полем, но перестало быть гейтом: его
поднимает только Google, поэтому оно честно значит «почту подтвердил Google» — и плашка в интерфейсе
показывается лишь когда `true`.

**Регистрация — заявка, а не пропуск.** У `UserAccount` появился `status`: `draft` (вошёл, анкеты нет)
→ `pending` (анкета отправлена, ждёт решения) → `active` (одобрен) либо `rejected` (отказ с причиной,
анкету можно поправить). Дефолт — `draft`, чтобы новый аккаунт (в том числе заведённый
Google-callback'ом) попадал в воронку сам, без «не забыть проставить» в каждом месте создания.
Существующие аккаунты одноразовым `UPDATE` в миграции переведены в `active` — иначе действующие люди
оказались бы заперты. Владелец (`OWNER_EMAIL`) вне воронки: `accountStatus()` возвращает ему `active`
всегда, иначе, зачистив базу, он запер бы сам себя — апрувить его некому.

**Анкета неодобренного живёт в JSON на аккаунте** (`UserAccount.application`), а `Player` создаётся
только при апруве. Публичные витрины (`/roster/players`, статистика, драфт) читают `Player` без
фильтров: заводить его сразу — значит показывать неодобренных в ростере и добавлять флаг
«опубликован» во **все** выборки. Заявка на уже существующего игрока (claim) работает как прежде.

**Анкета и политика площадки** (этап 2). Пока аккаунт в `draft`, кабинет показывает **только** анкету —
иначе в очередь модерации попадали бы пустые аккаунты. Схема анкеты и её проверки — чистый
`src/lib/application.ts` (тип, разбор JSON, валидация, вывод `account_id` из ссылок): по нему рисуется
форма, им же проверяется server-action, из него же на апруве соберётся `Player`. **Ссылки — каждая
своим полем** (Dotabuff / Stratz / Steam): в общем поле «ссылка на профиль» нельзя было понять, что
человек дал и чего не хватает; одна из трёх обязательна — без `account_id` игрок не находится ни в
одном матче. По той же причине поле разнесено и в self-service правке `/me/profile`, а `account_id`
пересчитывается из ссылок, но **не затирается**, если ни одна не разобралась (его мог поставить
оператор или `resolve-vanity`). Согласие с политикой (`/rules`) — обязательное условие отправки, и
проверяется оно в `submitApplication`, а не только чекбоксом: до БД можно дойти мимо формы. Сама
`/rules` — документ в коде, а не данные: отдельная модель ради одной страницы избыточна. Черновик
ответов возвращается в форму из состояния экшена — React после submit сбрасывает неуправляемые поля
к `defaultValue`, и без этого опечатка в одной строке стирала бы всю анкету.

**Решение: одна модерация вместо двух очередей (23.08.2026).** «Регистрации» и «Заявки» жили по
разным адресам под одним правом `accounts.approve`, и оператор проверял то одну страницу, то другую.
Теперь это `/admin/moderation` с вкладками в query (`?tab=links`), число новых показано и на вкладке,
и бейджем на плитке `/admin`; оба старых адреса — постоянные редиректы в `next.config.ts`. Имя
раздела нарочно шире «регистраций»: следующими сюда переедут заявки команд на турнир.

**Модерация регистраций** (этап 3). Очередь `/admin/registrations` — одна на обе ветки воронки, с
пометкой типа: «новая анкета» (в `application` лежит JSON) и «привязка к профилю» (выбран `claimId`).
Апрув новой анкеты **заводит `Player`** (`createPlayerFromApplication`: slug уникализируется от ника,
`account_id` выводится из ссылок), апрув привязки только связывает уже существующий профиль; оба пути
ставят `active`, `reviewedAt`/`reviewedById`. **MMR в форме апрува — поле оператора:** в анкете он со
слов игрока, а в лиге это её собственные данные. Позиция из анкеты в `Player` не переносится вовсе —
роль в составе живёт в `RosterSpot` и появляется вместе с командой. Отказ обязателен с причиной
(`rejectedReason`) — человек видит её в кабинете и правит анкету, отправка возвращает заявку в
`pending`. Право `accounts.approve` проверяется **в самих `approveRegistration`/`rejectRegistration`**,
а не только на странице: до апрува можно дойти из любой точки служебной части. `pendingClaims()`
(старый `/admin/claims`) теперь исключает `pending` — иначе одна заявка висела бы в двух очередях;
за ним остался исходный случай: уже одобренный аккаунт просит привязку. Анкета в читаемом виде —
общий `app/_components/application-summary.tsx`: её одинаково видят оператор в очереди и игрок в
кабинете («что вы отправили»), иначе спорить о заявке было бы не о чем.

**Права — гранулярные и проверяются по БД.** Реестр ключей — чистый `src/lib/permissions.ts`
(`accounts.approve`, `roster.delete`, `series.edit`, `studio`, …), хранение — строка через запятую в
`UserAccount.permissions` (как `Player.tags`: sqlite не умеет массивы, а таблица ради десятка флагов
избыточна). Роль осталась **грубым** гейтом в `proxy.ts` (пускать ли вообще в служебную часть), а
конкретный раздел открывает право: `requirePermission(key)` в `account.ts` читает **БД**, а не куку.
Причина — та же плата за «крипту вместо БД» в сессии: роль в куке обновляется лишь при следующем
входе, а снятое право обязано пропасть сразу. Служебная часть не горячий путь, лишний запрос там
дешевле дырки в доступе. У владельца права все и неотчуждаемо; новый админ получает **ноль** прав —
владелец отмечает нужные.

**Право проверяется трижды, и это не дублирование.** `proxy.ts` — роль (админ ли вообще), страница —
`denyUnlessPermission(key)` (`(admin)/_components/permission-gate.tsx`), пишущий API-роут — `guard(key)`
(`src/lib/api-guard.ts`, 403 в том же виде `{ error }`, что и остальные ошибки API). Уровни закрывают
разные дыры: до роута доходят не только наши формы, а страницу можно не открывать вовсе. Витрина
(плитки `/admin`, кнопки правки на публичных карточках ростера, ссылка на панель TP) фильтруется тем
же правом — «не видно того, чем нельзя пользоваться», но это удобство, а не защита: гарды выше стоят
независимо от того, что нарисовано. По той же причине операторские куски публичных страниц ростера
спрашивают `can("roster.edit")`, а не «админ ли» (`isAdmin()`): форма и роут, куда она пишет, должны
открываться одним и тем же ключом.

**Одно исключение — `PATCH /api/roster/players/[id]`:** через него пишет и правка анкеты, и панель TP.
Право зависит от тела запроса: поле `tp` требует `tp.edit`, любое другое — `roster.edit`. Иначе
«начислить очки» стоило бы полного доступа к ростеру, а правка анкеты открывала бы сезонный зачёт.

**Панель ролей стала «Командой лиги» (`/admin/staff`).** Владелец и админы — отдельными списками
(требование «админы в интерфейсе отдельно от игроков»), у каждого админа чекбоксы прав, там же
назначение и снятие роли; `/admin/roles` остался редиректом в `next.config.ts` — адрес мог осесть в
закладках. `requireOwner` больше нет: панель открывает обычный ключ реестра `accounts.admins`, который
у владельца есть всегда, — так владелец может разгрузить себя, не раздавая `OWNER_EMAIL`. Свой аккаунт
из панели не правится (иначе «выдать себе всё» — один клик, а «снять себе роль» — способ запереться),
и снятие роли гасит права: вернув админа, начинаем с нуля, а не с прежнего набора.

### Решение: снимок БД в git (23.07.2026)

Проблема вылезла при работе с двух устройств. Данные текли **в одну сторону** — таблица сезона → `roster.json`
→ БД → сайт, — а обратной дороги не было. Всё, что заводят руками в UI (счета серий, правки ростера, баллы,
генерации), живёт только в `dev.db`, а он в `.gitignore`: это данные, не исходники. Забрал репозиторий на втором
маке — получил код и пустую базу; полетел диск — данные лиги не восстановить ничем, кроме гугл-таблицы.

Стало: **`web/data/snapshot.json` — снимок всей базы, коммитится вместе с кодом.** Пара скриптов, обе стороны:
`npm run db:export` (БД → снимок) и `npm run db:import` (снимок → БД).

Ключевое в формате: **в снимке нет числовых `id`**. Они автоинкрементные и на каждой машине свои, поэтому связи
пишутся по `slug` — тому же сквозному ключу, что уже связывает гугл-таблицу, БД и файлы ассетов. Матч своего slug
не имеет: ключ — `openDotaMatchId`, а у несыгранной встречи собирается из участников и даты.

Импорт — **зеркало, а не слияние**: после прогона база повторяет снимок один в один, лишнее удаляется (список
печатается до записи, есть `--dry`). Слияние двух разошедшихся баз потребовало бы разрешения конфликтов — это
отдельная задача, и молча угадывать здесь хуже, чем иметь один явный источник истины. Команды и игроки при этом
обновляются upsert'ом по `slug`, чтобы не менялись id в ссылках UI; производные строки сносятся и создаются заново.

Почему не общая БД в облаке (Turso): адаптер это умеет и строка подключения — единственное, что меняется, но
тогда история данных не версионируется вместе с кодом и появляется зависимость от сети. Снимок в git даёт
и перенос, и бэкап, и возможность откатить состояние лиги к любому коммиту.


## Турниры как сущность (22.08.2026)

Дивизионы были константой в коде: «завести сезон» означало правку исходников. Теперь сезон или кубок —
строка `Tournament`, дивизион (`Division`) принадлежит турниру, а участие команды — отдельная строка
`TournamentEntry` (там же группа и посев). Разделение принципиальное: **команда переживает турнир**,
её участие — нет, поэтому «дивизион команды» не поле у команды, а связь. Состав тоже сезонный —
`RosterSpot.divisionId`, иначе заявка нового сезона затирала бы прошлый.

**Зеркала строкой — сознательное отступление.** `Team.group`, `Series.division` и `GroupEntry.division`
продолжают хранить имя дивизиона текстом: по ним фильтруют полтора десятка выборок (standings,
leaders, архив серий, витрины ростера), и переписать их разом ради чистого FK — способ уронить
работающий сезон. Источник правды — `divisionId`; единственный, кто пишет зеркала, — `src/lib/tournaments.ts`.
Новый код разрезает данные по `divisionId`, а не по строке.

**Составы попадают в лигу двумя путями, писатель один.** Импорт таблицы оператором (`roster-import.ts`)
пишет в ростер сразу — подтверждать себе нечего. Заявка капитана с сайта ложится в очередь
`TeamApplication` (payload — состав целиком JSON, `Team` до апрува не создаётся, как в плане аккаунтов)
и попадает в ростер только при одобрении. Обе ветки зовут `writeTeamToRoster` и общий набор проверок
`applicationProblems` (дубли, конфликт составов, занятый слаг). Разбор входов — один парсер на все
формы (колоночная раскладка, блочная сезонная таблица, построчный текст), а сеть — Steam и
OpenDota — вынесена отдельным шагом (`enrich.ts`): запрос посреди сохранения дюжины команд
превращается в таймаут. Из OpenDota сохраняем только ранг (`Player.rank`); ник в лиге человек
выбирает сам, а `Player.photo` у нас всегда локальный файл — и то, и другое оператору показываем
справкой.

**Удаление турнира** (`deleteTournament`) сносит сезон целиком: карты серий, серии, строки групп,
места составов дивизионов, начисления TP и сам турнир (дивизионы, участие, заявки — каскадом).
Зеркала и кеш `Player.tp` чинятся следом, потому что FK-каскад их не знает. Команды и игроки
остаются в ростере — уходит только участие. Задумано для тестовых прогонов, право `tournaments.edit`.

Права: всё, что пишет турниры, закрыто `tournaments.edit` — и на странице, и в server-action
(до экшена можно дойти мимо страницы, ACCOUNTS-PLAN.md §2.2).

### Решение: турнир заводится мастером (23.08.2026)

`/admin/tournaments/new/<шаг>`: Описание → Дивизионы → Импорт составов → Жеребьёвка → Готово. Шаг —
в адресе, черновик создаётся на **первом** шаге и живёт в БД: прогресс не теряется при закрытой
вкладке, а вернуться и поправить можно кликом по пройденному шагу. Формы шагов — те же серверные
экшены, что у карточки турнира (`admin/tournaments/actions.ts`); мастер их раскладывает по экранам,
а не заводит вторую реализацию, и карточка остаётся местом правки уже заведённого сезона.

Дальше не пускаем только там, где следующий шаг невозможен по смыслу: без дивизионов команду ставить
некуда. Импорт составов и жеребьёвку можно **пропустить** — составы приезжают и заявками капитанов,
а группы разводятся позже. Статус мастер не переключает: турнир остаётся черновиком, «Приём заявок»
или «Идёт» оператор включает осознанно. **Заявки команд в цепочку создания не входят** — это работа
с уже открытым турниром, а не его заведение.

### Решение: регистрация команды капитаном (23.08.2026)

Заявку на турнир подаёт **любой вошедший аккаунт**, даже в статусе `draft`: капитан новой команды
часто сам ещё не в лиге, а заявка всё равно проходит модерацию — второй фильтр на входе только мешал
бы. **Капитан — тот, кто отмечен в составе**, а не тот, кто отправил: заявку может подать менеджер.

**Одна заявка на команду в турнире.** Повторная подача правит существующую (ищем и по подавшему, и
по слагу команды в payload), возвращённая заявка при досыле правок снова встаёт в `pending` — очередь
не заполняется дублями одного состава. Форма при этом предзаполняется прошлой заявкой.

**Проверки — до отправки, а не у модератора.** Кнопка «Проверить состав» гоняет тот же
`applicationProblems`, что видит оператор, и показывает замечания капитану; красное замечание (дубль
ника, один account_id на двоих) отправку закрывает. Ответ сервера возвращает введённое обратно в
форму — поля неконтролируемые, поэтому форма перемонтируется по метке ответа.

Игроки лиги подсказываются `datalist` по никам ростера; **новичка капитан пишет руками** — `Player`
ему заводит апрув, а не форма, как и в анкете кабинета. Одобрение заводит команду, игроков, состав и
участие в дивизионе (`approveApplication` → `writeTeamToRoster`). В разделе `/admin/moderation`
появилась третья вкладка «Заявки команд» — список со ссылкой на разбор внутри турнира: раздел
отвечает за «не пропустить», а не дублирует экран решения.

## UI-примитивы: shadcn/ui на токенах LOST (03.08.2026)

shadcn/ui — не зависимость, а генератор: компоненты копируются в `web/src/components/ui/` (Radix +
`class-variance-authority`, иконки `lucide-react`, утилита `cn()` в `src/lib/utils.ts`). Добавление —
`npx shadcn@latest add <name>`; конфиг — `components.json` (style `new-york`, alias `@/components/ui`).

**Решение: мост токенов, а не вторая палитра.** У проекта уже своя дизайн-система (`globals.css`:
canvas/surface/ink/accent). Дефолтный `init` завёл бы параллельный набор переменных в OKLCH и серый вид,
спорящий с идентичностью LOST. Поэтому `init` не запускали — вместо этого в `@theme inline` **алиасим**
слоты shadcn на наши токены: `--color-primary → --accent`, `--color-card → surface-1`,
`--color-border → hairline`, `--color-ring → --accent` и т.д. Один источник правды по цвету.

**Грабля `@theme inline`:** ссылку акцента вести на **сырой** рантайм-переменную (`var(--accent, …)`),
а не на theme-токен (`var(--color-accent)`). Цепочка через theme-токен схлопывается в литерал на сборке и
перестаёт слышать переопределение дивизиона (`standings/[div]/layout.tsx` ставит `--accent` инлайном). При
прямой ссылке shadcn-хром (кнопки, ring, hover в меню) сам перекрашивается D1→D2, как и остальной хром.

**Граница ответственности:** shadcn — для **интерактива** (dialog, dropdown, tabs, tooltip, формы — всё с
`"use client"` и Radix). Серверные презентационные примитивы (`SectionHeader`, `Chip`, `StatTile`) остаются
в `src/app/_components/ui.tsx` — они без `"use client"` и через Radix их гнать незачем.

**Кнопки/поля стандартизованы на shadcn.** Все action-кнопки (CTA, сабмиты, строчные действия) сведены к
`Button` (варианты default = flat-accent / outline / ghost) — рукодельные градиентные кнопки убраны. Фирменный
янтарь UNDERBEER сохранён как `className` поверх `Button`. Текстовые поля/пароль/поиск — на `Input`, многострочные —
на `Textarea`, галочки — на `Checkbox`; `TextField`/`TextAreaField`/`SelectField` в `_components/form.tsx` внутри
уже на shadcn, поэтому все формы обновились разом. `alert()` — на `sonner`-тосты (нативный alert/confirm глохнет
в webview). Чип-метка `ui.tsx#Chip` — на базе `Badge` (вид LOST задан поверх). **Сознательно НЕ переведены** (иной
примитив, не `Button`): сегмент-тоглы и пилюли-фильтры (пилюли дивизионов, фильтры архива), табы (отчёт матча,
карточка команды), навигация (на роутинге), оверлей-иконки (↻/✕), инлайн-редакторы названий (прозрачные, без рамки)
и плотные инпуты/плитки борда драфта (своя sky/amber-палитра) — у них своя семантика.

**Карточки остаются на токенах, а не на `Card`-примитиве.** Бордер/поверхность карточек уже задаются теми же
токенами, что и `Card` (`rounded-xl border-hairline bg-surface-1` ≈ `bg-card`), а разметка внутри у каждой своя —
у команд, серий, драфтов, `StatTile`. Оборачивать их в `Card` = либо менять
паддинги/тень, либо гасить дефолты `Card` классами: визуально ноль, churn ненулевой. Поэтому `Card` держим для
**новых** обобщённых панелей, а существующие карточки — презентационный слой LOST на общих токенах.

## Заметки по стеку

Грабли Prisma 7, запуск, проверки — в [CLAUDE.md](./CLAUDE.md) (§5) и `web/AGENTS.md`, чтобы не расходились
в двух местах.

Почему такой выбор: **libsql-адаптер** (`@prisma/adapter-libsql`) — чистый JS, без нативной сборки, поэтому
не требует тулчейна на Windows. **SQLite** — файловая БД, минимум инфраструктуры; рост до Postgres меняет
только строку подключения и адаптер.
