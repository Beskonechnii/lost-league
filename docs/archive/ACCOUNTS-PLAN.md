Статус: **план закрыт** — все четыре этапа сделаны (20–21.08.2026, см. `WORKLOG.md`).

## 1. Что меняем

Семь требований, с которых всё началось:

1. Письма при регистрации не уходят → **почтовый флоу убираем совсем**, вход не должен от него зависеть.
2. Регистрация — это **заявка**. Пускает в лигу владелец (апрув), а не сам факт регистрации.
3. Все новые — **игроки**. Админство выдаётся отдельно и осознанно.
4. У админа — **гранулярные права**: удаление профилей, доступ к фичам, назначение админов, апрув регистраций.
5. Админы в интерфейсе — **отдельно от игроков**, с удобной раздачей прав.
6. Сразу после регистрации — **обязательная анкета** (данные игрока, ссылки **каждая отдельным полем**,
   прочее). Пока не заполнена — аккаунт **не попадает** в очередь модерации.
7. Перед отправкой на апрув — **показываем политику площадки** и требуем согласия.

## 2. Ключевые решения

Решения, принятые до кода, — чтобы не переигрывать на середине.

### 2.1 Заявка не создаёт `Player`

Анкета неодобренного человека живёт **в JSON на `UserAccount`**, а `Player` создаётся **только в момент
апрува**.

*Почему.* Публичные витрины (`/roster/players`, статистика, драфт) читают `Player` без фильтров.
Если заводить `Player` сразу, любой неодобренный сразу попадёт в публичный ростер, и пришлось бы
добавлять флаг «опубликован» и фильтровать его **во всех** выборках — это разъедет по всему коду.
Хранение заявки на аккаунте не трогает ни одной существующей выборки.

Заявка на **уже существующего** игрока (claim) работает как раньше: `Player` есть, апрув только связывает.

### 2.2 Права проверяются по БД, а не по куке

Роль вшита в подписанную куку сессии — поэтому сегодня в панели ролей честно написано: «новая роль
вступает в силу при следующем входе». Для **прав** это неприемлемо: снял право — оно обязано пропасть
сразу, а не через неделю.

Поэтому:
- `proxy.ts` остаётся **грубым** гейтом по роли (admin/owner вообще пускать в служебную часть) — как сейчас;
- **гранулярное** право проверяется на странице/в экшене функцией `requirePermission(key)`, читающей БД.

Служебная часть не горячий путь, лишний запрос там дешевле дырки в доступе.

### 2.3 Владелец — вне воронки

`OWNER_EMAIL` всегда `active` и всегда со всеми правами. Иначе владелец, зачистив базу, запрёт сам себя
(апрувить его будет некому).

### 2.4 Почтовый флоу удаляем, а не прячем

Решение Стаса: **убрать совсем**. Удаляются подтверждение почты, сброс пароля, модель `AuthToken`,
`mailer.ts`, `auth-tokens.ts`, страница `/reset`, роут `/api/auth/verify`.

*Как вернуть потом.* Всё это лежит в git — восстанавливается из коммита, предшествующего этапу 1
(см. запись в `WORKLOG.md` за этап 1: там будет SHA). Возврат = `git show <sha>:<путь>` по нужным файлам
плюс ключ `RESEND_API_KEY` в `.env`.

**Следствие, которое надо принять:** «Забыли пароль» перестаёт работать. Пути восстановления доступа:
- вход через **Google** той же почтой — подхватывает тот же аккаунт (ключ аккаунта — email);
- у Google-аккаунта можно **задать пароль** в кабинете (`/me/security`) — это остаётся;
- в крайнем случае владелец удаляет аккаунт, человек регистрируется заново (профиль игрока при удалении
  аккаунта не пропадает).

Если этого окажется мало — отдельной задачей сделать владельцу «сбросить пароль аккаунта» в панели
команды. В план этапов не включено намеренно (лишний объём до первого боевого использования).

## 3. Модель данных

Изменения в `prisma/schema.prisma`, модель `UserAccount`:

| Поле | Тип | Зачем |
|---|---|---|
| `status` | `String @default("draft")` | воронка: `draft` \| `pending` \| `active` \| `rejected` |
| `application` | `String?` | JSON анкеты-заявки; `Player` из неё создаётся при апруве (см. 2.1) |
| `policyAcceptedAt` | `DateTime?` | когда принял политику площадки (требование 7) |
| `submittedAt` | `DateTime?` | когда отправил заявку на апрув — порядок очереди модерации |
| `reviewedAt` | `DateTime?` | когда рассмотрели |
| `reviewedById` | `Int?` | кто рассмотрел (id аккаунта) — для истории решений |
| `rejectedReason` | `String?` | причина отказа: человек видит её и правит анкету |
| `permissions` | `String?` | ключи прав через запятую; канон — `src/lib/permissions.ts` |

Формат `permissions` — строкой через запятую, как уже сделано у `Player.tags` (sqlite не умеет массивы,
а заводить таблицу ради десятка флагов не стоит).

**Удаляется:** модель `AuthToken` (вместе с почтовым флоу).

**Поле `emailVerified` остаётся**, но перестаёт быть гейтом входа: его ставит только Google-вход, и он
честно значит «почту подтвердил Google». В интерфейсе показываем плашку, только когда `true`.

**Миграция.** В схеме `status` по умолчанию `draft`, но существующие аккаунты одноразовым UPDATE
переводятся в `active` — иначе действующие люди (включая владельца) окажутся заперты в воронке.
Дефолт именно `draft`, чтобы **новые** аккаунты — в том числе создаваемые Google-callback'ом — попадали
в воронку автоматически, без «не забыть проставить» в каждом месте создания.

## 4. Воронка аккаунта

```
регистрация (email+пароль или Google)
        │
        ▼
     draft ──── анкета заполнена + политика принята ───▶ pending
        ▲                                                  │
        │                                        апрув ─────┼───── отказ
        │                                                  │
        │                                                  ▼
   правка анкеты ◀──────────── rejected ◀──────── (причина отказа)
                                                           │
                                              апрув ──▶  active
```

- **`draft`** — вошёл, но анкеты нет. В кабинете **ничего, кроме анкеты**, не показываем.
  В очереди модерации не значится (требование 6).
- **`pending`** — анкета и согласие с политикой есть, ждёт решения. Кабинет показывает «на рассмотрении».
- **`active`** — одобрен. `Player` создан (или привязан), кабинет работает полностью.
- **`rejected`** — отказ с причиной; человек правит анкету и отправляет снова (возврат в `pending`).

Обе ветки онбординга — «я новый игрок» и «я уже в ростере» — заканчиваются в `pending`; в очереди
модерации они помечаются типом (новая анкета / привязка к существующему).

## 5. Права

Реестр — `src/lib/permissions.ts` (чистый модуль: ключ, подпись, группа), как `roles.ts` / `player-tags.ts`.

| Ключ | Что открывает |
|---|---|
| `accounts.approve` | апрув регистраций и заявок на привязку |
| `accounts.admins` | назначение админов и раздача прав (у владельца всегда) |
| `roster.edit` | правка команд и игроков |
| `roster.delete` | **удаление** профилей — отдельно от правки, разрушительное |
| `series.edit` | архив серий и карт |
| `tp.edit` | начисление TP |
| `studio` | студия графики (в т.ч. платная генерация) |
| `underbeer` | шоу-драфт |
| `theme` | тема UI |
| `tools` | разбор матча, варды, показатели (инструменты чтения) |

- Владелец имеет **все** права неявно, отнять нельзя.
- Новый админ по решению Стаса получает **ноль** прав — владелец отмечает нужные галочками.
- Плитки хаба `/admin` и подвкладки показываются только при наличии права: не видно того, чем нельзя
  пользоваться.
- Проверка — на трёх уровнях: `proxy` (роль), страница (`requirePermission`), экшен/API-роут
  (`requirePermission`). Гейт в роуте обязателен: страницу можно и не открывать.

## 6. Разделы админки

| Раздел | Что с ним |
|---|---|
| `/admin/staff` | **новый.** Команда лиги: владелец и админы **отдельным списком**, у каждого чекбоксы прав. Отсюда же назначают админа. Требование 5 |
| `/admin/registrations` | **новый.** Очередь новых регистраций: карточка заявки (анкета целиком, заявленный MMR, ссылки), кнопки «Одобрить» / «Отклонить с причиной». Право `accounts.approve` |
| `/admin/claims` | остаётся — заявки на привязку к существующему игроку. Уходит под то же право `accounts.approve` |
| `/admin/roles` | **удаляется**, заменён на `/admin/staff` (редирект). Заодно чинится баг: ссылка на профиль там ведёт по `slug`, а роут ждёт числовой `id` |
| `/rules` | **новый, публичный.** Политика площадки; ссылка из формы регистрации и из анкеты |

### Этап 2 — анкета и политика ✅ сделано 20.08.2026

- Чекбокс согласия с политикой (со ссылкой на `/rules`) → `policyAcceptedAt`, отправка → `pending`

### Этап 3 — модерация регистраций ✅ сделано 21.08.2026
- `/admin/registrations`: очередь `pending` (обе ветки в одном списке, помечены типом), карточка заявки
  с анкетой целиком, апрув — создаёт `Player` из `application` либо связывает claim — и возврат с причиной.
- **MMR в форме апрува ставит оператор** (в анкете он заявленный); позиция в `Player` не переносится —
  роль в составе живёт в `RosterSpot`.
- Право `accounts.approve` проверяется в `approveRegistration`/`rejectRegistration`, а не только на
  странице; без права вместо очереди — плашка.
- `/admin/claims` больше не показывает заявки в `pending` — иначе одна заявка висела бы в двух очередях.
- Кабинет: «на рассмотрении» со сводкой отправленного и «заявку вернули» — причина, дата решения и
  та же анкета с прежними ответами; повторная отправка возвращает заявку в очередь.
- Сводка анкеты — общий `app/_components/application-summary.tsx`: оператор и игрок видят одно и то же.

### Этап 4 — команда лиги и раздача прав ✅ сделано 21.08.2026
- `/admin/staff`: владелец, админы и остальные аккаунты отдельными списками; чекбоксы прав,
  назначение/снятие роли. Панель открывает ключ `accounts.admins` (у владельца всегда), а не
  `requireOwner` — его убрали. Свой аккаунт не правится, снятие роли гасит права.
- Право проверяется на трёх уровнях: `proxy` (роль) → страница (`denyUnlessPermission`,
  `(admin)/_components/permission-gate.tsx`) → пишущий API-роут (`guard`, `src/lib/api-guard.ts`).
- Плитки `/admin` и операторские куски публичных витрин ростера/TP фильтруются по праву
  (`can()` вместо `isAdmin()`). Отдельного ряда подвкладок у админки нет — его заменил хаб плиток,
  поэтому фильтрация плиток и есть фильтрация подвкладок.
- `/admin/roles` удалён, остался редирект в `next.config.ts`; ссылка на профиль в новой панели
  ведёт по числовому `id` (старый баг со `slug`).
- Исключение по правам: `PATCH /api/roster/players/[id]` пишет и анкету, и TP — поле `tp` требует
  `tp.edit`, любое другое — `roster.edit`.

## 8. Долги и открытые вопросы

- **Восстановление пароля.** После удаления почтового флоу его нет (см. 2.4). Возможное продолжение —
  «сбросить пароль» в панели команды у владельца.
- **Возврат писем.** Когда появится `RESEND_API_KEY` — вернуть файлы из git и включить подтверждение
  почты как шаг воронки (`draft` → анкета → подтверждение → `pending`).
- **Сезон в анкете.** Формального понятия «сезон» в модели нет, поэтому лимит смены ника — скользящее
  окно 120 дней (см. §9 `CLAUDE.md`). Когда появятся сезоны — привязать к ним.
