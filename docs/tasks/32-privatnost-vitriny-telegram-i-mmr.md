# ТЗ: Приватность витрины — телеграм и MMR гасятся тумблером лиги

**Статус:** done
**Входит в MVP:** да — по телеграму (см. «Вердикт»)

## Вердикт (решает `pm`)

**В MVP.** Телеграм-хендл — контакт живого человека. Он собирается анкетой и ботом ради связи
лиги с игроком (`DECISIONS.md` 10.09.2026), разрешения публиковать его никто не давал, а на
странице игрока он висит кликабельной пилюлей `@handle` для любого анонима. Открытая витрина
лиги на две сотни игроков = готовый контакт-лист для рассылок. Основание то же, по которому в
MVP вошло ТЗ 29 (`DECISIONS.md` 18.09.2026), и `/privacy` (в MVP по `MVP.md` §1) не должен врать
о том, что лига публикует.

**MMR сам по себе в MVP бы не вошёл** — это игровой показатель со слов игрока, сезон открывается
и с ним. Он едет в этом же ТЗ, потому что механизм один (флаг → слой данных → те же файлы), и
отдельное ТЗ на второй тумблер стоит дороже, чем строка в том же коде. Отдельным этапом MMR не
выносится и приёмку телеграма не задерживает.

Номер 32, а не 31: 31 в `BACKLOG.md` занят ручным пунктом «Мусор в публичных данных».

## Цель

Владелец лиги одним экраном решает, показывать ли на публичной части телеграм игроков и их MMR.
Выключил — этих данных нет ни на одной странице, ни в одном открытом API, ни в ответах бота, ни
в payload страницы. Оператор в админке и редакторах видит их как прежде: они нужны ему для
работы. Закрыли, когда `curl` по всем публичным адресам не находит ни хендла, ни числа MMR.

## Scope

**Входит:**

- Две настройки лиги: «показывать телеграм» и «показывать MMR». Одна пара на лигу, не поле игрока.
- Значение по умолчанию — **скрыто**. Пустая база, свежая выкатка, сломанное чтение настройки —
  во всех трёх случаях данных на публичке нет. Приватность не должна зависеть от того, успел ли
  кто-то нажать кнопку.
- Правит только владелец (`OWNER_EMAIL`). `admin` видит экран или нет — решает `design`+`stage`
  по действующему укладу прав, но **менять** значение может только владелец.
- При выключенном флаге поле не попадает на публичную поверхность **ни в каком виде**: ни в
  разметке, ни в RSC-payload страницы, ни в JSON открытого API, ни в тексте бота.
- Производные от MMR гасятся вместе с ним: средний MMR команды, `Σ MMR` на оверлее, полоска
  `Meter`. Причина: средний по пятёрке при четырёх известных выдаёт пятого, а полоска — это то же
  число, нарисованное иначе. Ровно на таких полумерах разъехалось ТЗ 29.
- Свои данные игрок видит всегда: `/me`, `/me/profile`, мини-профиль своего аккаунта, своя анкета
  в `/me/welcome`, ответы бота о **своём** профиле. Флаг про чужое.
- Все поверхности из двух таблиц выше — единым заходом.

**НЕ входит:**

- Флаг у каждого игрока — решено Стасом: один тумблер на лигу.
- Админка, редакторы ростера, модерация, дубли, импорт, CRM, `/admin/tp`, админский драфт: там
  данные остаются видны всегда — оператор ими работает, без них экраны бесполезны.
- Изменения анкеты, регистрации в боте и формы заявки: поля собираются как прежде. Флаг про
  показ, а не про сбор.
- Переписывание уже поданных заявок (`TeamApplication`) в базе — это операционный архив лиги, а
  не витрина; см. пункт про `application-summary` в критериях.
- Другие личные поля (город, страна, дата рождения, ранг, осколки, ссылки на профили) — не
  заказано, отдельный разговор.
- Скрытие самого существования полей от оператора, аудит-лог изменения флага, история
  переключений — на открытие сезона не влияет.
- Правки `/privacy` текстом — это ТЗ 03 (`docs/tasks/03-seo-bazovyi.md`), здесь только механизм.

## Требования · DEV

### Где живут флаги — решено: строкой в базе

Не файлом рядом с `data/theme.json`. Обоснование:

1. **«Переживёт выкатку» вариантов не различает.** Том `lost-data:/app/data`
   (`web/docker-compose.yml:19`) держит и `dev.db`, и `data/theme.json` — оба переживают
   пересборку образа одинаково.
2. **Различает другое: расхождение с репозиторием.** `data/theme.json` коммитится. После Б1
   боевой файл в томе и файл в git разойдутся так же, как база, — но про базу вопрос «кто
   главный» уже поставлен письменно и у неё есть бэкап (`docs/DEPLOY.md` §Данные и бэкапы).
   Второй расходящийся артефакт = второй такой же вопрос, только незаданный. На настройке
   приватности цена ошибки — «выкатили и открыли контакты, не заметив».
3. **Прецедент уже в базе.** Настройки, которые правит оператор, лежат в БД: `HomeBanner` (одна
   строка) и `BotSetting` (ключ-значение). `theme.json` — файл по своей причине: тема нужна
   корневому layout как CSS и возится между машинами вместе с ростером, а не правится в бою.
4. **Снимок данных настройку не трогает:** `web/scripts/export-db.ts` эти таблицы не выгружает,
   значит `db:import` флаг не сбросит. Файл же сносится обычным `git checkout`.

Форму хранения (строка `id=1` по образцу `HomeBanner` или две записи в `BotSetting`) выбирает
`stage`. Требование одно: **чтение не падает на пустой базе и на битом значении — в обоих случаях
отдаёт «скрыто»**.

### Остальное

- Источник правды один: и страницы, и API, и бот спрашивают настройку в одном месте. Разъехаться
  двум местам нельзя — это и есть механика ТЗ 29, повторённая заново.
- Гасить поле нужно **до** передачи в клиентские компоненты, а не условием в разметке: иначе оно
  уезжает в RSC-payload (грабля ТЗ 29, `(bare)/overlay/underbeer/[id]/page.tsx`).
- `GET /api/underbeer/[id]` отдаёт `session.payload` анониму. Снимок пула внутри payload может
  содержать MMR, записанный при создании сессии, — то есть флаг обязан действовать и на **ответ
  роута**, а не только на рендер оверлея. Старые сессии в базе уже содержат MMR; переписывать их
  не надо, достаточно не отдавать.
- Смена флага должна быть видна без перезапуска и без ручной инвалидации: публичные витрины
  кэшируются (`dynamic = "force-dynamic"` стоит не везде — проверить `/roster`, `/roster/teams`,
  страницу игрока). Прецедент сброса — `revalidatePath("/", "layout")` в `src/app/api/theme/route.ts`.
- Бот читает настройку на каждое обращение, как `bot-settings.ts`: он живёт долгоживущим
  процессом, перезапуск после каждого переключения = настройка, которая не работает.
- Миграция Prisma + `npx prisma generate`. `web/prisma/dev.db` коммитится.

### 3. Четыре состояния

- **Загрузка** — `admin/privacy/loading.tsx` по образцу `admin/banner/loading.tsx`: `SkeletonHeader`
  + один `Skeleton variant="card"`, контейнер `role="status" aria-label="Загружаем настройки показа"`.
- **Пусто** — отдельного пустого состояния у экрана нет и заводить его нельзя: нет строки в базе =

- **Ошибка** — чтение настройки не удалось: экран рисуется как «скрыто» плюс `Alert tone="warn"
  block` сверху: «Настройку прочитать не удалось — витрина работает как «скрыто». Сохранение
  перезапишет значение». Ошибка записи отдельного блока не получает: её показывает `Alert tone="err"`
  внутри `SaveButton`.
- **Нет прав** — два разных случая:
  1. нет права `privacy` (обычный админ без него, `player`): существующий
     `denyUnlessPermission("privacy", "Приватность витрины")` — `AdminHeader` + `Alert tone="warn"`
     с именем права. Ничего нового.
  2. право есть, но аккаунт не владелец: **экран виден целиком и только для чтения.** Оба `Toggle`
     с `disabled` (состояние есть в Ките — `kit-showcase.tsx:143`), `SaveButton` не рисуется вовсе
     (кнопка, которая всегда отвечает 403, хуже её отсутствия), сверху `Alert tone="info" block`:
     «Показ переключает владелец лиги (`OWNER_EMAIL`). Здесь видно, что открыто сейчас».
     Почему видно, а не спрятано: оператор работает с телеграмом и MMR в модерации и импорте, и без
     этого экрана вопрос «почему на витрине нет MMR» уходит к разработчику.
     Прецедент разделения «раздел по праву, действие по владельцу» — `/admin/staff` (`page.tsx:199`).

  строкой ряда (`py`) и кликабельной подписью (`htmlFor` у `Toggle` уже есть). Горизонтального

- **1280 / 1440.** Та же колонка `FORM_MAX_W` (48rem) по центру, ничего не растягивается и не
  переезжает. Во вторую колонку экран не раскладывается: две настройки рядом читаются как выбор
  «или/или».

  не пунктом этого ТЗ.
- Больше ничего заводить не нужно: всё перечисленное в разделе 2 в Ките уже есть.

### 6. Витрины, с которых поле убрали

Правило одно, и оно же снимает бо́льшую часть работы: **поле гасится в DTO (`roster-data.ts`,
`draft-data.ts`, `apply/pool.ts`), а не условием в разметке** — то же требование, что в DEV. Разметка
витрин уже написана терпимо к `null` (`filter(Boolean).join(" · ")`, `{p.mmr && …}`), поэтому ниже —
только места, где остаётся прочерк, операторский текст или дыра.

Общий принцип для всего неперечисленного: **скрытое поле уходит вместе со своей подписью; заголовок
блока остаётся, пока в блоке есть хоть что-то ещё; прочерк вместо значения не ставится** — прочерк
означает «у этого игрока пусто» и врёт, когда причина в настройке лиги.

1. **Страница игрока** (`(public)/players/[key]/page.tsx`)
   - Пилюля `@handle` (419–423) уходит из `OverlapRail`. Рельс — поток пилюль, соседи сдвигаются,
     ширина блока «Ссылки» задана (`lg:w-[300px]`) и не меняется: колонка не прыгает.
   - Пустая ветка блока «Ссылки» (`page.tsx:448`) — «Ссылок нет — заполните account_id или телеграм»
     — это совет оператору, показанный посетителю. Развести: `authed` — прежний текст, остальным
     «Профилей игрока нет».
   - `FactBox` «MMR» (513) уходит из сетки `grid-cols-2`. Дыры не остаётся: сетка автопотоком,
     «Ранг» держит `col-span-2 sm:col-span-1`, остальные плитки поднимаются. Карточка «Данные» и её
     `BlockLabel` остаются.
   - Пустая ветка фактов (552): фраза «Анкета пока не заполнена» при скрытом MMR врёт про человека.
     Развести так же: `authed` — прежний текст, посетителю — «Открытых данных об игроке нет».
   - Плашка «Не заполнено: … телеграм» (`page.tsx:277`, `gaps` из `profiles.ts:318`) сейчас видна
     **всем**; на витрине турнира такая же диагностика уже закрыта под `authed`
     (`tournaments/[slug]/roster/players/page.tsx:124`). Закрыть и здесь, а при выключенном флаге
     «телеграм» не приходит в `playerGaps` для не-оператора вовсе.
2. **`/roster`, карточки команд** (`roster/_components/team-cards.tsx`)
   - Строка игрока (92–94): правый столбец `shrink-0 text-right` с числом и `Meter` убирается
     **целиком**, а не превращается в «—». Прочерк у всей пятёрки читается как потеря данных. Имя и
     `Chip` роли занимают строку, высота ряда прежняя — её держит аватар.
   - Плитка «ср. MMR» в шапке (209–212) не рисуется. Кнопка раскрытия состава остаётся на своём краю
     (она `shrink-0` в том же ряду), имя команды забирает освободившуюся ширину. Плитка TP в пуле
     стоит на том же месте и от флага не зависит — шапка не пустеет.
   - Мета-строка свёрнутой карточки (132–133) садится на «N игрок(ов)» сама, потому что
     `mmrAverage` приедет `null`. Правок в разметке не нужно.
   - `mmrPct`/`Meter` при выключенном флаге не считается вообще: полоска — то же число картинкой.
3. **`/roster/players` и `/tournaments/<slug>/roster/players`** (`PlayerMiniCard`,
   `players-explorer.tsx:135`, `roster/players/page.tsx:135`): `mmr` не передаётся, мета-строка
   `flex-wrap` смыкается (TP · роль · медаль ранга · стрелка). Сортировок по MMR на витринах нет —
   порядок карточек не меняется, сетка `sm:grid-cols-2 lg:grid-cols-3` не трогается.
4. **Страница команды** (`roster/teams/[id]/page.tsx`): подзаголовок (156) и `sub` строк состава
   (329) собраны через `filter(Boolean).join(" · ")` — `null` уносит и разделитель; список в
   `<details>` (288) уже под `{p.mmr && …}`. Заголовки секций и `RosterLine` остаются как есть.
   Подзаголовок становится «капитан: X · N игрок(ов)» — строка не пустеет никогда.
5. **Заявка в турнир**: `apply/board-player.tsx:38` передаёт `value={null}` — `PlayerLine`
   (`pouf/player-line.tsx:36`) рисует строку без правого числа, это штатный режим атома, доска не
   перестраивается. `apply/board-ready.tsx:55` — правый угол занят двумя смыслами сразу: MMR и
   предупреждение «нет в пуле». Гасим **только число**: у игрока из пула угол пустой, предупреждение
   остаётся — оно про заявку, а не про MMR.
6. **Оверлей UNDERBEER** (`overlay-live.tsx:67,82,98`): `Σ MMR` уходит из шапки команды, в ряду
   остаётся знак цвета и имя (`justify-between` с одним ребёнком не ломается); у строки игрока
   убирается правый блок «число / MMR» целиком, ник занимает ширину. Оверлей — тёмная OBS-поверхность
   вне Light Clay: тон, отступы и размеры не трогаем, только снимаем два элемента.
7. **Мини-профиль на главной** (`(home)/mini-profile.tsx:163`) — это **свой** профиль: `StatTile`
   «MMR» остаётся всегда, прочерк там уже мотивирован постоянной высотой карточки. Флаг сюда не
   доходит.
8. **Бот** (`tg-menu.ts:248`, `tg-tournaments.ts:296`): строка «MMR: …» и «Средний MMR основы» не
   заменяются прочерком, а не печатаются; порядок остальных строк карточки прежний.

## Acceptance criteria

Проверяется при **выключенных** обоих флагах, если не сказано иначе. `<slug>` — игрок с
заполненными `telegram` и `mmr`.

- [ ] Владелец открывает экран настройки, видит два переключателя, выключает оба, перезагружает
      страницу — оба остаются выключенными
- [ ] Аккаунт с ролью `player` и аккаунт `admin` без прав владельца изменить значение не могут:
      попытка записи отвечает отказом (403 / текст ошибки), значение не меняется
- [ ] Аноним: `curl -s localhost:3000/players/<slug>` — в ответе нет ни `t.me/`, ни хендла игрока,
      ни его числа MMR (проверяется по **всему** телу ответа, включая `self.__next_f.push` —
      именно так ловится payload)
- [ ] Вошедший игрок (не владелец) на `/players/<slug>` чужого игрока: тот же результат
- [ ] `/roster`, `/roster/players`, `/roster/teams/<id>`, `/tournaments/<slug>/roster/players` —
      в теле ответа нет чисел MMR, нет среднего MMR команды, нет полоски `Meter` у игрока
- [ ] Страница игрока без MMR и телеграма не показывает пустые подписи «MMR» и «Телеграм» и не
      ломает блок фактов: у игрока, у которого кроме MMR ничего нет, работает состояние «пусто»
- [ ] `/tournaments/<slug>/apply`: капитан собирает состав — в пуле и в готовом составе чисел MMR
      нет ни на экране, ни в payload страницы
- [ ] Заявка, поданная при выключенном флаге, доходит до оператора полной: `/admin/moderation`
      (или экран заявок) показывает MMR и телеграм заявленных игроков — данные собираются, но не
      публикуются
- [ ] Оверлей `/overlay/underbeer/<id>` без входа: на экране нет `Σ MMR` и нет MMR игроков, и

- [ ] `curl -s localhost:3000/api/underbeer/<id>` без куки: в JSON нет значений MMR (включая
