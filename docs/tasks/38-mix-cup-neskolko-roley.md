# ТЗ 38: Заявка на индивидуальный турнир спрашивает роли, а не молчит о них

**Статус:** done · принято `qa` 24.09.2026, все 6 критериев pass
**Входит в MVP:** нет — Mix Cup и UNDERBEER целиком later (`MVP.md`), это починка внутри уже
отложенной функции

Заголовок и файл остались от первой версии («Mix Cup»), но по ответу Стаса 23.09.2026 UNDERBEER
тоже становится форматом турнира с публичной регистрацией (`docs/tasks/37-*.md`, Scope п.4) — эта
проблема и это решение относятся к обоим форматам одинаково, не только к Mix Cup. Переименовывать
файл ради этого не стал — номер и так ссылка, лишняя правка ссылок дороже.

## Цель

Игрок, который сам записался на Mix Cup или UNDERBEER-турнир (без команды — в обоих индивидуальных
форматах командной привязки нет никогда), сегодня не имеет ни одной роли вообще, и в пуле драфта
падает в «Без позиции» — единственный сегмент, который не про позицию, а про «непонятно кто».
Вводная Стаса: при записи на такой турнир **обязательно** спрашивать, в каких ролях человек хочет
играть, и это **несколько** ролей, а не одна.

Закрыто, когда: новый гость, записавшийся на индивидуальный турнир без ростерного места, выбирает
несколько желаемых ролей на форме записи, и в пуле драфта капитан видит его карточку одной строкой
со всеми выбранными ролями — а не в общей яме «Без позиции». Верно для обоих форматов одним и тем
же кодом.

## Контекст

- **Роль в проекте живёт только у `RosterSpot.role`** (`web/prisma/schema.prisma:360`) — место
  игрока в конкретной команде лиги, одна строка = одна роль. У `Player` своего поля роли нет
  никогда — роль это позиция В СОСТАВЕ, а не свойство человека. У игрока без команды (типичный
  случай индивидуальной регистрации) `RosterSpot` нет вовсе.
- Справочник ролей — `web/src/lib/roles.ts`: `ROLES` (carry/mid/offlane/soft-support/hard-support/
  standin/coach), `isRole`, `roleLabel`, `roleShort`, `rolePosition`. Общий модуль, «второго разбора
  одного и того же быть не должно» (комментарий в файле) — используется ботом, анкетой, драфтом.
- **Общая анкета лиги уже спрашивает ОДНУ позицию**: `Application.position` (`web/src/lib/
  application.ts:27,295`) — «Выберите позицию», проверка `isRole`. Это поле про заявку в состав
  лиги (сезонный формат) и не трогается этим ТЗ: там одна роль осмысленна (человек идёт в
  конкретный состав на конкретное место), в отличие от индивидуальных форматов, где состав ещё не
  существует и роль — это набор желаемого, а не факт.
- Пул драфта: `web/src/lib/draft-data.ts` → `draftPool()` читает роль игрока из `p.main.role`
  (основное место в ростере, `listPlayers()`); у игрока без места — `role: null`, `position: null`.
- Сегментация пула: `web/src/lib/draft.ts` → `PoolPlayer.role`/`.position` (по одному значению),
  `segmentPool()` раскладывает по позициям 1–5 плюс «Без позиции» (`draft.ts:63-83`). Рендер —
  `web/src/app/(admin)/underbeer/[id]/_components/pool-columns.tsx` — общий компонент борда, его
  правка автоматически действует и на Mix Cup, и на UNDERBEER-турнир (один движок, один борд,
  `docs/tasks/33-*.md`). Подпись под ником — `player-line.tsx:41` (`roleShort(player.role)`, одно
  значение).
- Регистрация: `web/src/lib/mixcup.ts` → `registerForMixCup()` (по ТЗ 37 обобщается на оба формата,
  сигнатура и имя файла могут поменяться внутри самого ТЗ 37 — здесь важно только то, что модель
  регистрации одна). Модель — `TournamentRegistration` (после ТЗ 37; до него — `MixCupRegistration`
  с `eventId`, если этот этап почему-то стартует раньше 37, чего быть не должно). `
  createPlayerFromApplication` (`web/src/lib/account.ts:420`) сегодня не пишет роль никуда — писать
  некуда, у `Player` поля нет.
- Форма записи — `web/src/app/(public)/mixcup/[slug]/page.tsx`/`actions.ts` для Mix Cup; для
  UNDERBEER-турнира — новая страница по адресу из ТЗ 37 (открытый вопрос там, не блокирует это
  ТЗ — механизм формы один и тот же).
- «Все обязательно числятся в базе» (вводная Стаса) — уже так: `registerForMixCup`-подобный путь
  заводит `Player` сразу, до апрува анкеты (`DECISIONS.md` 22.09.2026, «в пул до модерации, на
  витрины — только после апрува»). Это ТЗ ничего не меняет в воронке модерации, только добавляет
  данные, которые эта воронка пропускала.

## Scope

**Входит:**

1. **Множественные желаемые роли на записи в индивидуальный турнир** (Mix Cup и UNDERBEER —
   одинаково). Форма даёт выбрать несколько ролей из справочника `roles.ts` (мультивыбор, не
   радио). Обязательное поле — нельзя записаться, не отметив ни одной роли (вводная Стаса:
   «обязательно должны запрашивать»).
2. **Хранение — на `TournamentRegistration`** (общая модель обоих форматов после ТЗ 37). Новое
   поле `desiredRoles String?` — CSV ключей ролей (`"carry,mid"`), тем же приёмом, что `series` у
   турнира: строка, а не связь и не JSON, потому что значений мало и они из фиксированного
   словаря. Парсинг/сборка CSV — две функции в `roles.ts` (`parseRoleKeys`/`joinRoleKeys` или
   аналог), не новый модуль.
   **Живёт у регистрации на КОНКРЕТНЫЙ ТУРНИР, не у `Player` и не у общей анкеты** — это желание
   именно для этого события (человек может хотеть другую роль на следующем), а не постоянное
   свойство игрока.
3. **Пул драфта показывает все роли одной строкой** — верно для борда любого из двух форматов, это
   один компонент. `PoolPlayer` получает список ролей вместо одной (для игрока с ростерным местом —
   список из одного значения, поведение не меняется). `segmentPool()`: игрок с одной ролью — в её
   колонке, как сегодня; игрок с несколькими — в **новом сегменте «Несколько ролей»** (перед
   «Керри», первым слева — капитаны разбирают гибких участников осознанно, а не потерянными в
   конце). Игрок остаётся в пуле **ровно одной строкой** при любом числе ролей — не размножается по
   колонкам. Строка игрока показывает все выбранные роли (короткие подписи через разделитель —
   `roleShort` уже это умеет, применяется к каждой).
4. **Игрок с ростерным местом ведёт себя как сегодня.** Роль берётся из `RosterSpot.role` (одна),
   `desiredRoles` не спрашивается и не участвует — множественность роли это свойство ИМЕННО
   одиночной записи без команды, а не общее свойство драфта.

**НЕ входит:**

- **Правка общей анкеты `Application.position`.** Там одна роль — это про заявку в состав лиги,
  разные с индивидуальными форматами сценарии, второй не отменяет первый.
- **Множественная роль как постоянное свойство игрока (`Player`).** Роль игрока в проекте — это
  место в конкретном составе (`RosterSpot`), это архитектурное решение не переигрывается здесь.
  `desiredRoles` — данные заявки на конкретный турнир, а не игрока.
- **Список ролей ограничивать позициями 1–5** (убирать coach/standin из выбора на форме записи).
  Если `design`/Стас решат, что тренер и замена в миксе бессмысленны — режется на приёмке одной
  строкой в форме, не архитектурный вопрос.
- **Ad hoc-драфт UNDERBEER без турнира** (`/underbeer`, `docs/tasks/37-*.md`, «Решение pm»). Там
  нет регистрации и спрашивать роль не у кого — состав набирается из всего ростера вручную, как
  сегодня.

## Требования · DESIGN

Три места: поле выбора ролей на `/join/<slug>`, роли в списке участников консоли, роли в строке
пула драфта. **Один новый атом Кита** (`ChoiceChips` — обещан первым пунктом в DESIGN §5 ТЗ 37),
остальное — существующими атомами. Экран записи и консоль уже собраны под это ТЗ 37, перестройки
раскладки нигде не требуется.

### 1. Кит: `ChoiceChips` — ряд чипов множественного выбора

**Новый артборд на странице «Атомы»** Кита (`.claude/skills/kit/SKILL.md`, «Новый компонент —
новый артборд»). Артефакт **не трогаю** — правка макета отдельной просьбой Стаса, до неё атом
живёт кодом и этим разделом.

Файл — `web/src/components/pouf/choice-chips.tsx`. Почему не берём существующее:

- `pouf/checkbox.tsx` — только коробочка 20px, без раскладки строки и без подписи (так и написано
  в его шапке: «ряда с подписью здесь нет намеренно»);
- `PillButton`/`PillTrack` (`pouf/tabs.tsx`) — навигационный разрез (`aria-pressed`, меняет вид
  списка), не поле формы со значением;
- `Segmented` — ровно один выбранный из многих, и он клиентский.

**Вид берётся у пилюли, не изобретается:** внутри `ChoiceChips` зовётся `pillClasses`
(`pouf/tabs.tsx`) — отмеченный чип это приподнятая мятная подушка, неотмеченный — плоский
`variant="field"`. Второго «почти такого же» вида пилюли в системе не появляется.

```ts
export function ChoiceChips({
  name,                 // имя поля формы; отмеченные уходят несколькими значениями одного имени
  label,                // подпись группы
  options,              // { value: string; label: string; disabled?: boolean }[]
  defaultValue,         // string[] — что отмечено при открытии
  hint, error,          // как у Field
  required,             // звёздочка у подписи
  disabled,             // вся группа
}: ChoiceChipsProps)
```

- **Атом серверный, без `"use client"`.** Внутри — нативные `<input type="checkbox" name=… class="peer sr-only">`
  + `<label>` с чипом, состояние отмеченности рисуется `peer-checked:` (класс `.pouf-choice-chip`
  в `pouf/pouf.css`, рядом с остальной пластилиновой фурнитурой). Причина та же, по которой в
  DESIGN §1 ТЗ 37 поле «Формат» стало скучным `FormSelect`, а не `Segmented`: форма записи — это
  server action без клиентского состояния (`join/[slug]/page.tsx`), и клиентский атом потащил бы
  за собой клиентскую обёртку всей панели действия.
- **Свои подпись/ошибка, без обёртки в `Field`.** Группа флажков — это `<fieldset>` + `<legend>`,
  а `Field` рисует `<label for>` на один контрол. Прецедент уже есть (флажок согласия в анкете,
  комментарий у `FieldError` в `pouf/Input.tsx`): `ChoiceChips` внутри повторяет разметку `Field`
  — `pouf-field` / `pouf-label` / `pouf-hint` / `FieldError` — и выглядит с полями формы одинаково.
- **Тач-цель.** Чип добирает до 44×44 (`min-h-11`), как вкладки добирают `TOUCH_TARGET`
  (`UI-GUIDELINES.md` §6): это поле под палец, а не фильтр в ряду.
- **Состояния артборда:** ничего не выбрано · выбрано одно · выбрано несколько · ошибка (красная
  плашка `FieldError` под рядом, ряд не краснеет целиком) · `disabled` вся группа · фокус
  с клавиатуры (`focus-visible` на чипе, не на скрытом флажке) · длинный список в перенос.

### 2. Роли на форме записи `/join/<slug>`

`web/src/app/(public)/join/[slug]/page.tsx`, `ActionPanel` — стопка под это и заводилась (ТЗ 37
DESIGN §3), карточка действия не перестраивается.

- Ветка **вошедший · приём открыт · не записан**: `ChoiceChips` первой строкой `Stack`, кнопка
  «Участвовать» — последней.
  `label="В каких ролях готовы играть"`, `required`,
  `hint="Можно отметить несколько — капитаны увидят все"`,
  `options` = все семь `ROLES` из `lib/roles.ts` в их порядке (1–5, затем «Замена», «Тренер»),
  подписи — `roleShort`. Список не режем: Scope прямо оставил это на приёмку.
- Ветка **гость**: чипов нет, как сегодня одна кнопка «Участвовать» → `intent`-кука → вход.
  Собирать роли до входа бессмысленно — это не форма, а ссылка, и выбор потерялся бы на
  круге через логин. Вернувшись, гость видит этот же экран уже вошедшим и отмечает роли здесь.
- Ветка **записан**: под `StatusPill «Вы записаны»` — ряд `Chip` (`pouf/blocks.tsx`) с выбранными
  ролями, только чтение. Отдельного редактирования ролей в 38 нет: поменять = «Отменить запись»
  и записаться заново (кнопка рядом уже стоит). Развилка — «Открытые вопросы».
- Ветка **приём закрыт** — как сегодня, `Alert tone="warn"`, чипов нет.

**Состояния экрана** (сверх таблицы ТЗ 37 §3, которая остаётся целиком):

- *ошибка «ни одной роли»* — `error` у самого `ChoiceChips` (`FieldError` под рядом), **не**
  `Alert` над формой: ошибка поля живёт у поля, иначе на 390 причина уезжает от места правки.
  Отмеченные чипы при отказе сохраняются (правило ТЗ 30);
- *ошибка записи целиком* (мест нет — ТЗ 39, прочее — ТЗ 30) — `Alert tone="warn"/"err"` между
  чипами и кнопкой. **Два сообщения не конкурируют:** одно принадлежит полю, другое — действию,
  и оба помещаются в ту же стопку без перестройки — это и есть «не мешать 39»;
- *пусто* — турнира нет, `notFound()` → `stub-page.tsx` (ТЗ 37);
- *загрузка* — в `loading.tsx` карточка действия получает `Skeleton` высотой 44px на месте ряда
  чипов плюс существующий скелет кнопки;
- *нет прав* — это гость, см. ветку выше.

**390:** ряд чипов `flex-wrap`, семь чипов по 44px ложатся в три строки — это нормальная высота
для обязательного поля; кнопка `w-full` до 640, как уже сделано. **1440:** колонка `FORM_MAX_W`,
ряд укладывается в одну-две строки, шире не растягивается.

### 4. Роли в пуле драфта

`web/src/app/(admin)/underbeer/[id]/_components/player-line.tsx` (`DraftPlayerLine`) и
`pool-columns.tsx` — один компонент на оба формата.

UNDERBEER-турнира — покрыто `docs/tasks/37-*.md` (новый адрес).

## Acceptance criteria

- [ ] Гость записывается на Mix Cup, отмечает две роли → запись сохраняется, `desiredRoles`
      содержит обе
- [ ] Гость записывается на UNDERBEER-турнир, отмечает роль → тем же путём сохраняется
- [ ] Попытка отправить форму без отмеченной роли (любой из двух форматов) → отказ текстом на этом
      же шаге, поля формы не стираются (правило ТЗ 30)
- [ ] Оператор открывает борд драфта (Mix Cup или UNDERBEER-турнира) с таким участником → карточка
      в пуле одна, лежит в сегменте «Несколько ролей», подпись показывает все выбранные роли
- [ ] Игрок с местом в ростере (обычный участник лиги, попавший в этот же драфт) отображается в
      пуле как сегодня — одна роль, своя колонка, `desiredRoles` не участвует
- [ ] `npx tsc --noEmit`, `npm run lint`, `npm run build` чисто
