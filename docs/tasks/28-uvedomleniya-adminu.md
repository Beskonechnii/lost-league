# ТЗ 28: Уведомления оператору строками в колокольчике

**Статус:** **ready.** Состав событий подтверждён Стасом 16.09.2026: анкета новичка · привязка к профилю · заявка команды · правка профиля. Дубли профилей остаются бейджем — у расчёта похожести нет момента появления, события из него не сделать
**Входит в MVP:** нет — очереди видны на `/admin`, лига узнаёт о работе; это скорость реакции

## Цель

Оператор узнаёт о новой анкете, заявке команды или новом дубле там же, где узнаёт обо всём
остальном, — в колокольчике бара, на любой странице сайта. Сегодня признак «есть работа» живёт
бейджами на плитках `/admin`, и увидеть его можно, только зайдя туда. Закрыто, когда событие
очереди приходит строкой в панель колокольчика тем, у кого есть право этой очереди.

## Контекст

- Панель колокольчика есть: `web/src/app/_components/app-shell.tsx` (собирает `lines` из последних
  сообщений системной беседы) и `_components/notifications.tsx`; полная витрина — `/chat/system`.
- Системный канал: `web/src/lib/system-chat.ts` — `tellPlayer(playerId, …)` и
  `tellAccount(accountId, …)`. Адресации «всем, у кого есть право» нет.
- Очереди уже посчитаны одним местом: `lib/moderation.ts` → `moderationQueues(mayEdit)` даёт
  `profiles` (анкеты новичков), `links` (заявки на привязку к профилю), `teams` (заявки команд),
  `edits` (правки профиля) и `total`; `lib/duplicates.ts` → `duplicatesCount()`.
- Права очередей: `accounts.approve` — модерация, `roster.edit` — дубли и правки профиля.
- **Не противоречит** решению 04.09.2026 «системные уведомления живут в чате, а не в
  колокольчике»: канал остаётся тем же (беседа с лигой), новым становится только адресат —
  оператор вместо игрока. Второго списка сообщений работа не заводит.
- Решение Стаса 16.09.2026: **вариант B** — строками в колокольчике, тем же системным каналом.

## Scope

**Входит:**
- Адресация системного сообщения **всем аккаунтам с нужным правом**, а не одному игроку.
- Событие очереди → строка в колокольчике адресатов, с переходом на экран, где это разбирают.
- Минимальный состав событий (из того, что уже порождает очередь в продукте; подтверждается
  Стасом, см. «Открытые вопросы»):
  | Событие | Право | Куда ведёт строка |
  |---|---|---|
  | Пришла анкета новичка | `accounts.approve` | `/admin/moderation` |
  | Пришла заявка на привязку к профилю | `accounts.approve` | `/admin/moderation` |
  | Пришла заявка команды в турнир | `accounts.approve` | `/admin/moderation` |
  | Игрок прислал правку профиля | `roster.edit` | `/admin/moderation` |
- Сообщение уходит **один раз на событие**, а не при каждом заходе на страницу.

**НЕ входит:**
- Новый дубль профиля. Дубли не «приходят» событием: `duplicatesCount()` — расчёт похожести по
  всему ростеру, и момента появления у него нет. Останется бейджем на своей плитке.
- Дублирование этих событий в телеграм оператору — канал уже занят решениями по заявкам
  (`lib/tg-notify.ts`), второй поток туда же превратит бота в лог.
- Настройки уведомлений (что получать, что нет) — сначала пусть будет сам поток.
- Отдельная страница «Уведомления» — витрина есть, это `/chat/system`.
- Изменение того, что получает игрок: его сообщения остаются ровно как есть.

## Требования · DEV

- Рассылка по праву живёт рядом с `system-chat.ts` и переиспользует `tellAccount`: правило «кому
  можно» берётся из `lib/permissions.ts`, а не перечислением ролей по месту.
- Отправка не ломает действие, которое её породило: анкета сохраняется даже если сообщение не ушло
  (тот же уговор, что у `tg-notify.ts` и `tellAccount`).
- Сам себе лига не пишет: аккаунт, совершивший действие, своего же уведомления не получает.
- Текст строки называет предмет («анкета от `<ник>`», «заявка команды `<название>` в `<турнир>`»),
  а не «есть новое событие»: строка, по которой непонятно, что случилось, стоит ровно столько же,
  сколько бейдж.

## Требования · DESIGN

Заполняет роль `design`: отличима ли строка оператора от строки игрока в одной панели и нужно ли
их отличать, поведение счётчика непрочитанного, состояние «уведомлений нет».

## Требования · SEO

Не требуется: колокольчик и `/chat/system` — личные экраны, не индексируются.

## Acceptance criteria

- [ ] Подача анкеты новичка (через кабинет или бота) даёт строку в колокольчике у аккаунта
      с правом `accounts.approve`; в строке видно ник подавшего.
- [ ] Подача заявки команды в турнир даёт строку с названием команды и турнира тем же адресатам.
- [ ] Заявка на привязку к профилю даёт строку адресатам с `accounts.approve`.
- [ ] Правка профиля от игрока даёт строку адресатам с `roster.edit`.
- [ ] Переход по строке открывает `/admin/moderation`, и там лежит та самая запись.
- [ ] Аккаунт-игрок без этих прав ни одной из четырёх строк не получает.
- [ ] Повторный заход на страницы админки и перезагрузка не порождают новых копий строк по тому же
      событию (число строк по одной анкете остаётся одним).
- [ ] Сообщения игроку (решение по анкете, приглашение в состав, вызов в лобби) приходят как
      прежде — проверяется одним сценарием одобрения анкеты.
- [ ] `npx tsc --noEmit` и `npm run lint` чисто, `npm run build` проходит.
- [ ] 390px, **1280px** и 1440px без горизонтального переполнения панели.

## Открытые вопросы

**Состав событий — Стасу.** Выше взят минимум из того, что уже порождает очередь в коде: анкета
новичка, привязка к профилю, заявка команды, правка профиля. Подтвердить или дополнить одной
строкой. Кандидаты, которые `pm` сознательно не взял: новый дубль (момента появления нет, см.
«НЕ входит»), новое сообщение в чате лиги (это обычная личка, она и так приходит), старт и конец
приёма заявок по сроку (событие календаря, а не очереди — отдельная работа с расписанием).
