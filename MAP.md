# MAP — структура проекта

Где что лежит: папки, разделы приложения, слои логики, скрипты. Единственное место, куда смотрят
и человек, и агент, когда ищут файл.

Рядом: `CLAUDE.md` — правила работы и запуск · `BACKLOG.md` — что впереди ·
`ARCHITECTURE.md` — как устроены подсистемы · `DECISIONS.md` — почему так решили ·
`WORKLOG.md` — что делали по этапам.

## 2. Разделы приложения

Маршруты разделены на две группы: **`src/app/(public)/`** — продукт (его видит посетитель) и
**`src/app/(admin)/`** — служебная часть (всё, что пишет). Группы на URL не влияют, у каждой свои
layout, навигация и метаданные. Почему так, а не отдельным репозиторием — «Продукт и служебная
часть» в `ARCHITECTURE.md`.

Навигация — `src/app/_components/site-nav.tsx`. Верхняя строка **единая на весь сайт**: две вкладки
рядом — `Турниры` (продукт) и `Админ` (операторская); `PublicNav` и `AdminNav` рисуют её одинаково,
разными их держит лишь то, что зовут разные layout'ы. Отдельной вкладки «текущий сезон» нет:
всё, что относится к турниру — дивизионы, таблицы, ростер — лежит внутри `/tournaments/<slug>/…`.
`SubNav` — второй ряд подвкладок (ростер турнира: команды/игроки). У операторской вместо второго ряда
**постоянный сайдбар** (`(admin)/_components/admin-sidebar.tsx`); его пункты и плитки хаба `/admin` берутся
из одного реестра `(admin)/_components/tools.ts`. Вглубь витрин продукта ведут **крошки**, а не кнопка «Назад».
Тач-цели и промотка активной вкладки — одним токеном в `_components/nav-scroll.ts`. Стандарт — `UI-GUIDELINES.md`.
**Матч живёт в группе `(admin)`** — перенесён под вкладку «Админ» и
закрыт по роли наравне со студией; с лендинга его убрали.

| Раздел | Маршрут | Что делает | БД |
|---|---|---|---|
| **Лендинг** | `/` | Входная дверь продукта: кто такие, цифры сезона, карточки разделов. Цифры считаются из базы, не вписаны руками | читает (`count`) |
| **Матч** | `/match`, `/match/[id]` (группа `(admin)`) | Постгейм-отчёт по ID матча из OpenDota: скорборд, таланты, предметы, драфт, график золота. У отчёта постоянная ссылка — состояние (источник, вкладка, названия команд) живёт в query. Архив выгруженных картинок (файлы, не БД) лежит рядом. Живёт под вкладкой «Админ», требует роли (`/match` в `PROTECTED_PAGES`) **и права `tools`** — им же закрыт роут полки `/api/postgame/archive`, включая чтение | не трогает |
| **Карта вардов** | `/admin/vision` (группа `(admin)`) | Расстановка вардов команды по всем её картам из архива: выбор команды → сводное наложение + каждая карта с полоской времени (10-мин деления, 0:00 = вся расстановка). Данные в БД (`Ward`), строится офлайн | читает `Ward` |
| **Турниры** | `/tournaments`, `/tournaments/<slug>` + `/admin/tournaments`, `/admin/tournaments/<slug>/{import,registrations}` (право `tournaments.edit`), `/tournaments/<slug>/apply` | Сезон или кубок как сущность: описание, регламент, сроки, статус (`draft`/`registration`/`running`/`finished`) и дивизионы внутри. Команда встаёт в дивизион строкой `TournamentEntry` (там же группа и посев) — участие живёт отдельно от команды, потому что команда переживает турнир. Жеребьёвка — кнопкой «змейкой» по среднему MMR основы или руками построчно. «Текущий» для витрин — тот, что в статусе «Идёт». Публично видны все, кроме черновиков. Составы попадают в лигу двумя путями. **Импорт таблицы** оператором — мастер в три шага (источник → разбор → запись), пишет в ростер сразу: подтверждать себе нечего. **Заявка капитана** с сайта (пока турнир в статусе «Приём заявок») собирается мышью из пула игроков лиги (`/tournaments/<slug>/apply`: пул слева, слоты позиций справа, `@dnd-kit`), ложится в очередь `TeamApplication` и попадает в ростер только при апруве. В пуле только игроки с `account_id`; новичка зовут ссылкой `t.me/<бот>?start=invite` — он регистрируется в боте и появляется в пуле. Пишет ростер одна функция — `writeTeamToRoster`, проверки перед записью общие (`applicationProblems`). Логика — `src/lib/tournaments.ts` + `roster-import.ts`/`team-application.ts`, план — `TOURNAMENTS-PLAN.md` | пишет `Tournament`/`Division`/`TournamentEntry` |
| **Дивизион турнира** | `/tournaments/<slug>/<div>` (`d1`/`d2`) + `/groups`, `/playoff`, `/stats` | Раздел дивизиона: «Таблицы» — по группам, с зонами выхода; «Групповая стадия» — сетка встреч; «Плей-офф» — черновик сетки; «Статистика» — рейтинги игроков и команд, разрез (стадия + группа или половина сетки) живёт в query. Один шаблон на оба дивизиона, дивизион в URL. Старые адреса `/standings/<div>/…` — редирект на тот же раздел текущего турнира (`(public)/standings/[[...path]]`): ссылки раздавались в чат и стоят в закладках. Справочник дивизионов — `src/lib/divisions.ts` | читает + правит `Series` |
| **Ростер (турнир)** | `/tournaments/<slug>/roster/{teams,players}` + карточки `/roster/{teams,players}/<id>` | Витрина команд и игроков **турнира**: список строится по участию (`TournamentEntry`) и местам его дивизионов, поэтому новый сезон не показывает команды прошлого. Карточки остались общими — команда и игрок переживают турнир. Формы создания и операторская диагностика (пробелы в анкетах, `slug`) видны при праве `roster.edit` (`can()` из `account.ts`) — том же, что требуют роуты, куда эти формы пишут | читает |
| **Ростер (пул)** | `/roster` (таб рядом с «Турниры») | Общий пул команд лиги, **сквозной по всем турнирам**: фильтр по турниру + поиск (клиент, `pool-explorer.tsx`), список — `listPoolTeams()`. Каждой команде показывается её собственный актуальный состав (`teamDivision`, устойчив к «места есть, участия нет»). У оператора с правом `roster.delete` — **двухэтапное удаление**: разрез «В пуле / Архив» (`?view`), кнопки «Убрать из пула» (архив, `Team.archivedAt`, обратимо) и «Удалить полностью» (снос из архива). API — `DELETE /api/roster/teams/[id]?mode=archive\|purge` и `POST .../restore`. `/roster/{teams,players}` (без id) редиректят в текущий турнир | читает + `Team.archivedAt` |
| **Кабинет игрока** | `/me`, `/login/tg`, `/rules` + `/admin/moderation` | Вход **через Google (OAuth), по email+паролю ИЛИ по одноразовому коду из бота** (`/login/tg` — у пришедшего из телеграма почты нет вовсе, `src/lib/tg-login.ts`); первые два способа рядом, один аккаунт может держать оба (ключ — `email`). Писем нет: подтверждение почты и сброс пароля убраны (`ACCOUNTS-PLAN.md` §2.4), регистрация сразу пускает внутрь — но заводит аккаунт в статусе `draft`, то есть в **воронке модерации** (`draft` → `pending` → `active`/`rejected`). Пока `draft`/`rejected`, кабинет показывает **только анкету-заявку**: ник, имя, дата рождения, город, страна, позиция, **заявленный** MMR, телеграм, ссылки **каждая отдельным полем** (Dotabuff/Stratz/Steam) + согласие с `/rules` → `pending`. **Анкета уходит на модерацию только заполненной целиком**: обязательны все поля, кроме достижений; по ссылкам — хотя бы одна из трёх (у части игроков есть не каждый профиль). Правда одна — `normalizeApplication`, форма лишь дублирует её нативным `required`. Ветка «я уже в ростере» вместо анкеты подаёт заявку на привязку. `Player` до апрува не заводится — анкета лежит JSON'ом в `UserAccount.application`. Свою анкету одобренный правит на `/me/profile`, вход — на `/me/security`. Логика — `src/lib/account.ts` (+ `application.ts`/`password.ts`/`permissions.ts`), сессия — `player-auth.ts`/`player-session.ts`, OAuth — `google-oauth.ts` | пишет `UserAccount` |
| **Модерация** | `/admin/moderation` (группа `(admin)`, вкладки в query `?tab=links`) | Один раздел на все решения «пускать в лигу», четыре вкладки: «Регистрация личного профиля», «Привязка к профилю», «Заявки команд» (список со ссылкой на разбор внутри турнира) и «Правки профиля» — правки, присланные игроком из бота (`src/lib/profile-edit.ts`; разбираются здесь целиком, «было → стало», у фото — картинки рядом). Правки живут под своим правом `roster.edit`: это правка ростера, а не решение «пускать в лигу», и без права вкладки нет вовсе. Старые адреса `/admin/registrations` и `/admin/claims` редиректят сюда (`next.config.ts`); число новых видно на вкладке и на плитке `/admin`. Списки режутся **по виду заявки, а не по статусу аккаунта**: анкеты новичков — в первой вкладке (`pendingRegistrations`: `pending` + без claim), привязки — во второй (`pendingClaims`: есть `claimId`, нет `playerId`), независимо от того, пришла привязка из воронки регистрации или от уже открытого аккаунта. Одобрение везде одно — `approveRegistration`: заводит `Player` из анкеты (MMR ставит оператор — в анкете он заявленный) либо связывает выбранный профиль, и открывает аккаунт (`active`). Отказ разный: у анкеты и у привязки из воронки — `rejectRegistration` с причиной (человек видит её в кабинете), у привязки от открытого аккаунта — `rejectClaim` просто снимает заявку, из лиги никого не выкидывая. Право `accounts.approve` — проверяется и на странице (плашка вместо очереди), и в самих функциях | пишет `UserAccount` + создаёт `Player`, вкладка правок — `Player` |
| **Правила лиги** | `/rules` | Политика площадки: аккаунт и вход, заявка на вступление, пароль, данные профиля, поведение. Открыта всем — под ней подписываются в форме регистрации и при отправке анкеты. Текст — документ в коде (`(public)/rules/page.tsx`), отдельной модели ради одной страницы нет | не трогает |
| **Команда лиги** | `/admin/staff` (право `accounts.admins`, у владельца всегда) | Владелец и админы **отдельными списками** + «остальные аккаунты»: назначение и снятие роли, у каждого админа чекбоксы прав из `permissions.ts`. Владелец — по `OWNER_EMAIL` (вошёл этой почтой → `owner`, роль и права неотчуждаемы). Новый админ получает **ноль** прав; снятие роли их гасит. Свой аккаунт из панели не правится. Пришла на смену `/admin/roles` (тот теперь редирект в `next.config.ts`) | пишет `UserAccount.role` + `.permissions` |
| **TP** | `/tp` (public, `?all=1` — за всё время) + `/admin/tp` (группа `(admin)`) | **Турнирный** зачёт очков MVP: витрина показывает зачёт текущего турнира, переключатель — сумму за всё время. Истина — реестр `PointsEntry` (reason=`tp`, `tournamentId`), `Player.tp` остался кешем «за всё время» для карточек. Правит оператор на `/admin/tp` (pouf-стиль, как архив серий): построчно или кнопкой «Начислить очки» (окно с выбором игрока + поле очков, без команд — зачёт сквозной по сезонам). Пишет через `PATCH /api/roster/players/[id]` полем `tp` (роут кладёт **разницу** строкой в реестр, а не переписывает поле — `src/lib/tp.ts`); право: поле `tp` требует `tp.edit`, любое другое — `roster.edit`. Первичная заливка — `scripts/import-tp.ts` из столбца «B_TP» листа «Игроки» | читает + правит `Player.tp` |
| **Встреча** | `/series/<slug>` | Публичная страница серии: счёт, карты одна под другой, у каждой оба состава с героями и K/D/A. Форма — с разбора серии на Dotabuff; детали карты не дублирует, ведёт в `/match/<id>`. Ключ в адресе — слаг (`guzliki-vs-from-paris`), а не `id`: `id` после `db:import` другой | читает |
| **Архив серий** | `/admin/series` | Встречи турнира (группа и плей-офф) и карты в них: завести, привязать/отцепить/перечитать карту, удалить встречу. Фильтр по разрезам (группа A/B, верхняя/нижняя сетка, гранд-финал). **Единственный вход в архив**: привязка карты сразу читает стату, из неё считается «Статистика» дивизиона | пишет `Series` + `Match` + `MatchStat` |
| **Правка ростера** | `/admin/roster/{teams,players}/<id>/edit` | Формы — **сюда пишут**. Живут в `(admin)`, поэтому граница видна прямо в URL | пишет |
| **Студия · Шаблоны** | `/studio` | Сборка графики по данным лиги — **только читает ростер** | читает + `Render` |
| **Студия · Генерация** | `/studio/generate` | Картинки по промту через OpenAI Images (платно) | не трогает |
| **UNDERBEER 2.0** | `/underbeer`, `/underbeer/<id>` | Шоу-драфт: капитаны по очереди (змейка) собирают команды из ростера, у каждой по разу «закрепить»/«украсть». Состояние — `DraftSession.payload` JSON. Операторское, за паролем | читает ростер + `DraftSession` |
| **Оверлей драфта** | `/overlay/underbeer/<id>` | «Голый» публичный рендер результата драфта для OBS-сцены — без навигации и пароля (группа `(bare)`) | читает |
| **1х1 / fearless draft** | `/admin/1x1`, `/admin/fearless-draft` | Заглушки будущих инструментов админки («в разработке»). Держат место в ряду `Админ`; общий компонент `WorkInProgress` в `(admin)/_components/wip.tsx` | не трогает |
| **Вход / доступ** | `/me` (кабинет), `/login/tg` (код из бота) | Вход — через Google **или email+пароль** (пароля-админки больше нет; «Забыли пароль» тоже нет — писем не шлём). Доступ к служебной части даёт роль сессии (owner/admin), а конкретный раздел — **право** из `permissions.ts`. Проверка **на трёх уровнях**: `proxy.ts` (роль), страница (`denyUnlessPermission` — плашка «попросите владельца»), пишущий API-роут (`guard` → 403). Закрыто всё, что пишет: `/studio*`, `/admin*`, `/underbeer*`, `/match*`, не-GET к `/api/*`. Вкладку «Админ» в шапке видят только админы, плитки `/admin` и операторские кнопки на публичных витринах — только владельцы нужного права. Публичная часть открыта (вкл. `/me`) | не трогает |
| **Тема** | `/admin/theme` (группа `(admin)`) | Панель цветов UI: акцент (бренд/D1 + D2), поверхности, текст, границы **и слой 1st-Pouf** (фон/поверхность/текст pouf + статусы warn/down/up/info/orange — бейджи, «в разработке»). Живое превью обоих слоёв, «Сохранить» пишет `PUT /api/theme` → `data/theme.json`. Корневой layout ставит значения инлайн-`style` на `<html>`=`:root`; токены LOST в `globals.css` развёрнуты в `var(--lost-*, fallback)`, а pouf-переменные скоуп `.pouf-lost` раздаёт из `var(--lost-pouf-*, fallback)`. Значения санитайзятся. Хранилище — `theme-store.ts`, чистая логика — `theme.ts` | не трогает БД (файл) |

Направление данных важное: **ростер — источник, студия и таблица — потребители.** Если студии не хватает поля
у команды/игрока — оно заводится в модели ростера, а не дублируется в payload шаблона.

## 3. Ключевые слои (`src/lib/`)

| Файл | Ответственность |
|---|---|
| `prisma.ts` | singleton клиента. Prisma 7 требует driver-adapter (грабли — `CLAUDE.md`) |
| `auth.ts` | **чистый модуль** (его тянет `proxy.ts`): только `needsAdmin()` — карта того, что требует прав администратора. Кто их имеет — вопрос роли (`player-auth.ts`), не пароля. Развилка — `src/proxy.ts` |
| `admin-session.ts` | **только сервер**: `isAdmin()` — «админ ли вообще»; остался ровно для вкладки «Админ» в шапке. Что показывать на странице, решает право (`can()` в `account.ts`), а не роль. Отдельно от `auth.ts`, потому что `next/headers` нельзя тянуть в `proxy.ts` |
| `google-oauth.ts` | **только сервер**: ручной OAuth-флоу Google для входа игроков (без NextAuth). `authUrl`/`exchangeCode` + распаковка `id_token`. Ключи `GOOGLE_CLIENT_ID/SECRET` в `.env` |

## 4. Движок студии (`src/studio/`)

**Шаблон = размер холста + декларативная схема полей + React-компонент.** Форма мастера строится из схемы
автоматически, поэтому **новый шаблон = файл в `templates/` + строка в `registry.ts`**, без новых страниц и форм.

| Файл | Роль |
|---|---|
| `types.ts` | контракт: `FieldDef` (text/select/team/player/match/group), `TemplateDef`, `ScoreBoard`, хелперы `asText/asTeam/asPlayer/asBoard/asRows` |
| `registry.ts` | единственная точка регистрации шаблонов |
| `resolve.ts` | payload формы (id строкой) → развёрнутые объекты для рендера. Поле `match` разворачивается через `Refs.boards` (скорборд карты, см. `lib/scoreboard.ts`) |
| `Canvas.tsx` | превью: натуральные пиксели под `transform: scale`, contain по обеим сторонам |
| `templates/parts.tsx` | общие куски шаблонов |

Страницы студии — в `src/app/studio/`: `page.tsx` (список), `new/[templateId]` (мастер),
`_components/wizard.tsx` (форма + превью + экспорт), `render/[templateId]` («голый» рендер),
`generate/` + `_components/generator.tsx` (генерация по промту — к движку шаблонов отношения не имеет).

Что важно помнить:
- **Превью и экспорт — один и тот же компонент.** Экспорт PNG клиентский (`modern-screenshot`), масштаб снимается
  на клоне → PNG выходит ровно `size.w × size.h`. Поэтому «что вижу — то и скачал»; не ломать этот инвариант.
- `/studio/render/[templateId]?p=<base64>` — рендер без интерфейса, задел под серверный скриншот (Playwright).
- Сохранённые генерации — модель `Render` (payload формы строкой), открываются обратно через `?render=<id>`.
- Подложки шаблонов — `public/templates/<id>/bg.png`. Файла нет → фирменный градиент-заглушка.


## 5. Наполнение ростера (три шага)

```bash
npx tsx scripts/sheet-to-roster.ts --sheet "<ссылка на таблицу>"   # → data/roster.json
npx tsx scripts/import-roster.ts                                    # → БД, upsert по slug
npx tsx scripts/import-media.ts --from "<папка>"                    # лого/фото по имени файла = slug
npx tsx scripts/import-crm.ts --file "<выгрузка.xlsx|csv|json>" --dry   # анкеты из CRM в уже заведённых игроков
npx tsx scripts/resolve-vanity.ts --dry                             # steamcommunity.com/id/<имя> → account_id (нужен STEAM_API_KEY)
```

Игрок без `account_id` не попадает ни в один архив матча — его просто некем опознать. Ссылки на
Dotabuff/Stratz/OpenDota и `profiles/<steam64>` разбираются на лету (`playerAccountId` в
`src/lib/profiles.ts`), а именной адрес Steam превращает в число только `resolve-vanity`.

Берётся **xlsx**-экспорт, не CSV: ссылки на профили — гиперссылки ячеек, в CSV их нет.
Есть готовый скилл `roster-sync` — он это и делает. Второй скилл, `ship`, — коммит и пуш.

## 6. Перенос данных между устройствами

`dev.db` в `.gitignore`, поэтому состояние лиги ездит снимком `data/snapshot.json` (он **коммитится**):

```bash
npm run db:export   # БД → снимок. Делать перед коммитом, если правил данные в UI
npm run db:import   # снимок → БД. Делать после git pull
```

Импорт — **зеркало**: база становится копией снимка, лишнее удаляется (список печатается, есть `--dry`).
Снимок версионируется (`version`, сейчас **11**); старую версию импорт не чинит, а отвергает — пересними базу
свежим экспортом там, где данные актуальны. Перед записью импорт печатает, где строк в снимке
**меньше**, чем в базе — молча потерять руками введённую сетку встреч он не должен.
Связи в снимке идут по `slug`, а не по id: id автоинкрементные и на разных машинах разные. Разбор — в
`DECISIONS.md` («Решение: снимок БД в git»).
