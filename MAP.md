# MAP — структура проекта

Где что лежит: папки, разделы приложения, слои логики, скрипты. Единственное место, куда смотрят
и человек, и агент, когда ищут файл.

Рядом: `CLAUDE.md` — правила работы и запуск · `BACKLOG.md` — что впереди ·
`ARCHITECTURE.md` — как устроены подсистемы · `DECISIONS.md` — почему так решили ·
`WORKLOG.md` — что делали по этапам.

## 2. Разделы приложения

Маршруты разделены на две группы: **`src/app/(public)/`** — продукт (его видит посетитель) и
**`src/app/(admin)/`** — служебная часть (всё, что пишет). Группы на URL не влияют, у каждой свои
layout, навигация и метаданные. Почему так, а не отдельным репозиторием — «Продукт и служебная
часть» в `ARCHITECTURE.md`.

Навигация — **один сайдбар на обе группы маршрутов** (решение 02.09 в `DECISIONS.md`; верхней строки
сайта больше нет). Собирает его `src/app/_components/app-shell.tsx` — серверный компонент, который
знает, кто вошёл и что ему разрешено; рисует `app-sidebar.tsx` — клиентская колонка с тремя
состояниями (полная 300px / рельс значков 76px / рельс + `Sheet` на телефоне). В шапке колонки —
бренд, профиль-блок (единственный вход в кабинет) и **поиск по лиге** (`league-search.tsx` →
`/api/search` → `lib/search.ts`: команды, игроки, турниры по имени, тегу и слагу). Секции: «Лига»
(`Турниры`, `Ростер`), инструменты оператора из реестра `_components/tools.ts` (он же кормит плитки
хаба `/admin`) и «Кабинет» (там же `Сообщения` со счётчиком непрочитанного — только у игрока лиги);
под поиском — строка «N в сети» (`_components/chat-live.tsx`). Порядок секций — по частоте обращения
(`Кабинет` → `Модерация` → `Лига` → `Showmatch` → остальные инструменты), сортировка в `app-shell.tsx`; пункт без права не рисуется. Всё, что относится к турниру — дивизионы,
таблицы, ростер сезона — лежит внутри `/tournaments/<slug>/…` и выбирается строкой турнира
(`_components/tournament-bar.tsx`), а не колонкой. `SubNav` (`_components/sub-nav.tsx`) — ряд
подвкладок раздела, остался у студии. Вглубь витрин продукта ведут **крошки**, а не кнопка «Назад».
Тач-цели и промотка активной вкладки — одним токеном в `_components/nav-scroll.ts`. Стандарт — `UI-GUIDELINES.md`.
**404 и «страница упала»** собирает `_components/stub-page.tsx`; его показывают `app/not-found.tsx`
(корень — сам оборачивается в `AppShell`, потому что корневой layout навигации не рисует),
`(public)/not-found.tsx` и `(admin)/not-found.tsx` (колонку даёт layout группы) и клиентская
граница `app/error.tsx` с `reset()`. **Состояние загрузки** — `loading.tsx` витрин
(дивизион, оба ростера, карточка игрока) на компонентах `components/pouf/skeleton.tsx`.
**Общая обвязка служебных экранов** — `(admin)/_components/`: `admin-header.tsx` (крошки → eyebrow →
H1 → поясняющая фраза), `panel.tsx` (подушка блока с заголовком, плотность 16px),
`permission-gate.tsx` (гейт раздела по праву), `session-list.tsx` (архив сессий эфемерного
инструмента: карточка, статус, удаление — один на UNDERBEER и fearless, Э11b), `tools.ts` (реестр
инструментов для сайдбара и плиток `/admin`), `wip.tsx`. Свою шапку и свои рамки экраны админки
не верстают (Э9).

**Матч живёт в группе `(admin)`** — перенесён под вкладку «Админ» и
закрыт по роли наравне со студией; с лендинга его убрали.

`/me/security` — редирект). `/me` остаётся дверью ровно для тех, у кого страницы в лиге ещё нет:
гость, анкета в воронке, ожидание решения, привязка к существующему профилю. Логика — `src/lib/account.ts` (+ `application.ts`/`password.ts`/`permissions.ts`), сессия — `player-auth.ts`/`player-session.ts`, OAuth — `google-oauth.ts` | пишет `UserAccount` |
| **Модерация** | `/admin/moderation` (группа `(admin)`, вкладки в query `?tab=links`) | Один раздел на все решения «пускать в лигу», четыре вкладки: «Регистрация личного профиля», «Привязка к профилю», «Заявки команд» (список со ссылкой на разбор внутри турнира; в строке — «подтвердили N из M» по ответам позванных, `src/lib/team-invites.ts`) и «Правки профиля» — правки, присланные игроком из бота **или с сайта** (`src/lib/profile-edit.ts`; разбираются здесь целиком, «было → стало», у фото — картинки рядом). С сайта в эту очередь идут **ник, город, ссылка на профиль и MMR** из `/me/profile` — правило одно на оба входа: через оператора то, чем человек представлен лиге, напрямую (имя, страна, дата рождения, телеграм) — то, что касается только его (`DECISIONS.md`, 04.09.2026). Правки живут под своим правом `roster.edit`: это правка ростера, а не решение «пускать в лигу», и без права вкладки нет вовсе. Старые адреса `/admin/registrations` и `/admin/claims` редиректят сюда (`next.config.ts`); число новых видно на вкладке и на плитке `/admin`. Списки режутся **по виду заявки, а не по статусу аккаунта**: анкеты новичков — в первой вкладке (`pendingRegistrations`: `pending` + без claim), привязки — во второй (`pendingClaims`: есть `claimId`, нет `playerId`), независимо от того, пришла привязка из воронки регистрации или от уже открытого аккаунта. Одобрение везде одно — `approveRegistration`: заводит `Player` из анкеты (MMR ставит оператор — в анкете он заявленный) либо связывает выбранный профиль, и открывает аккаунт (`active`). Отказ разный: у анкеты и у привязки из воронки — `rejectRegistration` с причиной (человек видит её в кабинете), у привязки от открытого аккаунта — `rejectClaim` просто снимает заявку, из лиги никого не выкидывая. Право `accounts.approve` — проверяется и на странице (плашка вместо очереди), и в самих функциях | пишет `UserAccount` + создаёт `Player`, вкладка правок — `Player` |
| **Телеграм-бот** | `/admin/bot` + `/admin/bot/flow` + `/admin/bot/flow/guide` | Что бот говорит и как ведёт разговор. На `/admin/bot` — только тайминги и тексты уведомлений (`BotSetting`, в БД отличия от дефолта в коде): у них нет входящего сообщения и потому нет ноды. Вкладка «Вопросы» (`BotQuestion`) убрана на Э6 — формулировка шага стала свойством ноды. **`/admin/bot/flow` — редактор графа диалога** (`BOT-FLOW-PLAN.md` Э2): канвас на атоме Кита `pouf/board.tsx`, палитра девяти типов нод, связи мышью от кружка выхода до ноды, инспектор выбранной ноды (текст, переменная, проверка ответа, кнопки с условиями показа, выходы) и версии — черновик, «В эфир», откат публикацией уже существующей версии. Там же (Э3) панель «Проверка» — список претензий валидатора, ошибки не пускают в эфир, — и «Симулятор»: прогон диалога прямо по графу с экрана, с подсветкой активной ноды и содержимым переменных, без записи сессии и без Telegram. Там же (Э6) панель «Перехваты» — что бот разбирает раньше ноды, на которой стоит разговор (`/start`, `/cancel`, кнопки первого уровня, кнопки из уведомлений), и поле ноды «служебная кнопка»: срабатывает перехват или повторяется вопрос. С Э7 графов несколько (`?flow=main|invite|answer|…`): переключатель и заведение нового флоу — сверху, панель «Точка входа» — как в этот граф попадают (главный флоу, хвост deeplink'а, кнопка из уведомления). Граф уезжает на сервер целым JSON-документом по кнопке, а не по каждому перетаскиванию. Отдельным маршрутом, а не вкладкой: канвасу нужна ширина витрины. Право у обоих одно — `tournaments.edit` С Э8 рядом лежит **гайд оператора** — `/admin/bot/flow/guide` (`flow/guide/page.tsx` + `flow/guide/_components/`): вводная для того, кто открыл редактор впервые — разбор каждого типа ноды и каждого поля инспектора, переменные, реестры действий и модулей, точка входа и перехваты, черновик и версии, симулятор, таблица «сообщение валидатора → что значит → как чинить», рецепты и разбор поломки. ## 4. Движок студии (`src/studio/`)

**Шаблон = размер холста + декларативная схема полей + React-компонент.** Форма мастера строится из схемы
автоматически, поэтому **новый шаблон = файл в `templates/` + строка в `registry.ts`**, без новых страниц и форм.

| Файл | Роль |
|---|---|
| `types.ts` | контракт: `FieldDef` (text/select/team/player/match/group), `TemplateDef`, `ScoreBoard`, хелперы `asText/asTeam/asPlayer/asBoard/asRows` |
| `registry.ts` | единственная точка регистрации шаблонов |
| `resolve.ts` | payload формы (id строкой) → развёрнутые объекты для рендера. Поле `match` разворачивается через `Refs.boards` (скорборд карты, см. `lib/scoreboard.ts`) |
| `Canvas.tsx` | превью: натуральные пиксели под `transform: scale`, contain по обеим сторонам |
| `templates/parts.tsx` | общие куски шаблонов |

Страницы студии — в `src/app/studio/`: `page.tsx` (список), `new/[templateId]` (мастер),
`_components/wizard.tsx` (форма + превью + экспорт), `render/[templateId]` («голый» рендер),
`generate/` + `_components/generator.tsx` (генерация по промту — к движку шаблонов отношения не имеет).

Что важно помнить:
- **Превью и экспорт — один и тот же компонент.** Экспорт PNG клиентский (`modern-screenshot`), масштаб снимается
  на клоне → PNG выходит ровно `size.w × size.h`. Поэтому «что вижу — то и скачал»; не ломать этот инвариант.
- `/studio/render/[templateId]?p=<base64>` — рендер без интерфейса, задел под серверный скриншот (Playwright).
- Сохранённые генерации — модель `Render` (payload формы строкой), открываются обратно через `?render=<id>`.
- Подложки шаблонов — `public/templates/<id>/bg.png`. Файла нет → фирменный градиент-заглушка.


## 5. Наполнение ростера (три шага)

```bash
npx tsx scripts/sheet-to-roster.ts --sheet "<ссылка на таблицу>"   # → data/roster.json
npx tsx scripts/import-roster.ts                                    # → БД, upsert по slug
npx tsx scripts/import-media.ts --from "<папка>"                    # лого/фото по имени файла = slug
npx tsx scripts/import-crm.ts --file "<выгрузка.xlsx|csv|json>" --dry   # анкеты из CRM в уже заведённых игроков
npx tsx scripts/resolve-vanity.ts --dry                             # steamcommunity.com/id/<имя> → account_id (нужен STEAM_API_KEY)
```

Игрок без `account_id` не попадает ни в один архив матча — его просто некем опознать. Ссылки на
Dotabuff/Stratz/OpenDota и `profiles/<steam64>` разбираются на лету (`playerAccountId` в
`src/lib/profiles.ts`), а именной адрес Steam превращает в число только `resolve-vanity`.

Берётся **xlsx**-экспорт, не CSV: ссылки на профили — гиперссылки ячеек, в CSV их нет.
Есть готовый скилл `roster-sync` — он это и делает. Второй скилл, `ship`, — коммит и пуш.

## 6. Перенос данных между устройствами

`dev.db` в `.gitignore`, поэтому состояние лиги ездит снимком `data/snapshot.json` (он **коммитится**):

```bash
npm run db:export   # БД → снимок. Делать перед коммитом, если правил данные в UI
npm run db:import   # снимок → БД. Делать после git pull
```

Импорт — **зеркало**: база становится копией снимка, лишнее удаляется (список печатается, есть `--dry`).
Снимок версионируется (`version`, сейчас **11**); старую версию импорт не чинит, а отвергает — пересними базу
свежим экспортом там, где данные актуальны. Перед записью импорт печатает, где строк в снимке
**меньше**, чем в базе — молча потерять руками введённую сетку встреч он не должен.
Связи в снимке идут по `slug`, а не по id: id автоинкрементные и на разных машинах разные. Разбор — в
`DECISIONS.md` («Решение: снимок БД в git»).
